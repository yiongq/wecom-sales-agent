# 检索评测：现状与混合检索（真实嵌入）

2026-11-07 · 18 号 spec R5、plan 4.2 与 4.4 · 混合检索实现在 `src/core/retrieval-hybrid.ts`、`src/packs/industrial/match.ts`，与本报告同一个 PR · 嵌入用智谱 `embedding-3`（2048 维）

## 结论

- **总体**：截断 recall@5 从 91.0% 提到 98.5%，MRR@5 从 68.3% 提到 98.4%。精确型号、别名、系列前缀三类两种实现都是 100%。误给型号两种实现都是 0/45。
- **提升集中在不带完整型号的三类问法**：属性组合的 MRR 从 37.4% 到 98.9%，描述性的 recall 从 84.4% 到 97.3%，口语/错别字的 recall 从 62.8% 到 93.4%。现状能找到相关产品，但会按「有货、型号字母序」重排，把相关度的顺序丢掉。
- **64 条手写查询**（最接近真实问法）：recall 从 78.2% 到 91.0%，MRR 从 85.4% 到 95.1%。其中口语/错别字只到 62.5%，是剩下最弱的一类。
- **速度与内存**：单次检索 p95 从 32.3 ms 降到 15.8 ms（不含查询嵌入的网络往返）。2048 维向量本身两种实现都约占 88 MB；混合检索的关键词与属性索引另占 9.7 MB。
- 验收 16–18 全部满足，逐条见文末。

## 怎么测的

- **产品库**：`eval/retrieval/gen-catalog.ts` 用种子 1805 生成 5000 条，沿用 `PartSchema` 的 4 个类目。sha256 `e4b7c580…04464e2`，用种子重新生成后逐字节一致。
- **查询集**：`eval/retrieval/gen-queries.ts` 生成 704 条，8 类各 88 条，其中手写 64 条（每类 8 条，来自 `queries.handwritten.json`）。sha256 `988c5f61…bded1a`。
  - 精确型号、别名、系列前缀、属性组合、描述性、口语/错别字六类：每条有 1–5 个相关条目。
  - 宽泛（broad）：相关条目都超过 5 个，只计 precision。
  - 库里没有：没有相关条目，只看空结果率和误给型号。
- **指标**：逐条计算后按查询宏平均。
  - 截断 recall@5 = 前 5 条里的相关数 ÷ min(5, 相关条目数)。
  - precision@5 = 前 5 条里的相关数 ÷ 返回条数，返回 0 条记 0。
  - MRR@5 取前 5 条里第一个相关结果名次的倒数。
  - 误给型号率的分母是走到语义回退的纯型号查询（45 条），只要返回了规格里不含这串字符的型号就算一次误给。
- **嵌入**：产品文本与生产代码的 `retrievalText` 相同（型号、名称、类目、规格、别名）。产品向量和查询向量都在计时之外生成，匹配器内部照常做余弦计算：现状对全部 5000 条向量做召回，混合检索只给属性过滤后的候选打分。每个查询最多调一次嵌入，评测脚本里有断言。
- **费用**：付费运行 1 次，共 90 次请求、312,968 tokens、¥0.156。之后用下文「复现」里的命令从向量缓存复跑，0 次请求，质量指标逐项一致。下表和同目录的 JSON 都取自这次复跑：开了 `--expose-gc`，内存数字更干净；延迟每次跑会差 1 ms 左右。
- **环境**：Node v22.22.0，darwin/arm64。

## 和假嵌入的对照

开工时先用假嵌入（字符 n-gram 哈希，256 维，不懂语义）跑过同一套数据：

| 总体          | 假嵌入 现状 → 混合 | 真实嵌入 现状 → 混合 |
| ------------- | -----------------: | -------------------: |
| 截断 recall@5 |        94.6 → 99.9 |          91.0 → 98.5 |
| MRR@5         |        76.0 → 99.7 |          68.3 → 98.4 |
| precision@5   |        58.2 → 60.9 |          57.6 → 60.0 |

换成真实嵌入后，两种实现的数字都比假嵌入低一些。查询是照产品库的写法生成的，字面重合多，假嵌入其实相当于又一路关键词匹配，所以它给出的数字偏乐观。两种嵌入下的结论方向一致。

## 局限

- **生成查询对关键词偏有利**：生成查询和产品文本出自同一套词表。手写子集的总体 recall 是 91.0%，比全部查询低 7.5 个百分点，真实问法下大概也在这个区间。
- **延迟没算嵌入往返**：两种实现每个查询都调一次嵌入（精确型号、别名、系列前缀命中时不调），线上还要加这一次网络往返。
- **库里没有的东西**：两种实现都有约一半返回了不相关的候选，没有给出空结果。混合检索在这一类上没有变好，也没有变差。要不要在这类问法下直接说「没有」，是产品上的取舍，不在 18 的范围内。
- **precision 的上限**：很多查询只有 1–2 个相关条目，却固定返回 5 条，precision 的上限就是 20%–40%。

## 复现

在仓库根目录跑：

```bash
node --import tsx eval/retrieval/gen-catalog.ts
node --import tsx eval/retrieval/gen-queries.ts
node --expose-gc --import tsx eval/retrieval/run.ts --matcher current --embed real --env-file .env --out var/retrieval/real/current.json
node --expose-gc --import tsx eval/retrieval/run.ts --matcher hybrid --embed real --env-file .env --out var/retrieval/real/hybrid.json
```

- `--env-file` 只读嵌入用的变量（`EMBED_*`、`ZHIPU_*`、`LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_API_KEY`）。
- 请求只发往生产代码里的境内端点清单，费用默认封顶 ¥1（`--max-yuan`）。
- 向量按「模型 + 文本」缓存在 `var/retrieval/embed-cache`，第二条命令不再花钱。

同目录的 `current.json` 和 `hybrid.json` 是两种实现的完整结果。
