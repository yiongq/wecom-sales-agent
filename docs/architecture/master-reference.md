# wecom-sales-agent 总参考

一句话：企业微信「微信客服」等渠道上的 AI 销售与客服 agent，钱和订单由代码确定性把关；正在从单店 demo 演进为多租户、按行业包扩展的生产级产品。

## 项目定位

客户在微信里被 AI 接待：了解需求，按商家的产品库推荐和报价，建单，付款后跟进；遇到明确要人工、投诉、退款或 AI 处理不了的情况，转给人工顾问。模型只负责理解和话术，价格、链接、订单、转人工这类必须每次都对的事由代码决定和核对。当前的参考实现是虚构品牌「云途定制旅行」的高端定制游，产品数据也是虚构的。产品化的目标是让同一套引擎通过「行业包（代码）+ 租户数据（数据库）」服务不同商家，运营人员在后台自己改 SOP 和产品库，每次改动都有版本、过发布闸、可以回滚。仓库以 MIT 公开；市场、客户和收费相关的判断不在本仓库，另记。动工前的初始规格存档在 [initial-spec.md](./00-baseline/initial-spec.md)，只作历史参考，当前事实以代码和各阶段 spec 为准。

### 仓库与工程约定

照搬 Tenon 的做法，owner 于 2026-09-25 确认；细则以 `AGENTS.md` 为准。

- 开发方式：SDD，每个目标只有 `spec.md` 与 `plan.md` 两个文件。唯一例外是 `00-baseline/` 里另存的历史存档 `initial-spec.md`，不再更新。
- 分支：`dev` + `main`，PR 合进 `dev`。
- 提交：Conventional Commits，标题不超过 50 字符；commit-msg hook 拦截 AI co-author 署名。
- 门禁：`package.json` 里的 `format:check`（oxfmt 0.68）、`lint`（oxlint 1.83）、`typecheck`（`tsc --noEmit`）、`test` 四个名字是唯一接口，hook、CI、Stop hook 都只调这四个名字。`test` 把 6 组自测和 `LLM_MOCK=1` 的回归串成一个脚本，不迁 vitest。加入 `console/` 之后，四个名字不变，内容扩到覆盖它（ADR-002 决策 3）。
- hook：lefthook 2.1 负责 pre-commit（format:check、lint、typecheck）和 commit-msg（commitlint、署名拦截）；Claude Code 另有 Stop hook。
- 全仓首次格式化单独一个提交，写进 `.git-blame-ignore-revs`（00 的 plan 里做）。
- 文档：`AGENTS.md` 用英文，其余用中文。
- 行业包目录：`src/packs/<name>/`。公开白名单是 `travel`、`ecommerce-aftersales`，其余由门禁拦截（ADR-003 决策 4）。

### 决策细节

#### 先做国内适配（技术原因）

- **模型**：国内只调用已备案的国产模型，模型调用不出境。适配海外就要换模型：OpenAI 不支持中国大陆和香港；Anthropic 限制中国控制的实体使用；智谱在美国实体清单上。剩下的选择只有托管在海外的开源权重模型，8 秒延迟线和前缀缓存都得重新横评（未核实）。
- **渠道**：海外主渠道是 WhatsApp Cloud API 和 Instagram 私信，和微信客服的接入方式、会话窗口、额度规则都不同，要另写适配器。WhatsApp 允许业务型 bot，2026-01-15 起禁止的是通用 AI 聊天机器人。
- **代码**：金额识别只认 ¥；整行没有汉字会被判成注入残留；英文化估计要 2–4 周。
- **保留的三条缝**：金额带币种、下限可配；租户表带 `locale/region`（01 建表时就带）；渠道能力描述。海外适配什么时候启动按信号，信号另记。

#### 渠道

- 国内按优先级：
  1. **微信客服（kf），做深**：多账号；48 小时内最多 5 条的发送额度账本；接收 `msg_send_fail` 回执，因为按官方文档，接口返回成功不代表已送达。现在的适配器把系统事件全过滤掉了。
  2. **网页 / H5 组件**：模拟器转正，不依赖任何平台。转正时要换新的渠道名和 id 前缀，因为 `sim-` 会话按演示数据处理：凭 id 就能匿名读，闲置 24 小时自动删。
  3. **认证服务号的客服消息**：有条件才做，前提是商家有服务号粉丝，粉丝又习惯在公众号对话框里直接发消息。
- 不做：
  - 抖音私信：第三方转述说已不给新开发者开通（未核实）。
  - 小红书：只开放给授权的 IM 服务商。
  - 淘宝、京东、拼多多：企业 ISV 门槛。
  - 语音：引擎一轮最多约 8 秒，语音要求 1 秒以内。
  - 企微员工号 RPA，或以销售个人身份托管 1v1 私聊：平台在打击外挂，也和 AI 显式标识冲突。1v1 场景只做「会话存档 + AI 辅助，由人点发送」。
- 海外渠道（后置）：WhatsApp Cloud API（用商家自有的 WABA）、网页组件（和国内共用）、Instagram 私信。
- 渠道层 v2 在 04 做：统一入站事件、消息部件、渠道能力描述、按窗口的发送账本；新增一个平台只加一个适配器，不改引擎。

#### 场景模板

- **模板的构成**：行业包（代码，随仓库版本走，放在 `src/packs/<name>/`）+ 默认 SOP 分节与 policy + 产品库 schema 与样例数据 + 评测用例。租户自己的 SOP 版本、产品库和知识库在数据库里。开通租户时，把模板默认值复制成 SOP v1，并绑定该包的回归用例。
- **定制游**：参考实现、演示实例和回归基线，品牌和产品数据都是虚构的。03 补售后退改。
- **电商售后**：第二个公开参考包，用合成数据。形态是售后和工单：查订单要订单号加邮箱核验，核验失败不返回任何数据；查政策；退款额由代码算；申请退款做幂等；只有未发货的订单能改地址。设计为英文、多币种，可对标 τ²-bench retail。
- **来自客户的行业包（如有）**放私有（ADR-003）。
- 引擎里的旅游逻辑现在是写死的，04 才抽成行业包。第二个真实行业包跑通之前，「通用」只是设计主张，不是已验证的能力。
- 所有包的共同前提：价格护栏只看 ≥1000 的金额，金额识别只认 ¥。这两处都要改成配置，否则到了低单价行业（比如按课时收费）护栏会完全失明。

#### AI 显式标识

- 依据：《人工智能生成合成内容标识办法》第四条要求在文本的起始、末尾或中间加提示，或者在交互界面显著位置加提示；《互联网信息服务深度合成管理规定》第十七条要求对可能导致公众混淆的智能对话做显著标识。「被问才承认」不构成标识。
- 做法：
  - 客服账号名和欢迎语首句都写明「AI 旅行顾问」。账号名要在企微后台手动改。
  - 对话里不反复自称机器人。
  - 「被问必认」的代码兜底保留。
  - 网页模拟器早就标着「AI 顾问在线」，两个渠道口径一致。
- demo 也开：demo 的客服二维码公开挂在 guide 页上，面向真实微信用户，在标识办法的适用范围内。实现成本约半天，生产本来就要这个开关。
- prod 强制开：`DEPLOY_PROFILE=prod` 下租户设置关不掉，发布闸也检查这一项。
- 给租户预留公示模型名称和备案号的位置（欢迎语或菜单）。

#### 确定性护栏

- **原则**：钱、订单和每次都必须发生的动作交给代码，LLM 只负责理解和话术。防注入靠架构限制后果（最小权限、确定性校验输出），不指望检测率。
- **现有的几道**：
  - 价格出口核对：回复里的每个金额都要能追溯到本会话出现过的线路按规则算出的价、本会话的报价、订单金额或客户原话，追溯不到就整条替换。
  - 链接白名单与补救。
  - 订单幂等。
  - 客户明确要下单、模型却没调工具时，由引擎建单。
  - 转人工安全网。
  - 注入劫持拦截。
  - 工具参数按客户原话核对：模型编的预算、客群、年份不会进参数和画像。
- **边界要讲准**：价格护栏本质上是金额集合的白名单，不是把「这个价」绑定到「这条线路、这个人数」上；它只管金额，不管折扣率和免费升级。结构上真正的强项是订单金额只由报价工具算出。对外只描述为「出口二次校验」。
- **演进**：
  - 02 补齐确定性转人工的触发条件（紧急情况、交互失败达到阈值、负面情绪）。
  - 03 把同一思路推广到政策陈述。
  - 04 把 13 道出口护栏按现有顺序包成有序的 Guard 流水线，每次裁决（放行、删句、替换、修补、追加、转人工）记一行 `guard_events`；阈值和币种改成配置。

#### 前缀缓存

- 请求顺序固定：tools → 不变的 system → 历史（按 10 条一块推进）→ 会话状态（contextNote）→ 本轮客户消息。README 实测命中率 94.2%，条件是 glm-5.2、20 条回归用例，不是线上流量。
- tools 数组不按阶段裁剪。阶段限制放在工具执行层，返回一条告诉模型「下一步该怎么做」的错误。
- SOP 发布时渲染一次，先规范化（NFC、`\n` 换行、去掉行尾空白、不带 BOM）再存 hash；运行时逐字节读取存好的文本，从不重新渲染。hash 覆盖整段 system，也就是 SOP 加上代码里的硬性要求（含品牌名和 AI 标识），不能只算 SOP。
- 每轮会变的东西（日期、阶段、画像、最近线路）只放进 contextNote。
- 回滚 = 用旧内容重新发布，hash 不变，旧缓存还能命中。代码部署改了硬规则或工具定义时，自动生成一个「包升级」版本并记日志。
- 发给模型的工具结果字节要稳定：`jsonb` 会重排键序，见 ADR-001。
- 不用框架托管的记忆：逐条滑动的窗口，或把 working memory 放进 system，都会打掉前缀缓存。

#### 从单实例到多租户

- **现在**：单进程、单副本，同会话串行、在途消息落盘后重放、跟进扫描、SSE 全在进程内。按 1000 客户/天 × 20 轮估算，平均 0.23 QPS，瓶颈在模型 API。
- **00–03**：一个镜像、两个 profile，demo 和 prod 各用一个数据库；prod profile 对 demo 功能硬封顶，租户设置不能重新打开。企微的全局单例拆掉之前，一个租户一个容器一个库，公开路由用环境变量里的默认租户。从 01 建表起，租户内的表都带 `tenant_id`，并开 FORCE 行级安全（登录相关的表除外，见 ADR-001）；`conversations`、`orders` 从 02 建表起主键就是 `(tenant_id, id)`。
- **04（按信号启动，启动信号另记）**：同一部署服务多个租户。前提有四条：企微状态按账号拆开，公开路由能解析租户，进程内缓存键全部带租户，会话主键带租户（02 建表时已做）。
- **05（按信号）**：多副本。要加三样东西：`chat()` 返回后重读转人工和阶段（fence read）；每会话一把 advisory lock；企微拉取和任务执行用 advisory lock 选主。在那之前只跑单副本。

## 分阶段路线

各阶段的 spec 放 `docs/architecture/NN-<goal>/`，序号与此处一致；spec 顶部的 `Phase` 行指向本节。每个阶段都要保持三件事：demo 照常运行，自测与回归全绿，系统前缀逐字节不变（有意改变的除外，逐条记进 plan）。

### 阶段 0：冻结基线（docs/architecture/00-baseline/）

- 只放之后改不起的东西：
  - 部署级开关 `DEPLOY_PROFILE=demo|prod`：demo 的默认值等于现在的行为；prod 对 demo 功能硬封顶。覆盖范围：「重置」口令、免密只读后台、种子保鲜、访客模拟器（含访客预算与清理）、模拟支付、AI 显式标识。
  - 从 git tag 部署（`git archive`），保留回滚到上一个镜像；类型检查在归档出来的目录或镜像构建里跑，不查本地工作区。
  - 系统前缀逐字节稳定的检查就位（形式见开放问题），之后每个阶段都拿它做验收。
  - 公开边界落地（ADR-003）：路径黑名单（含 `src/packs/` 白名单）、内容黑名单与密钥扫描。推上去的东西自己洗不掉，所以最先做。
  - 四个门禁接上真实工具；全仓首次格式化单独提交。
  - 横评原始数据迁出临时目录，放进仓库外的持久存储（不进 git）。
  - 定下公开路由白名单。之后每个阶段的鉴权验收都分开断言：白名单里的路由可以匿名访问，其余都属于管理面。
    - 始终公开：付款 / 订单确认页 `/pay/:orderId` 与单订单读取 `/api/orders/:id`、方案书 `/proposal/*` 与 `/api/proposal/*`、客服二维码 `/kf-qr.png`、企微回调 `/wecom/callback`（验签）、`/healthz`。
    - 只在 demo 公开：网页模拟器（`/chat.html`、`/guide.html`、`/api/chat`、`/api/stream/:sessionId`）和模拟支付 `POST /api/orders/:id/pay`，prod 下由对应开关关掉。
- 本阶段修的缺陷：
  - 转人工后客户发图片、语音等非文字消息，AI 仍会自动回复。要先查是否已转人工，并把这条消息记进会话（现在完全不记，后台看不到客户发过图）。
  - 未知渠道默认走模拟器，会出现「显示已回复、实际没发出」。修的时候也不能在标记已付之后抛错返回 500：改成返回一个「推送失败」的空适配器，并告警。
  - 转人工正则认不出「人工」「找人工」「真人」这几种最常见的说法。
  - 回访欢迎语里「之前聊的内容我都记得」是不实承诺（每轮只带最近 30–39 条历史），改掉。
  - prod 下禁用「重置」，因为它会连已支付订单一起删。
  - 企微渠道加 AI 显式标识（账号名 + 欢迎语首句），demo 也开。
  - README 把「以销售个人身份托管 1v1 私聊」写成了生产路径，和上文「渠道 → 不做」冲突，改成「1v1 只做会话存档 + AI 辅助、由人点发送」。
- 验收：
  - demo 下行为不变：「重置」在网页和企微都生效，匿名只读和种子保鲜照旧。
  - prod 下：「重置」无效；管理面接口（会话与订单列表、会话详情、用量、洞察、接管 / 交还 / 代发）匿名请求返回 401；网页模拟器的路由返回 404；「始终公开」的路由照常可以匿名访问；带 AI 标识。后台 SSE 只推「有变化」的信号、不带数据，它的鉴权在 01 随 cookie 会话一起做。模拟支付怎么处理见开放问题。
  - 四个门禁在本地和 CI 全绿；改动的断言只限本阶段有意改变的行为。
  - 提交黑名单路径（含白名单以外的 `src/packs/<name>/`）或一段假密钥时，门禁失败。

### 阶段 1：PG 底座 + 配置入库 + 后台 v0（docs/architecture/01-pg-config-console/）

- Postgres 与 Drizzle 就位（ADR-001）：
  - 三个角色、`withTenant`、本阶段 7 张表（`usage_daily` 移到 02，见 [01 spec](./01-pg-config-console/spec.md) 裁决 R14）；`tenants` 表带 `locale/region`（海外适配保留的三条缝之一，建表时不带，以后就是一次改表）。
  - 迁移 lint：没有显式标注的 `DROP` / `RENAME` 直接拒绝。
  - 每晚备份，加一次恢复演练；CI 上的 RLS 套件跑在真实 Postgres 上。
  - 部署换成 compose 编排（Postgres、迁移任务、应用、备份）。`deploy.sh` 在 00 改成按 tag 部署，这里再改一次。
- SOP 和产品库入库：导入脚本幂等，SOP 按节逐字节保留；运行时改读数据库里已发布的渲染文本和产品库快照，同步签名不变。
- 评测 runner 和导入脚本支持 `--cases <path>` 这类仓库外路径（ADR-003）。
- 个人账号与后台 v0 五页（ADR-002）：登录、SOP、产品库、会话只读列表、审计日志。登录限流；会话 cookie 用 `__Host-`；写请求再要求一个 CSRF 头；prod 下 `/api/console/*`（登录接口除外）和 `/api/admin/*`（含后台 SSE）匿名请求返回 401，公开路由白名单不变。
- 四个门禁扩到 `console/`，脚本名不变（ADR-002 决策 3）。
- 发布闸 v0：静态检查加 SOP 契约检查。
- 开工前，spec 必须补齐以下 8 处空缺：
  1. **文件模式与数据库模式**：自测和回归直接读 `data/` 下的文件。要规定没设 `DATABASE_URL` 时走现在的文件模式，否则「启动时读不到快照就失败」会让它们全部挂掉。
  2. **发布闸 v0 对 SOP 没有检验作用**：mock 根本不读 system prompt。改成 SOP 契约检查：把自测里断言的短语抽成共享清单，发布时逐条校验；SOP 里引用的工具名和字段名必须真实存在。
  3. **只锁四节不够**：除了「报价纪律」、价格规则那一节、「能力边界」「转人工条件」这四节，「各阶段目标」「订单」「我们没有的目的地」也被代码依赖。第一个 `## ` 之前的前言要单独成一节，否则逐字节往返不相等。
  4. **产品库编辑会直接改变报价和护栏行为**，而报价快照要到 02 才有：要么把价格相关字段设为只读，要么把报价快照提前；zod 要校验 `bestSeason` 能解析出月份。
  5. **共享快照会被原地修改，语义索引也不会重建**：无过滤条件时查酒店会对快照原地排序，所以快照要 deep-freeze；检索要加 `invalidateIndex()` 和按条增量向量化，否则新增的线路永远召回不到。
  6. **RLS 与租户解析**：登录相关的表不能套租户模板；公开路由要能解析租户；`usage_daily` 建了表，却没有迁移用量统计的任务。
  7. **构建链**：要有多阶段 Dockerfile、`/console/*` 的 SPA 回退、Hono RPC 用的链式子应用；共享 zod 不能引入 drizzle 或 pg。
  8. **回滚语义**：数据库里改过 SOP 或产品库之后，回滚到上一个（文件版）镜像会静默退回 git 里的 SOP，运营的修改就没了。处理方式要预先定。
- 验收：
  - 自测和回归零断言修改，全绿。
  - 导入后发布出的系统前缀与文件版逐字节相同；每条线路的快照和原 JSON 深度相等。
  - 编辑并发布后，下一轮记录新的 SOP 版本；回滚后 hash 复原。
  - 没设租户时返回 0 行；租户 A 读写不到 B。
  - 迁移里放一条没有标注的 `DROP COLUMN`，迁移 lint 拒绝。
  - 故意改坏一个 console 接口的类型，`pnpm typecheck` 失败。
  - 恢复演练成功。
  - 前缀（按 [01 spec](./01-pg-config-console/spec.md) 验收 21）：DB 模式的 mock 回归里，每个请求实际发出的 system 与 tools 的哈希，都等于 `/healthz` 报的值（自动，进 `test`）；真实模型按「文件 → DB → 文件」交替各跑至少 3 遍，两种模式的 p90 都不超过 8 秒，缓存命中率只记录、不设门槛（手动，不进 CI）。

### 阶段 2：会话入库 + 坐席工作台（docs/architecture/02-conversations-workbench/）

- **会话、消息、订单入库**：
  - 用 identity map 让 `getSession` 保持同步，保住「生成中顾问接管」和「生成中客户付款」两个并发行为。
  - `conversations`、`orders` 的主键从建表起就是 `(tenant_id, id)`，旧 id 字符串不变，引用它们的外键带上 `tenant_id`（ADR-001 决策 5）。
- **数据**：
  - 消息只追加，带作者类型（AI / 人工 / 跟进 / 系统）。
  - 报价快照：方案书按快照渲染，调价后已发出的链接不变价。
  - 逐轮 trace：`turn_traces` + `guard_events`，挂在现有的工具回调和模型用量回调上。
  - `jobs` 表替代跟进的定时扫描，保持「最多发一次」。
  - 每个租户的 LLM 用量计量。
- **后台与交接**：
  - 后台 P0 对齐 admin.html：工作台、转人工队列、订单、按租户鉴权的 SSE。
  - 转人工即时推送和交接卡：触发原因与客户原话、需求要素、最近一次报价、订单状态。响应时限要结合微信客服的 48 小时 / 5 条窗口提醒。
  - kf 发送额度账本。
  - 价格确认闸：prod 关掉站内支付，顾问锁价后发客户自己的收款方式。
  - 压测：用模拟 LLM（2–8 秒延迟）测 SSE 并发、429 风暴和请求闸排队。
- **接真实租户之前必须有的**：
  - 确定性转人工补上三类触发。现在只有「要人工、退款、投诉」是确定性的，SOP 里「连续两轮无法理解」只是提示词。
    - 紧急情况：行程中高反、受伤、证件丢失、被困，回固定的应急话术并立即转人工。
    - 交互失败达到阈值：计数信号用兜底话术、客户重复提问、检索无结果。价格或注入护栏的命中是模型的问题，不计入。
    - 投诉词之外的负面情绪。识别方式由 02 spec 定。
  - 欢迎语附隐私说明链接。
  - 会话保留期清理任务：真实会话和逐轮 trace 按保留期删除，消息经清除函数删；日志里的客户原话也要有保留期。保留多久由 02 spec 定。
  - 敏感信息（长辈病史、带娃）单独同意，并记录同意；个人信息保护影响评估在接第一个真实租户之前完成。
  - 和模型厂商的委托处理约定属于合同，另记。
- **推迟到本阶段的已知缺陷**：
  - 人工回复即视为接管，`/reply` 在服务端校验会话状态。现在只靠前端拦，未接管的会话也能直接发人工消息，AI 下一轮还会把它当成自己说过的。交还之后，AI 要能分清哪些话是人工说的。
  - 「曾经转过人工」要持久化（`handoffAt` 一类的字段，交还时不清），订单付款时一并记录。现在交还会清掉转人工标记，转人工率和转人工贡献的成交占比都被系统性低估。
  - 跟进消息要过出口护栏（价格、内部用语、空头承诺清理），并识别「不用了 / 已经订别家了 / 别发了」这类拒绝。现在只看最后一条是不是我们发的。
  - 报价快照、逐轮 trace（见上）。
- **本阶段 spec 必须处理的点**：
  - identity map 是全量预载还是懒加载。建议启动时全量预载，把 store 在 import 时执行的副作用移进 `await store.init()`。
  - 三个同步落盘点（进程退出、跟进记账、企微状态）搬不到 PG。
  - 同一会话的写入可能乱序，要每会话一条写队列。
  - 不开跨越 LLM 调用的长事务。
  - 五处非追加写要改：重置、裁剪、改写转人工备注、重放对齐删句、种子平移时间戳。
  - 消息排序用自增 seq，不按时间戳。
  - 种子会话和网页访客会话只放内存。
  - 启动时用 `pg_try_advisory_lock` 拒绝第二个进程。
  - 后台 SSE 加鉴权并按租户过滤，事务提交后才发变更通知。
  - 数据迁入：按数组下标写 seq，保留全部可选字段，订单不对产品库建外键；另准备 PG → JSON 的导出脚本，供回滚用。
- 验收：
  - 自测与回归零断言修改，全绿；导入往返校验通过（每个会话从库里重建出的对象和原 JSON 深度相等）。
  - prod 鉴权套件通过：管理面接口（`/api/console/*` 除登录外、`/api/admin/*`、会话与订单列表、按租户鉴权的 SSE）匿名请求一律 401；白名单里的每条公开路由单独断言：能匿名访问，只返回凭 id 能取到的那一条数据。
  - 紧急情况、交互失败阈值、负面情绪三类触发各有用例，命中后确定性转人工。
  - 过了保留期的测试会话和它的 trace 被清理。
  - 本阶段结束时，具备以独立实例接入第一个真实租户的条件：「接真实租户之前必须有的」全部完成，开放问题里标了「接第一个真实租户之前」的都已定。

### 阶段 3：政策单一来源 + 知识库 + 售后退改（docs/architecture/03-knowledge-aftersales/）

- **policy 单一来源**：价格规则、AI 标识、品牌这些现在同时写在 SOP 文字和代码里的规则，改由一份结构化 policy 生成，SOP 对应的节只读。
- **SOP 版本全流程**：渲染一次并存 hash、lint、发布闸、发布、回滚。发布闸加真实模型回归：只有标了 regression 的用例能拦发布，失败的用例最多重跑 2 次，结果和当前发布版本上一次的结果比较。
- **知识库**：pgvector（`halfvec`）检索替换进程内的向量缓存文件，回答带条款引用。
- **定制游售后退改**：
  - 条款按距出发天数分档。
  - 查订单要核验订单号和手机尾号。
  - 退款额由代码按条款算。
  - 申请退款做幂等，超过阈值进人工审批。
  - 订单状态加「退款中」「已退款」。
- **推迟到本阶段的已知缺陷**：
  - 政策陈述护栏：回复里的比例、天数、条款和数据对不上就拦；退改、签证、保险、费用含不含查不到出处时，回固定话术并转顾问。
  - 看板拆成 AI 独立成交、人机协同成交、转人工率（按原因）三项，不再用「1 − 接管率」冒充「AI 独立完成」；种子、访客、真实客户分开统计。
  - trace 查看器与「存为回归用例」。
- 验收：
  - 导入未改动的 SOP，发布出的 hash 与文件版相同。
  - 故意改坏的 SOP（比如删掉价格规则节）被发布闸拦下。
  - 回滚后 hash 复原；稳态缓存命中不退化。
  - 能完整演示一次退改。

### 阶段 4：行业包抽取 + 渠道层 v2 + 同部署多租户（docs/architecture/04-packs-channels-tenancy/）

- 按信号启动，启动信号另记。在那之前一个租户一个实例。
- **先导出、再抽取**：先把引擎自测里约 155 个黑盒场景导出成 cases v2 数据，在旧引擎上跑绿，再按顺序抽取：
  1. 中文通用解析（金额、日期、人数）。
  2. 工具注册表与副作用标记。
  3. 护栏流水线：13 道出口护栏按现有顺序包装，「必须在谁之后」写成约束。
  4. 旅游逻辑搬进 `src/packs/travel/`。
  5. 阶段和画像改成包配置。
  6. 写死的阈值改成配置。
- **渠道层 v2**：
  - 每账号加密存凭据，独立的拉取和回调路由。
  - `channel_inbox` 按（账号，msgid）去重；出站消息记投递状态。
  - 链接由引擎显式产出，不再用正则抠。
  - 渠道中立的提示词只用于新租户，demo 租户的提示词逐字节不动。
  - 网页渠道转正（新的渠道名和 id 前缀）。
- **同一部署多租户**：
  - 企微全局单例（access_token、cursor、在途表、同步互斥等）按账号拆开。
  - 公开路由按域名或 `SECURITY DEFINER` 函数解析租户，不再用环境变量里的默认租户。
  - 从模板开通租户；每个租户有自己的 LLM 预算和成本统计。
  - 跨租户泄漏测试覆盖进程内缓存。
- **推迟到本阶段的已知缺陷**：模拟客户评测和 pass^k（暂定，见开放问题）。
  - 模拟客户：LLM 扮演带隐藏目标的客户，按业务终态做确定性判分：选对线路、人数、日期；客户没确认时不建单；该转人工时转了；没有编造的非金额承诺。
  - pass^k：真实模型下，对核心流程和护栏用例跑 k=5。
- 第一段私有代码出现时，按 ADR-003 切到外层 workspace + submodule。
- 如果第二个行业要先落地，本阶段的行业包抽取可以提到 03 之前。
- 验收：
  - `src/core/` 不引用 `src/packs/`（import lint）；主流程约 150 行。
  - 第二个同行业租户只靠配置和数据上线。
  - RLS 与内存缓存的隔离测试通过；两个租户交错对话时各自命中自己的前缀。
  - 回归与自测全绿。

## 开放问题

- **前缀稳定检查的形式**（已由 [00 spec](./00-baseline/spec.md)「前缀稳定测试」定：方案 B，不设静态 golden 常量；01 起比对「同一进程里文件渲染 == DB 渲染」，见 [01 spec](./01-pg-config-console/spec.md) 裁决 R4）：方案 A：提交一份静态的 golden hash。方案 B：运行时断言多轮之间逐字节不变并打印 hash，01 起再比对「文件渲染 == 入库渲染」，加 CRLF / NFC / 末尾换行的往返断言。SOP 改得很勤，静态常量会不停失效。
- **prod 下的模拟支付**（已由 [00 spec](./00-baseline/spec.md)「mock_pay 与 prod 的真实客户」定：prod 下匿名请求不能把订单标成已付，`/pay` 页和成交链路原样保留；02 交付收款流程之前，prod 实例只用于验收和预演、不接真实客户；「顾问锁价后发收款方式」留在 02）：整条成交链路都假设有 `/pay` 页，包括 SOP、支付链接、成单兜底和企微支付卡片，直接关掉的话客户点开链接就是报错页。选项：prod 暂时保留支付页并标为测试；链接照发，prod 下页面改成订单确认页、匿名不能付款，完整收款流程留到 02；或把「顾问锁价后发收款方式」提前到 00，这会改工具和 SOP，prod 前缀也会变。
- **冻结阶段的小修范围**：可以在冻结阶段顺手做的小修共七项：转人工正则认「人工」「找人工」，欢迎语写明人工入口；回访欢迎语去掉「之前聊的内容我都记得」；「重置」只对白名单生效、不删已支付订单；跟进过护栏并识别退订；交还时不清转人工标记；`/reply` 在服务端校验会话已接管；转人工时用群机器人发简版通知。本文暂把前两项放在 00，其余放在 02（交还标记和 `/reply` 见 02「推迟到本阶段的已知缺陷」，通知见下面「SSE 之外的转人工推送通道」）。00 spec 可以把其中几项提前；最迟在 02 结束、接第一个真实租户之前全部完成。
- **demo 下「重置」的底线**：方案 A：demo 保持现在的硬删除，引擎自测 E6 依赖这个行为。方案 B：任何环境下「重置」都先查是否已转人工，且不删已支付订单，同时保留「网页与企微都生效」的决定。00 spec 定，最迟在 02 随会话入库一起定。
- **自测默认跑哪种存储**（已由 [01 spec](./01-pg-config-console/spec.md) 裁决 R16 定：现有 6 组自测和 eval 默认跑文件模式，`test` 对它们显式设 `CONFIG_SOURCE=file`；DB 路径由新增的三组自测加一遍 DB 模式的 mock eval 覆盖；RLS 套件跑在真实 Postgres 上。02 的会话存储沿用同一原则，由 02 定）：方案 A：现有自测直接切到 PGlite。方案 B：store 抽成接口，现有 6 组自测默认跑内存实现，另加一组在两种实现上各跑一遍的一致性自测（PgStore 用 PGlite）。两种方案下 RLS 套件都跑在真实 Postgres 上（ADR-001 决策 3）。
- **LISTEN/NOTIFY**（已由 [01 spec](./01-pg-config-console/spec.md) 定：单副本期间不用，事务提交后由本进程直接更新缓存，见裁决 R5；多副本与 LISTEN/NOTIFY 放到 05 按信号定）：一种方案用它做 SOP 和产品库的缓存失效以及 SSE 扇出；反对的理由是单副本下用不着，而且 LISTEN 需要独立连接，断线后会一直读旧 SOP。
- **01 工期偏紧时先砍什么**（已由 [01 spec](./01-pg-config-console/spec.md) 裁决 R17 定：两级砍法和可观察的触发点见 [01 plan](./01-pg-config-console/plan.md)「工作量与砍法」；Hono RPC 不砍）：候选是 CSV 导入、diff、ECharts、多租户 RLS 场景测试（01 是一个容器一个租户）。Hono RPC 只能推迟：ADR-002 的决定不变，02 开工前补上；要取消就另写一份 ADR 取代 ADR-002 决策 2。
- **`channel_inbox` 是否从 04 提前到 02**：会话进了 PG、cursor 还在文件里时，两边的备份不在同一时刻，恢复后会重复回复或丢在途消息。02 spec 定。
- **SSE 之外的转人工推送通道**：SSE 只在后台页面开着时有用。真要推到顾问手上，得用企微应用消息（agentid + 顾问 userid）或群机器人，现在的配置里都没有。02 spec 定。
- **模拟客户评测与 pass^k 放哪个阶段**：它们和 cases v2 导出归在一组，尚未排期。放 04，还是提前到 03 支撑真实模型发布闸，03 开工前定。
- **非金额承诺的拦截**：折扣率、免费升级、赠送、「保证 / 包退」这类说法，价格护栏只核对金额，拦不住；尚未排期。建议 03 做政策陈述护栏时一起评估。
- **地方网信办登记是否适用于 1v1 客服**：以属地的书面答复为准。产品侧先预留公示位，接第一个真实租户之前定。
- **待核实**：
  - Drizzle 当前的稳定大版本（01 开工前核实，钉死精确版本）。
  - Ant Design 当前的稳定大版本。
  - Prisma 是否已经原生支持 pgvector。
  - PGlite 默认的超级用户连接是否绕过 RLS（按 Postgres 通则推断会绕过；RLS 套件因此不放在 PGlite 上）。
  - 托管 Postgres 能否授予 BYPASSRLS。
  - 海外托管的开源权重模型能否过 8 秒线、能否吃到前缀缓存。
  - 以上核实时点：用到的那个阶段开工前。
