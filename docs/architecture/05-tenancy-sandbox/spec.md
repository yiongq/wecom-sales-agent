## 背景与问题

04 之后同一套引擎只改配置就能换品牌、换行业，但一个进程仍只服务一个租户。目前没有具体客户，第一批真实客户仍「一家一个实例」，本阶段的价值主要是让访客亲手体验工作台（一键体验沙箱），以及以后的托管。开工前的只读盘点（按 `e5affab`，协调者另存，不进仓库）查到：

- **一个进程一个租户写在很多地方。** 启动按 `DEFAULT_TENANT_SLUG` 解析租户、取锁、装一份配置（`src/config/source.ts:332`、`:620`）；会话存储与渠道从同一个 `configRuntime()` 取 `tenantId`（`src/server.ts:1038`、`:1044`）；登录与 cookie 固定查它（`src/auth/session.ts:137`、`:206`）；产品库写入与运行数字明确拒绝别的租户（`src/config/catalog.ts:109`、`src/ops/metrics.ts:55`）。
- **公开路由没有租户维度。** 订单、支付页、方案书、隐私说明、模拟器直接查全局 identity map 与当前绑定（`src/server.ts:613`、`:696`、`:757`、`:919`、`:410`）；网页入口与企微回调按 key 在当前租户的账号里找（`src/channels/accounts.ts:221`）。库里不同租户可以有相同的会话 id、订单 id 与账号 key。
- **进程内状态多是按裸 id 的模块级单例。** 行业包绑定一个模块变量（`src/core/pack-api.ts:600`），配置一个 `loaded`（`src/config/source.ts:209`），会话与订单各一个全局 Map（`src/store.ts:113`），接管代次、发送账本、洞察缓存、console 事件环、SSE 订阅只按会话 id 建键。`src/` 里模块顶层的集合 91 个、模块级 `let` 115 个，另有模块级数组、当字典用的对象、事件发射器与加载时调一次的工厂闭包；评测的清理清单（`eval/v2/isolation.ts:11`）只登记了一部分。RLS 管不到它们（ADR-001 决策 4）。还有几处会悄悄继承作用域：`AsyncLocalStorage.snapshot()` 恢复的是模块加载时的上下文（`src/store/pg-backend.ts:64`、`src/store.ts:297`），模块级的去抖定时器会继承第一个触发者的上下文（`src/store.ts:146`）。
- **用量有租户、预算没有。** `usage_daily` 主键带租户（`src/db/schema.ts:466`），内存累加器却只按（日、模型、用途）建键，由绑在当前 PG 后端上的一个 writer 每 30 秒写一次（`src/trace/usage-daily.ts:41`、`:118`）。用量只按成功采用的响应记，重试与对冲的输家不记（`src/llm-gate.ts:95`、`src/core/llm/client.ts:317`）。访客预算是一个 `budget.json`，只在模拟器渠道的主对话占一个轮次名额（`src/budget.ts:9`、`src/core/engine/index.ts:610`）。
- **没有开通与删除整个租户的路径。** 开通是几条平台命令的组合，身份各不相同（`src/cli/tenant-create.ts:18`、`src/cli/import-config.ts:11`）；`erase-conversation` 只删一个会话、留下订单与审计；租户外键没有级联，`agent_app` 对 `tenants` 只有 SELECT（`drizzle/0001_rls_auth.sql:284`）；登录会话的创建函数固定写 7 天期限（`:190`）。
- **demo 的「免密」只是只读**（`src/console-api/app.ts:251`）。直接开一个可写的公开账号，人工回复会经企微真发给扫码的客户，访客之间互相看到聊天、改坏 SOP 与价格（owner 2026-10-10 否决）。
- **很多分支按「企微渠道」判断。** 发送按会话的 `channel` 选适配器（`src/server.ts:103`），人工回复的窗口与额度、工作台的送达状态与发送窗口只对 `wecom` 会话算（`src/handoff/takeover.ts:354`、`src/console-api/workbench.ts:251`）；转人工与订单通知任务、未保存转人工的群通知走另外的路（`src/handoff/record.ts:109`、`src/notify/handoff.ts:154`）；企微适配器内部还有自动回复、兜底、欢迎语、恢复的发送（`src/adapters/wecom.ts:1407`、`:1788`）。

本文的词：**宿主租户**是 `DEFAULT_TENANT_SLUG` 指的那个（线上 demo 就是它）；**standard 租户**是普通租户（含宿主）；**沙箱**是 `kind='sandbox'` 的临时租户；**宿主进程**是现在的 `app` 服务，**沙箱进程**是新的 `sandbox` 服务；**沙箱 Host** 是沙箱进程服务的主机名；**体验客服**是专为沙箱新开的企微客服账号（与线上 demo 的 `kf-main` 分开）；**绑定**是一个微信（external_userid）与一个沙箱的对应。

## 目标

1. **同部署多租户。** 一个进程能安全地服务多个租户：线上是沙箱进程里同时活着的多个沙箱；测试里同一进程装两个 standard 租户交错对话。配置、品牌、绑定、产品库、索引、会话与订单、缓存、事件与订阅互不可见。宿主进程线上仍只有宿主一个运行时。
2. **公开路由按租户解析。** 一个进程装了多个 standard 租户时按 Host 解析，缺 `public_host` 拒绝启动、未知 Host 404；只装了一个 standard 租户时任何 Host 都是它（「单 standard 实例的兼容」，即今天「一家一个实例」的部署形态）；沙箱只在沙箱 Host 上、按会话 cookie 解析。
3. **沙箱从模板开通、整租户删除。** 开通一个事务；删除能证明删干净（库里 0 行、进程里 0 个键）。standard 租户的模板开通与整租户删除不在本阶段。
4. **模型用量与花费按租户记账**：沙箱与全池在每次请求之前预占硬额度；standard 租户只有软上限告警。
5. **一键体验沙箱。** 登录页点「免登录体验」→ 从模板开通临时租户（配置、种子会话、订单、产品库都是副本）→ 免密进工作台随便操作（接管、回复、改价、标已付、改 SOP）→ 用微信扫工作台里的二维码，自己的微信就是客户：AI 回复、接管后的人工回复、付款确认都经体验客服真的发到这个微信，也只发给它；不方便扫码时用连着同一份副本的网页模拟器 → 24 小时后（或闲置、主动结束时）整个租户连同绑定删掉。
6. **跨租户泄漏测试覆盖进程内状态**；两个租户交错对话时各自命中自己的前缀；运行时个数从 0 到多再回到 0 的全过程不串台。
7. **宿主不受影响。** 宿主进程的四个哈希、demo 行为、作战室口径、`/healthz` 照旧（入口的改动只有 R23）；`docker compose stop sandbox` 不碰宿主。
8. **主站入口就是产品。** `/` 在两种 profile 下都进 console，未登录看到登录页；引导页删除；免登录体验只在 demo 的登录页上。

`data/sandbox-seeds.json` 是沙箱种子的唯一来源，开通只读它。它的结构由 TypeScript 自测 `src/tenancy/seed-fixture.selftest.ts`（进 `pnpm test`）核对：13 个会话、3 个订单，id 与订单的会话引用对得上，线路 id 都在 `data/routes.json` 里，时间都是相对值。它与 `scripts/seed-demo.py` 是否一致，由 CI 里四个门禁之外的单独一步核对：`python3 scripts/seed-demo.py --fixture` 重新生成，不同就失败。四个门禁也在应用镜像里跑，镜像里不一定有 python3，所以这一步不放进门禁。

- **沙箱 console**：同一个前端。顶栏横幅「体验环境 · 剩余 X 小时 · 回复只发到你自己的微信」（没配体验客服时是「只进模拟器」），带「打开模拟器」「结束体验」；会话详情加「在模拟器里打开」（只对 `sbx-` 会话）；绑定微信的会话照企微显示窗口、剩余条数与送达状态；不显示登录页，`/me` 回 401 `sandbox_required` 时跳 `/try`；写入被限时提示 `sandbox_write_limited`。右侧「体验清单」：① 扫码，用微信给 AI 发一句（附二维码与 `XXXX-XXXX`，窄屏换成「在微信里打开」；码过期自动换新；已绑定显示「已连上你的微信」与「换一个微信」；取码失败可重试；出码 3 分钟仍没绑上时提示「扫码没反应？先用模拟器体验」；没配体验客服时这一步是「打开模拟器发一句」，名额用完时同样换成模拟器并说一句「微信体验名额已满」）② 看 AI 怎么回、怎么报价 ③ 点接管，自己回一句，微信里马上收到 ④ 改价、标已付、改 SOP。每步是否完成由服务端按沙箱自己的数据算；可收起，收起状态按沙箱记在浏览器里。`Me` 加 `sandbox: { expiresAt: string; wechat: 'off' | 'full' | 'unbound' | 'bound'; steps: [boolean, boolean, boolean, boolean] } | null`。
- **沙箱模拟器**：同一份 `chat.html`，顶部同样一条提示，认 `?c=<id>`；刷新之后照旧经 `GET /api/sessions/:id` 恢复历史。锁定的 `server.selftest.ts` 对 `chat.html` 源码的检查（`LS_KEY`、单独执行的 `newSessionId()` 仍产出 `sim-`、`fillPayCard`、开场句）照旧通过。

## 不变量

1. 严格模式下（沙箱进程、多 standard 的宿主进程、`TENANCY_STRICT=1`），在租户作用域外读写任何登记的租户状态都抛 `TenantScopeMissing`，不回落；HTTP 回 500，后台入口记日志并推 `tenant_scope_missing`，进程不退出。
2. 两个租户用同一个会话 id、订单 id、账号 key 时，各自的 `getSession`、`getOrder`、接管代次、账本、SSE 订阅、console 事件互不可见。
3. 对话轮次发出的每个模型请求，system 与 tools 字节等于这一轮所属租户本轮捕获的发布版本；两个租户交错对话时各自的 `promptHash`、品牌、产品库、identity map 互不可见。
4. 一个公开请求只从 R4 解析出的那一个租户取数据；装了多个 standard 租户的进程里未知 Host 是 404；沙箱进程只答沙箱 Host（`/healthz` 除外）。
5. 沙箱进程的环境里没有 `WECOM_*`、渠道密钥环、`NOTIFY_WEBHOOK_URL`、OTLP 端点、对冲模型、`DEFAULT_TENANT_SLUG`，企微凭据至多只有体验客服一个账号的；它发往企微的每个请求的 `open_kfid` 都是体验客服的，每条 `send_msg` 的 `touser` 都等于发送那一刻所在沙箱在进程里发布的绑定，每次 `send_msg_on_event` 的 welcome_code 都来自这个微信、这个沙箱的进入会话事件，唯一例外是未绑定的固定话术；库里沙箱的 `channel_accounts` 与 `jobs` 行数恒为 0。
6. 沙箱里的会话只有两种：`sbx-` 开头且 `channel` 为 `simulator`；`wecom:<external_userid>` 且 `channel` 为 `wecom`，这个 external_userid 绑定过这个沙箱。沙箱进程不在 `var/` 写任何文件。
7. 到期删除成功之后：以不经 RLS 的身份数，每张带 `tenant_id` 的表（含 `sandbox_wechat`）里该 id 的行数为 0，`tenants`、`users`、`auth_sessions` 里没有它，进程内的解析不再指向它（它绑过、之后改绑到别处的微信照旧解析到那里，其余解析为空）；`tenantKeys(id)` 每项为 0，注册表里没有它。
8. 运行时进入 `closing` 之后，没有任何迟到的结果改它的状态（含绑定的发布与失败恢复）。删除的顺序固定：先确认它在途的每个数据库操作都已落定（提交、回滚或断开），再把用量写进库，再关后端，最后 purge；前一步没确认，后一步不做。
9. `sandbox_tenant_purge` 的删除清单覆盖系统目录里每一张带 `tenant_id` 的表。
10. 四个沙箱函数对 standard 租户一律报错，时刻只取库内 `now()`；purge 只删已到期的；`agent_app` 没有别的途径建、删租户。
11. `__Host-sbx` 只在沙箱进程被读；沙箱进程不读 `__Host-sid`、没有口令登录；一个沙箱的会话只能操作它自己；只带 `__Host-sbxw` 的请求只能用那个沙箱的支付页、方案书、隐私说明及其接口；沙箱的所有非安全方法拒绝 `Sec-Fetch-Site` 为 `same-site` 与 `cross-site` 的请求。
12. 每次请求尝试发出之前，本沙箱与全池的次数与金额都已预占；一个沙箱一生、全部沙箱一天的花费与尝试次数不超过各自上限。唯一例外是沙箱进程崩溃：每次崩溃至多少记两部分——最近 60 秒内结算、还没落库的尝试，以及在飞的至多 `LLM_MAX_INFLIGHT` 次。还没落库的最早一笔用量超过 60 秒时，没有沙箱能发出新的收费尝试；全池用完之后，没有沙箱再发出请求；池的当天数在重启时计入所有还没删掉的沙箱。开通的每小时与每 IP 计数同样只有崩溃重启这一个例外。
13. standard 租户的模型调用不因预算降级或被拒。
14. `src/**` 的模块级绑定（R5 列的例外之外）都在状态清单里，标成租户状态的都已登记。
15. 宿主进程的四个哈希、demo 行为（R23 改的入口除外）与开工时相同，`/healthz` 原有字段不变（只多 `role`）；停掉沙箱进程不改变宿主的任何行为。
16. `deploy.sh` 报部署成功时，宿主 `/healthz` 的 `revision` 等于本次 tag，目标是 05 及以后时 `role` 为 `host`（pre-05 的镜像没有这个字段，部署或回滚到它时不查）；沙箱启用时，沙箱的同样等于本次 tag、`role` 为 `sandbox`。05 之前的镜像不会以沙箱服务的身份起来服务：回到 pre-05 之前，沙箱容器已删、`.env.sandbox` 已不在；`.env.sandbox` 里从来没有 `DEFAULT_TENANT_SLUG`。
17. 沙箱会话的解析只有一套契约：已到期、还没删的回 410 `sandbox_expired`；无效、已删或没有 cookie 的回 401 `sandbox_required`。
18. 同一时刻一个微信至多绑一个未到期的沙箱，一个沙箱至多绑一个微信；绑定码只能用一次，过期的码绑不上（前提是不变量 22）。
19. 体验客服收到的消息只进发送者此刻所绑沙箱的作用域；没有绑定的人只收到固定话术，不调模型，任何租户的库里都没有他的消息。
20. 宿主的 `/` 在两种 profile 下都 302 到 `/console/`，`/guide.html` 是 404；登录页的「免登录体验」只在 demo 且配了 `SANDBOX_HOST` 时出现。
21. 链接令牌不出现在任何日志、审计与 `/healthz` 里；改绑一开始，旧绑定就发不出任何一段。
22. 同一时刻至多一个沙箱进程持有 `sandbox-process` 锁；丢了锁的进程察觉之后不再发起任何请求、不再发 COMMIT；码、绑定、链接令牌、cursor 与「名额已满」的写只有持当前 epoch 的进程能提交（此前发出的其他写可能迟到落定）；没拿到的沙箱进程不装载、不删、不改任何沙箱；拿不到某个沙箱的租户锁不会把它改成到期。

## 兼容与迁移

- 迁移只扩：新列可空或带默认，新表、新函数、新触发器旧镜像不碰。
- 升级没有手工步骤：宿主进程只装宿主，行为照旧；服务器上没有 `.env.sandbox` 时沙箱服务不起。线上 demo 开沙箱：配好沙箱 Host 的 DNS、证书与反向代理站点，写 `.env.sandbox`（不带 `DEFAULT_TENANT_SLUG`），部署（R20）。开体验客服：owner 按前置条件在企微后台建好，`.env.sandbox` 加五个 `SANDBOX_WECOM_*`，重新部署；不配就只有模拟器。
- 去掉引导页没有数据迁移：旧的 `/guide.html` 链接（含转发出去的）变成 404；外部拨测若拨 `/guide.html`，改拨 `/healthz`。
- 文件模式与锁定套件只有一个运行时，行为不变（入口按 R23 与开放问题 12）。回滚按 R18。

## 安全、隐私与性能

- 匿名访客能写的内容（SOP、产品文字、快捷回复、聊天）只在沙箱 Host 上渲染；沙箱 Host 与主站不同源，转义疏漏最多是访客在自己沙箱里自伤，碰不到成员的 cookie 与工作台。沙箱进程的页面另加 CSP：脚本只许同源与按 hash 或 nonce 放行的本页内联脚本（`chat.html`、`pay.html`、`proposal.html` 有内联脚本，不能直接照搬网页渠道那一套，`src/web/routes.ts:137`），不许任何外部来源。沙箱里的会话 id、订单 id 不再是凭据，一律要 cookie；写请求另过同源检查（R10）。不要 `__Host-sbx` 的只有体验客服回调（靠签名）与 `/wx/` 跳转（只开那个沙箱的支付页、方案书、隐私说明，R21）。
- 隐私：沙箱里有访客真实的 external_userid 与他在微信里发的消息。不拉昵称与头像；日志里的会话 id 照 03 R22 脱敏（`wecom:<id>` 本来就认，另加 `sbx-`），绑定、限频的日志只记短码；绑定与会话随租户整体删除，备份随保留期（本地 7 天、异地 30 天）滚掉；企微服务器上的聊天记录按企微的规则保存，不归本系统删。`/try` 与横幅写明这些，以及「回复只发到你自己的微信」、不要输入真实个人信息。沙箱进程没有 OTLP 端点。
- 滥用：二维码与链接会被转发。一次性码挡住同一个码被多人用；10 分钟过期挡住转发出去、晚些才扫的码；一个沙箱一个微信、后绑的赢，挡住多人共用一个沙箱的模型额度；未绑定的固定话术不调模型、不进库、限频，挡住拿到体验客服链接的人花模型钱、写库。微信里的对话照样计沙箱的模型额度（R15）。挡不住的是企业的接待名额（未验证时约 100 位）：用完之后自动退回模拟器并告警（R22）。
- 性能：沙箱进程多占一份 Node 常驻内存（开工实测）与一组数据库连接（池 max 5 加一条锁连接）；沙箱全量预载在内存，每个约一份配置快照加十来个会话，索引在沙箱之间共用。宿主进程不受沙箱的模型并发与内存影响，共享的只有数据库与模型供应商的速率限制；验收记录沙箱压测时宿主的排队延迟与库的写入积压。

## 验收标准

1. **进程内隔离（R17 的 A、B）。** 同一会话 id、订单 id、网页账号 key 在 A、B 各取到自己的对象；交错对话时，假模型记下的每个请求的 system、tools 哈希等于所属租户的值，A 的请求与回复里没有「山海」、B 的没有「云途」；只有 B 有的线路只出现在 B 的检索与报价里，改过价的线路在 A 照旧原价；A 的模拟器 SSE 与 console 事件流收不到 B 的推送，反之亦然；日志的租户字段各自正确。
2. **作用域与清单。** 严格模式下在作用域外调 `getSession`、`currentPack()`、`currentCatalog()` 都抛 `TenantScopeMissing`；后台入口缺作用域时进程不退出，日志有一行、`tenant_scope_missing` 推了一条；沙箱进程从 0 个运行时到 2 个再回到 0 个，全程没有串台、没有 `TenantScopeMissing`；`TENANCY_STRICT=1` 下 02–04 在 DB 模式下的非锁定自测全绿。往 `src/` 任一模块顶层加一个不进清单的数组或 `new Map()`，`pnpm lint` 失败，补上后通过。
3. **公开路由与 Host。** 测试里两个 standard 租户各设 `public_host`：「公开路由」表的宿主列每一行在自己的 Host 上取到自己的数据，换到另一个租户的 Host 是 404 或那个租户自己的数据；未知 Host 404；装两个而一个缺 `public_host` 时以 `tenant_host_missing` 拒绝启动；只装一个时任何 Host 都是它。沙箱进程对别的 Host 只答 `/healthz`。Host 带末尾点、带端口、IPv6 字面量都规范化正确。线上 demo：经真实反向代理，两个站点收到的 Host 原样，`clientKey()` 取到的是访客的真实地址。
4. **开通。** 从 `/try` 点开始到进工作台，20 次 p95 不超过 3 秒；沙箱里 13 个种子会话（都是 `sbx-`、`simulator`）、3 个订单、产品条目数等于宿主的 active 条目数，四个哈希与宿主已发布的相同；宿主已 `tenant-brand set`、还没重启时开通，沙箱的哈希仍等于宿主已发布的；宿主的库行数与哈希不变；带有效 cookie 再开通返回同一个沙箱。
5. **工作台全程。** 在沙箱里接手一个种子会话并回复，模拟器 1 秒内出现「【顾问】……」；交还后在模拟器发消息，AI 回复；刷新模拟器，聊天历史恢复；改一条线路的价格，模拟器里新报价用新价，宿主不变；标已付，模拟器收到付款确认；改 SOP 前言并发布，沙箱 `promptHash` 变、宿主不变；模拟器开的新会话实时出现在工作台；「重置」只影响沙箱的那个会话。
6. **只发给访客自己。** 沙箱进程的环境里设任意一个 `WECOM_*`、`CHANNEL_SECRETS_KEY`、`NOTIFY_WEBHOOK_URL`、`OTEL_EXPORTER_OTLP_ENDPOINT` 或 `LLM_HEDGE_MODEL`，以 `sandbox_env_forbidden` 拒绝启动；体验客服的变量缺一部分以 `sandbox_wecom_partial`、`SANDBOX_WECOM_OPEN_KFID` 等于某个 standard 租户的 `channel_accounts.open_kfid` 以 `sandbox_wecom_conflict` 拒绝启动；宿主进程的环境里有 `SANDBOX_WECOM_*` 拒绝启动。测试里把企微 API（记下每个请求的路径、`open_kfid`、`touser`）、两个 webhook、OTLP 都换成本机记录器，配上体验客服，跑完验收 5 与 16 再加：最早时间戳的种子会话（今天的企微窗口早已关闭）接手回复成功；模拟器没有 SSE 连接时回复成功、没有失败备注；一次会话落库失败；advisor 模式下顾问建单；一次转人工；一次进程级告警；再做几次故意违规：在沙箱 A 的作用域里发给 B 绑定的微信；`open_kfid` 换成别的值；在作用域外发固定话术以外的文字；用不在表里、或属于另一个沙箱的 welcome_code 调 `send_msg_on_event`；一条三段的回复发出第一段后改绑；假企微先回 42001、token 强刷期间改绑。结果：企微请求只有发往体验客服、`touser` 是发送那一刻那个沙箱所绑微信的那些，加上固定话术；违规的那些（改绑之前已发出的第一段除外）一条都没出去，各记一条 `sandbox_send_refused`；种子与模拟器会话没有产生任何企微请求；群通知 0，告警只有进程级那条与 `sandbox_send_refused`，OTLP 0；沙箱的 `jobs` 与 `channel_accounts` 行数为 0，没有会话被标 poisoned；给沙箱插 `channel_accounts` 被触发器拒。
7. **预算。** 同一沙箱多个会话加洞察并发、`SANDBOX_LLM_CALLS=5`：发出的请求尝试恰好 5 次，之后对话降级成 mock、`outcome = 'budget'`；假模型先回 500 再回 200，一次调用计 2 次；全池额度用完之后，已有的沙箱也停止调用（降级），开通回 503 并推一条 `sandbox_pool` 告警；让 `usage_daily` 的写入持续失败超过 60 秒，所有沙箱停止新的收费尝试（降级），写入恢复之后照常；重启之后已花数接着算，池的当天数计入一个已到期、purge 还没成功的沙箱的花费。standard 租户越过 `llm_daily_alert_milli` 只告警一次、对话不降级。作战室的「当日模型成本」不含沙箱花费。
8. **限额与写入上限。** 活着的沙箱到上限时下一个 429；每小时、每天、每 IP（含同一 /64 的两个 IPv6 地址）的上限各验一次；写入的每一项上限各验一次（`sandbox_write_limited`），模型降级之后写额度照计。20 个沙箱各连发 5 轮、并有一个沙箱按写上限连续写入时，宿主每轮的排队等待中位数比没有沙箱时多不超过 1 秒，宿主的写库积压不超过 2 秒；沙箱进程的 RSS 记进 plan。
9. **到期删除。** 把一个沙箱的 `expires_at` 拨到过去：1 分钟内接口回 410 `sandbox_expired`、页面跳 `/try?ended=1`；删掉之后，同一个 cookie 回 401 `sandbox_required`。以超级用户按系统目录逐表数它的行，全为 0，`tenants`、`users`、`auth_sessions` 里没有它；`tenantKeys(id)` 每项为 0；`sandbox_pool_daily` 当天的 `purged` 与花费加上了；它绑过的微信再发消息只收到固定话术。另验以下几种：一个模型请求超过 30 秒等待才返回，它的结果没有改任何状态（草稿缓存里没有它）；一个配置写事务被另一条连接的行锁挂住、超过 30 秒还没结束：reaper 停在 ②，没关后端、没 purge、锁没放；放开之后事务落定，下一分钟删干净；用量写入失败，停在 ③、后端没关，写入恢复之后先落库、再关后端、再删干净；purge 失败（锁超时），之后只重试 purge、删干净；绑定事务挂住期间沙箱到期、或点「结束体验」，① 当刻改 `closing`、新的签码与绑定被拒，reaper 停在 ② 直到那个事务落定，之后不发布新绑定、不恢复旧绑定，那个微信再发消息只收到固定话术；删除事务中途杀进程，重启时删干净。「结束体验」与闲置 `SANDBOX_IDLE_MINUTES` 之后同样删掉。过期超过 1 小时仍没删掉时推 `sandbox_purge`，沙箱进程 `/healthz` 的 `ok` 为 false。
10. **重启与角色。** 沙箱进程重启之后活着的沙箱还在（cookie、会话、改过的价格），到期的在启动时删掉、不装载；停机时没落库的写入丢弃、日志有条数、`var/` 下没有新文件。`docker compose stop sandbox` 之后宿主的 `/healthz`、四个哈希、企微一句一回不变，宿主没有重启。prod profile 下 `APP_ROLE=sandbox` 启动失败；缺 `SANDBOX_HOST` 或 `SANDBOX_TEMPLATE_SLUG` 启动失败；环境里有 `DEFAULT_TENANT_SLUG` 时以 `sandbox_env_forbidden` 启动失败。`sandbox list`、`sandbox end <slug>`、`sandbox purge --all`（沙箱进程在跑时以 3 退出）各验一次。沙箱进程在跑时对同一个库再起一个：第二个在 30 秒内以 `sandbox_already_running` 拒绝启动，没装载、没跑 reaper，活着的沙箱的 `expires_at` 一个都没变；先停第一个、再起第二个，第二个正常接手。运行中终止第一个的锁连接（`pg_terminate_backend`）：第一个当刻停止、以非零退出，察觉之后假企微没再收到它的请求，第二个取到锁、epoch 加一之后接手。另在察觉之前让第一个挂住一个绑定事务（测试钩子推迟它的 `onLost`），两种先后各验一次：旧事务先拿到 `FOR SHARE`，它提交、第二个的重建看得到；第二个先加了 epoch，旧事务核对失败回滚。两种情况下第二个的解析表都与库一致。
11. **会话与安全。** 沙箱进程上带 `__Host-sid`、宿主进程上带 `__Host-sbx`，都是 401；沙箱 A 的 cookie 访问沙箱 B 的会话 id 是 404；沙箱进程上口令登录 404；`sandbox_session_resolve` 对 standard 租户的 token、随机 token、已删沙箱的 token 返回 `invalid`（接口 401），对已到期、还没删的沙箱的 token 返回 `expired`（接口 410）；闲置 13 小时（未超过剩余寿命与闲置回收）之后 cookie 仍有效。从兄弟源（`Sec-Fetch-Site: same-site`）发的简单 POST 到聊天、模拟支付、结束体验、console 写接口都是 403。产品标题放 `<img src=x onerror=alert(1)>`：沙箱的支付页、方案书、模拟器、工作台都当文本显示，页面响应带 CSP。

## 开放问题

以下十五条 owner 2026-10-11 定：全部照推荐。其中 12 即 owner 授权按所列行号一次性修改锁定的 `server.selftest.ts`，别的锁定文件与断言不动。正文的 R 按推荐写。

1. **模板来源与复制范围。** A 配置取宿主当前**已发布**的（品牌、SOP、产品库同一份快照），种子取仓库里的固定种子文件；B 全取仓库静态数据（每次开通走一遍导入与渲染）；C 全取宿主当前状态（含内存里的种子）。推荐 A：访客看到的配置就是线上 demo 此刻的样子，四个哈希与宿主已发布的相同；宿主内存里的种子会被演示改动（成员回复带真实的显示名、有人点过模拟支付、被接手过），复制过去就把成员姓名与别人的操作带给了访客，所以 C 不行；B 会与线上 demo 不一致。依据：owner 要不要沙箱跟着线上 demo 的配置走。
2. **沙箱的持久化契约。** A 进 PG，种子与模拟器会话一律 `sbx-` id、`channel: 'simulator'`，绑定微信的会话照企微是 `wecom:<external_userid>`、`wecom`（R8），02 R6、`conversations_id_check`、不变量 11、console 排除 `sim-` 原文不动，02 不变量 6 与 13 按文件头部分取代；B 种子副本保留原 id 与 `channel: 'wecom'`，`Supersedes in part` 02 R6 与不变量 11，CHECK 换成触发器、`isDemoClassId` 改看租户；C 沙箱只在内存。推荐 A：已实现的会话契约不改，宿主「demo 类永不进库」的保护原样留着；`simulator` 渠道让按企微判断的窗口、额度、跟进、失败备注对种子自然不走，另一头是真微信的会话才照企微走，剩下的几处显式挡（R11）；删干净能用 SQL 证明。B 要给每个按企微判断的分支开沙箱例外；C 里 trace 等是 503，重启即丢。代价：种子在工作台里显示成「演示」渠道，没有企微观感。依据：owner 是否接受。
3. **沙箱在哪种 profile 下开。** A 只在 demo（`APP_ROLE=sandbox` 在 prod 下拒绝启动）；B prod 也能开（给以后托管的试用）。推荐 A：prod 实例服务真实客户，公开的开通入口与它的模型花费没有理由出现在那里；沙箱要的模拟器、模拟支付本来就是 demo 能力。托管要试用时另写 spec。现在就能定。
4. **每租户预算的口径。** A 按轮次（今天访客预算的口径）；B 按请求尝试次数；C 按金额。推荐 C 加 B、在尝试层原子预占、覆盖全部用途、沙箱禁用对冲：金额最接近真实成本，次数兜住未知价格的模型，预占才挡得住并发与重试；A 管不到工具循环、重试、对冲与工作台。沙箱与 standard 分开计：沙箱按个硬上限加当天池上限；standard 只有每天的软上限告警、从不降级，因为把真实客户的对话降成固定话术比多花钱更糟。依据：owner 要不要对 standard 租户设硬上限；现在没有真实的多租户托管，推荐先不设。
5. **免密会话的身份与有效期。** A 独立的 `__Host-sbx`，开通事务里签发、受限函数解析，空闲期限等于剩余寿命，有效 cookie 期间复用；B 复用 `__Host-sid` 加租户切换；C 凭 URL 里的令牌进入。推荐 A：B 让成员登录与沙箱互相挤掉；C 的令牌会经引用头、历史、截图泄露。代价：没有 cookie 的两个标签页同时首开会开出两个、各占名额（要严格「一个浏览器一个」就得另加开通幂等凭据，不值）。ready 之前定。
6. **「只发给访客自己」的边界。** A 只管客户渠道：体验客服只发给绑定的那个微信，其余照宿主；B 管全部对外副作用：客户渠道同 A，群通知、只关乎沙箱的告警、OTel 一律不发，跟进不做，只有模型与 embedding 照常、靠预算管。推荐 B：访客能随手触发转人工，A 会让任何人刷运营的企微群；沙箱的告警与遥测对运维是噪音，原文导出还多一处第三方存储；跟进会在访客走开之后继续往他的微信发消息。分进程之后 B 大半是结构上的（沙箱进程只有体验客服的凭据），代价很小。ready 之前定。
7. **沙箱用独立 Host 还是与宿主同源。** A 独立 Host；B 同源，沙箱挂在 `/s/<slug>/` 下。推荐 A，理由主要是同源要改的东西多：chat、pay、console 的根路径都写死；`chat.html` 的 `LS_KEY`（`public/chat.html:379`）同源时会与宿主模拟器共用；console 要支持运行时 basepath，展示时要给站内链接补前缀，还会碰锁定套件对 `chat.html` 的检查。另一个好处是匿名访客写的内容与成员的工作台不同源。注意：A 不等于跨站，沙箱 Host 若与主站同一注册域，防线是 `isCrossSite` 拒绝 `same-site`（R10）。分进程（开放问题 11）也要求独立 Host。依据：owner 是否愿意加一个子域名。
8. **限额的数值。** 推荐：同时 20 个；每小时 10、每天 50、每 IP 每天 3 个；闲置 120 分钟回收；每个沙箱 300 次尝试或 1 元、30 个新会话；全池每天 10 元；沙箱进程并发 2。写入：每分钟 30 个写请求、产品条目至多 80（模板 43 条）、每个条目至多 20 个版本、单次导入至多 80 行、每天至多 20 次 SOP 发布、快捷回复至多 50 条。绑定：码 8 位、10 分钟；每个沙箱每小时至多签 10 个码；固定话术每个微信 10 分钟一条、全进程每小时至多 200 条；每个微信每小时至多 10 次绑不上；名额用完的告警每天至多一次；出码 3 分钟没绑上就提示改用模拟器。最坏花费：每次尝试发出前都对全池预占了足额的金额，重启时池的当天数又计入所有还没删掉的沙箱，所以进程不崩溃时一天的总花费不超过池上限。用量写不进库超过 60 秒，沙箱一律停调，不会在刷写失败期间继续花钱。例外只有崩溃：每次少记至多 60 秒内结算、没落库的尝试，加在飞的 2 次；按并发 2、每次几秒估算约四十次请求，按 04 实测不到 0.1 元。反复崩溃时，`watch.sh` 的重启告警会提醒运维停掉沙箱服务。正常体验按 04 的实测（真实模型 30 段对话约 0.44 元）远用不到 1 元。ready 之前先定，上线一周后按 `sandbox_pool_daily` 再调。
9. **体验客服挂在哪、凭据给谁。** 官方文档（微信客服「概述」）写的是：管理员在「微信客服 → API → 可调用接口的应用」里选自建应用，再在「通过 API 管理微信客服账号 → 企业内部开发」处设置要由自建应用管理的客服账号；全局错误码 48007「API 接口无权限调用，由于对应的客服账号未授权」说明授权按账号算。但文档没写明同一企业里能否把两个客服账号分别授权给两个自建应用，也没写回调按应用分发。A（推荐）同一企业、单独的自建应用：体验客服只授权给它，回调指向沙箱 Host；沙箱进程的 secret 在企微那边就操作不了 `kf-main`，宿主进程收不到体验客服的事件。B 另注册一个企业放体验客服（不需要营业执照，同样未验证，名额各算各的）：隔离最硬；代价是多管一个企业，微信里显示的是另一个企业名。C 宿主收回调、替沙箱进程收发：宿主要持有体验客服的凭据、多一条沙箱专用的路径，沙箱的微信随宿主一起停，回滚到 pre-05 时这条路也断；两个账号在同一应用下时，「沙箱发不到 `kf-main`」只剩代码里的核对。不推荐 C，也不推荐与 `kf-main` 共用一个应用：沙箱进程是匿名可写的那个，凭据碰得到 `kf-main` 就回到了 owner 2026-10-10 否决的风险。依据：owner 建账号时按前置条件实测，48007 实测通就选 A，不通选 B。
10. **console 的渠道账号页。** 04 的非目标写成「阶段 5」。推荐本阶段不做：线上 demo 不建网页渠道账号，沙箱没有渠道账号，第一批真实客户一家一个实例、由运维命令开通；等托管多个真实租户时一起做。owner 确认后，主参考阶段 5 一节随 ready 补一句。
11. **沙箱单独一个进程，还是与宿主同一个进程。** A（推荐）单独的 `sandbox` 服务，同一镜像、`APP_ROLE=sandbox`、同一个 PG，见 R1 与「两个进程」表；B 同一进程装宿主与沙箱（原稿），分两步上线：05a 先上多租户核心与严格模式、在线上空跑几天，05b 再开沙箱。推荐 A：宿主进程线上永远只有一个运行时，02–04 的测试覆盖的就是这个形态，作用域漏了也只会在沙箱进程里暴露，碰不到线上 demo；沙箱进程只有体验客服的凭据，「只发给访客自己」大半是结构上的；出事 `docker compose stop sandbox` 即可，宿主不用重启。代价：多一个 Node 进程（估 150–250 MiB，开工实测）与一组数据库连接；`deploy.sh`、compose、`watch.sh` 认第二个服务；ADR-002「始终一个进程」要补注；语义索引不跨进程共用（沙箱进程首次多建一次，约 20 条 embedding）；「同部署多租户」的线上证明改由沙箱进程里的多个沙箱承担，两个 standard 租户同进程只在测试里验。B 省一个进程，但任何一处作用域遗漏都发生在线上 demo 的进程里，05a 的空跑只能发现已经走到的分支。依据：owner 能否接受多一个服务；ready 之前定。
12. **锁定的 `server.selftest.ts` 与去掉引导页冲突。** 它断言 prod 与 demo 关模拟器时 `/` 302 到 `/admin.html`（第 1165–1170、1195–1199 行），demo 下 `/` 302 到 `/guide.html`（第 1210 行）、`/guide.html` 200（第 1211–1216 行）。A（推荐）owner 一次性授权改这几处，单独一个提交、只改这些断言：第 1167–1168 行改成 `/` 302 到 `/console/`；第 1196–1197 行的 `/admin.html` 改成 `/console/`；第 1210 行改成 demo 下 `/` 302 到 `/console/`；第 1211–1216 行改成 `/chat.html` 200、`/guide.html` 404。`SIM_PAGES` 与第 1160 行（prod 下 `/guide.html` 的几种写法 404）照旧成立、不动，别的锁定文件与断言一字不动；提交后记下新的 sha256，plan 第一步核对。B 不改锁定文件：`/` 照旧跳 `/guide.html`，`guide.html` 改成立即跳 `/console/` 的空壳，满足断言的字面、违背本意（多一跳、页面闪一下，prod 下 `/` 仍去 `/admin.html`），不推荐。C 保留引导页，不做 R23。依据：owner 是否授权改锁定文件；ready 之前定。
13. **绑定码与重新绑定。** 码：A（推荐）一个 8 位码同时给扫码（`scene_param`）与手打用，10 分钟、一次性；B 只扫码，码可以更长。A 的手打是扫不了码时的退路（工作台与微信在同一部手机上），8 位 base32 约 40 位，加上每个微信每小时 10 次的错码上限，猜中别人的码不现实。重新绑定：A（推荐）后绑的赢，换一个码就能改绑，被顶掉的一边收到固定话术；B 先绑的锁住，到沙箱删掉才放开。A 的代价是转发出去的码若先被别人用掉，访客要点「换一个码」再扫一次；B 在码被抢先用掉时访客只能结束体验重开。依据：owner 是否接受 A 的这个代价；ready 之前定。
14. **微信里点开的链接。** AI 发到微信的支付链接、方案书在微信内置浏览器里打开，那里没有访客电脑上的 `__Host-sbx`，而沙箱的公开页按 cookie 找租户（R10）。A（推荐）每个沙箱一个与 slug 无关的随机链接令牌，发往绑定微信的请求体在发送边界改写成 `/wx/<令牌>/…`，跳转一次、设只开这几页的 `__Host-sbxw`（R21），页面与接口一行不改；令牌与 slug 分开，slug 照常当标识进日志，要管住的只有令牌出现的三处；B 沙箱的公开页不要 cookie、按订单 id 在所有沙箱里找：种子订单 id 在每个沙箱里都一样，与被否决的「按订单号全局解析」同一个问题；C 不处理，微信里点开跳到 `/try`，体验断在付款这一步。A 的代价：令牌在链接里就是这几页的凭据，转发给别人就能看、能模拟支付，与宿主的 `/pay/:orderId` 同一口径。依据：owner 是否接受这个口径。
15. **demo 下匿名打开 `/` 落在哪。** 今天 demo 匿名打开 `/console/` 进的是匿名只读外壳（后台 UX spec「外壳 · 启动」）；owner 2026-10-11 定的是未登录看到登录页，而 AGENTS.md 要求 demo 的匿名只读 console 照旧能用。A（推荐）先到登录页，「只看演示数据」进匿名只读外壳：照 owner 的方向，匿名只读还在、只是多点一下，后台 UX spec 那两句按文件头部分取代。B 照旧落在匿名只读外壳、在它的顶栏加「免登录体验」：不动后台 UX spec，但未登录看到的不是登录页。依据：owner 选；ready 之前定。

## 被否决的方案

- **线上开共享的可操作 demo 账号，每天定时重置。** 人工回复会经企微真发给扫码的客户；公开账号能看到真实会话与别的访客的聊天；访客之间互相改坏 SOP 与价格（owner 2026-10-10）。
- **沙箱用单独的库，或每个沙箱一个进程或容器。** 单独的库要另一套迁移、备份与角色，读模板要跨库；每个沙箱一个进程，内存与运维随沙箱数增长。R1 的做法是固定多一个服务、共用一个库，不随沙箱数增长（原稿以「内存与运维翻倍」否决的是这两种，不是固定的第二个服务）。
- **单运行时隐式回落作为通用规则。** 作用域遗漏会被单租户的测试掩盖，直到第一次开出沙箱才暴露；改为按角色与配置在启动时定（R3）。
- **按订单号全局解析公开路由（`SECURITY DEFINER` 函数）。** 方案书、隐私说明、模拟器没有全局唯一的 id，线路 id 在租户之间本就重复；还会让一个租户的支付页在别人的域名下打得开。
- **每个沙箱一个子域名。** 要通配证书与通配解析；一个沙箱 Host 加会话 cookie 就够分开。
- **装载库里全部未停用的 standard 租户。** 留着的测试与演练租户会被意外服务。
- **继续用一个全局 `bindPack`，每轮按租户切换。** 一轮里有多次 `await`，并发的两轮会切走对方的绑定。
- **沙箱种子保留 `channel: 'wecom'` 求企微观感。** 按企微判断的窗口、额度、跟进、通知、失败备注每一处都要开沙箱例外，漏一处就有副作用或误报。这条只针对种子：种子的另一头没有真微信；绑定微信的会话另一头是真微信，照企微走正是要的（R8）。
- **把 `kf-main` 改成体验客服。** 那样线上就没有任何东西在跑真实客户那条路径（03 的账号存库、`channel_inbox`、先落库后发送），部署后的自检也就没了；体验客服是另一套运行时（R21），替代不了它（owner 2026-10-11）。
- **体验客服复用 `kf-main`、按绑定码分流。** 沙箱进程就得持有 `kf-main` 的凭据，一处疏漏就会发给线上的真实客户，正是 owner 2026-10-10 否决的风险。
- **绑定解析经 `SECURITY DEFINER` 函数（上一稿）。** FORCE RLS 下函数要先查表才知道设哪个租户，只能逐个沙箱设作用域去找；沙箱进程本来就装着全部沙箱、独占它们的锁，在进程内解析更简单，库表照常套 RLS（R22）。
- **用 slug 当 `/wx/` 的凭据（上一稿）。** slug 会进日志的租户字段、装载日志、审计与 `sandbox list`，要管住的输出面太多；改成只出现在三处的链接令牌（R21）。
- **保留引导页、加「体验工作台」按钮（原稿）；`/try` 用 GET 即开通。** owner 2026-10-11 定引导页不是生产级的入口；GET 即开通会被微信等的链接预览白白开出沙箱。
- **用 `jobs` 表触发器挡沙箱的任务。** 任务随会话落库，触发器一拒，整次落库失败，会话被标 poisoned；在 `queueJobs` 丢弃。
- **按成功响应记账、操作开始前判一次额度。** 并发的操作会同时读到未超限，重试与对冲的输家不记；改为尝试层原子预占（R15）。
- **只靠测试清沙箱的状态。** 漏掉没写到的分支；要靠每个模块级绑定都分了类（清单与默认拒绝的 lint）加严格模式。
- **加验证码。** 依赖第三方、还要处理个人信息；全局上限与池上限已封住最坏的花费。
- **删除时留墓碑行。** 与「整个租户删掉」不符；统计进不带租户的 `sandbox_pool_daily`。
