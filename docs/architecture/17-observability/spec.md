## 给你看的一页

**做什么：** 在现有后台补上“看回复好不好、每天发生了什么、变慢时找得到原因”，再在本机验证追踪数据能被 Langfuse 看懂。

- 管理员在「AI 记录」里给一轮最终回复标好评或差评，差评必选原因；按未评、差评筛选，优先检查有问题的轮次。暂不让共享试用账号打分。
- 差评可以生成回归草稿，但不把客户原文装进下载文件。管理员在受控位置把问题改写成测试，真实来源的测试始终留在私有层；原有锁定用例不动。
- 运维群每天 09:00 收到一个租户昨日的接待会话数、转人工率、回复 p90、AI 错误率、模型费用及已付订单数。只用 SQL 和确定性计算，不调用模型，不做跨租户总榜。
- 连续三个五分钟窗口各有至少 20 条有效回复，且 p90 都超过 8 秒，发延迟告警；告警注明严重程度、处理手册和可用的 trace 链接。低流量显示样本不足，不当作恢复。
- 概览可切换 7 天、30 天趋势。只有 7 天留存就只显示 7 天可查询范围，采集缺失和已经清掉的数据不会画成零。
- Langfuse 只在本机用合成数据验证，不连线上，不采集正文。交付版本清单、字段对照与失败场景证据，不以“服务启动了”代替兼容验证。

**怎样算做完：** 登录后台完成一次差评，再把外部草稿改写成可执行回归并运行（验收 1–5、13）；跨重启仍不会重复排同一天摘要，故障状态可解释（验收 7–8）；可用受控数据准确触发及恢复延迟告警（验收 9–10）；短留存、窄屏、深浅色图表如实呈现（验收 11）；本机真实 Langfuse 看得到正确的 span 树及字段（验收 12）。

**代价与限制：** 增加少量 PostgreSQL 表和后台查询；不增加模型费用。抽检是人工意见，不等于总体质量分。群机器人发送成功但确认丢失时，无法同时保证绝不漏发和绝不重发，停止自动重发并标“结果未知”。趋势只解释留存范围内的数据，费用是模型成本记录，不是对客账单。

**不做：** 新监控平台、值班系统、商家老板日报、线上 Langfuse、模型自动打分、修改销售决策与提示词。

**已定结论：** D1 采用仓库外私有路径、无原文草稿及人工改写审查；D2 仅 owner/admin 打分，共享试用账号不能打分，面试时由管理员账号演示或用官网截图；D3 按租户每日 09:00 显式启用摘要；D4 发送未知不自动重发；D5 固定 8 秒阈值及有效连续窗口；D6 原生 SVG 加可读数据表；D7 固定 Langfuse v3.122.1 本机验证。owner 2026-10-31 已全部照推荐定案；档位仍待确认，未另行点名批准 ready 前不实施。

## 目标

1. 人工抽检能留意见、筛出问题，并经安全路径形成可执行回归。
2. 一个租户的昨日运行情况可按时汇总到运维群。
3. 持续慢回复有低噪声告警，通知能引导定位。
4. 现有概览直接显示可解释的逐日趋势。
5. 用本机合成链路核实指定 Langfuse 版本的字段兼容。

## 非目标

- 不做 Prometheus、Grafana、Loki、ELK、Sentry、值班系统；引入信号见「后续」。
- 不做商家老板日报、跨租户聚合、自动模型打分、自动改 SOP 或自动发布回归。
- 不接线上 Langfuse，不更换 OTel SDK，不开启 `OTEL_CAPTURE_CONTENT`。
- 不修改系统前缀、SOP、工具定义、四个哈希、价格、订单、审批；8 个锁定文件逐字节保留。成交只读。
- 不删除 demo 的重置、匿名只读、种子保鲜、访客清理；不把 15 的线上停沙箱决定变成源码删沙箱。

## 现状与方案

### R1 · 适用范围与逐角色权限

抽检、摘要、延迟告警与趋势的新持久化能力只用于 db 配置且 db 会话存储的 standard 租户。文件模式新接口在完成权限检查后返回 503 `store_file_mode`；沙箱返回 403 `observability_unavailable`，不建任务、不发群消息、不开放新评分/导出，现有沙箱 trace 能力不变。demo profile 下已登录且符合条件的成员可用，匿名只读不增加入口。

| 身份                          | 新抽检读 / 写  | 新回归草稿     | 新趋势           | 摘要及告警配置                     |
| ----------------------------- | -------------- | -------------- | ---------------- | ---------------------------------- |
| owner                         | 是 / 是        | 是             | 是               | 由受控运维配置，不增网页写设置     |
| admin                         | 是 / 是        | 是             | 是               | 同上                               |
| supervisor                    | 否 / 否        | 否             | 否               | 否                                 |
| agent（含 15 的共享试用账号） | 否 / 否        | 否             | 否               | 否                                 |
| viewer                        | 否 / 否        | 否             | 否               | 否                                 |
| 匿名 / 未登录                 | 否 / 否        | 否             | 否               | 否                                 |
| 平台运维身份                  | 不模拟成员打分 | 无网页绕过权限 | 不提供跨租户接口 | 显式租户作用域内配置和查看发送状态 |

未登录 401，角色不符 403；先鉴权再解析数据定位参数。停用租户继续按 14 拒绝后台访问。客户端隐藏按钮只是提示，所有请求仍由服务端检查。任何登录失效或切租户都清空相关查询缓存；不提升 agent 的 trace/费用权限。

### R2 · 抽检对象、存储与竞争

入口放在「AI 记录」详情的最终回复之后；列表加“全部 / 未评 / 好评 / 差评”和固定原因筛选，与现有时间、outcome 筛选相交。使用原有游标分页，单页最多 100 条，不新增评分总榜，也不把主动挑出的样本率称为总体好评率。

评分对象为一轮已经落库、存在最终文本且有关联 `messages.turn_id` 的 `author='ai'` 消息；评价最终发出的内容而不是模型原稿。确定性 AI 回复也可评。无最终回复、纯 silent/reset、欢迎语、人工消息及无可对应 trace 的 followup 不可评，返回 422 `review_not_applicable`。按轮打一次，分段不是多个评分。

新增 `turn_reviews`：`tenant_id uuid`、`turn_id uuid`、`rating ('good'|'bad')`、`reason`、`reviewer_user_id uuid`、`revision integer`、`created_at/updated_at timestamptz`。主键 `(tenant_id, turn_id)`；复合外键到 `turn_traces(tenant_id,id)`，`ON DELETE CASCADE`。不复制客户文本、模型原稿、工具参数、会话原 id，不设自由文本备注。原因固定为 `incorrect`（内容错误）、`missing`（遗漏）、`handoff`（转人工不当）、`format`（表达问题）、`other`（其他）；差评必须选一项，好评 reason 必须为 null。

一个租户一轮只有一个当前结论。首次 `expectedRevision=0`，修订带读到的 revision，条件更新成功才加 1；两名管理员同时提交，一名成功、另一名 409 `review_conflict`，不覆盖别人的意见。仅当当前 revision 等于 expectedRevision + 1、操作人相同且内容相同时，重复提交返回当前值、不重复记审计；其余旧 revision 提交仍冲突。改错允许修改，不提供普通 DELETE。成员失效后保留评分，显示“已移除成员”，不为评分保留成员邮箱。

写评分与 `trace.review` 审计同事务。审计只记录评分、原因、修订号和操作人，不复制回复，也不保存可还原客户标识的目标；评分详情可在当前授权事务中关联原 trace。评分不改变会话 `updated_at`，不得延长客户数据保留期。

### R3 · 留存、清理与多租户

- 新增的 `turn_reviews`、`ops_daily_reports`、`ops_latency_state`、`ops_metric_coverage` 四表均有 `tenant_id`、ENABLE + FORCE RLS、显式租户策略；跨租户复合键不能只靠 UUID 随机性。运行时只经 `withTenant`，平台身份也显式选择一个租户。
- `turn_reviews` 跟 trace 删除级联；`purge_expired_traces`、`purge_conversation`、平台 `eraseConversation` / `erase_conversation` 都必须证明评分消失。trace 先到期时提前清评分，会话先到期或行权删除时立即清。新迁移按需增补清除函数的计数投影，不能扩大 app 的任意 DELETE 权限。
- 15 的真实试用消息及 trace 保留 7 天，评分不会活得更久；种子会话保留期豁免不等于 trace 永久保留。手动重置两类会话时评分都清，不复制到新种子；受控种子里的用户输入仍视为真实来源。
- 沙箱本期不写新表，但 `sandbox_tenant_purge` 的表清单及防漏断言仍覆盖四表；意外残留不能阻止整个租户删除。
- 日账本只存日期、状态、计数与固定错误码，不存会话/trace/成员标识。业务数值在 `min(35, retention_trace_days)` 天后清掉，仅日期和终态保留 35 天以去重；过期日不会再次补发。延迟状态只留窗口终点、计数、p90 和状态，不长期保存样本 id。coverage 仅留日期和完整性标志，也按 R10 清理。清理与现有 retention job 同路径执行，不引入永久的原始数据副本。
- 新缓存、定时器和发送状态进 `src/tenancy/state-manifest.ts`；租户卸载、scope 丢失及进程关闭均有释放或停止路径。

### R4 · 差评回归：先做草稿，再做人审

**D1 已定：分清来源，文件落在仓库外。** 普通试用者、沙箱访客和真实商家的输入都按真实数据处理；只有受控夹具从输入到模型替身输出均为合成、且人工核对无混入时，才可成为公开用例。`seed=true`、手机号打码或一勾“已脱敏”都不是合成证明。

新增的“准备回归草稿”只在差评上可用，下载 `RegressionDraft` 附件：带固定原因、包 id、格式版本和空白的 v2 case 骨架；不携带 source trace id、会话 id、原话、最终回复、工具结果、客户产品库、附件、订单或现有模型调用快照。草稿强制 `_draft: true`、`turns: []`，不能直接通过 `validateCase`。生成与 `trace.regression_draft` 审计同事务，失败不给文件；`Cache-Control: no-store`，固定安全文件名，不按客户内容命名。

管理员在已授权详情里查看问题，人工用虚构产品、数量、措辞重建最小复现，补预期断言、合成模型脚本及 `pack`。不自动把错误回复当成正确答案，不调用模型做改写或评分。原始资料始终只在数据库/受控私有存储，脱敏后仍源自真实对话的评测集按 ADR-003 留私有层，不进入公开仓库。

发布前的人审检查包括客户姓名、联系方式、真实企微标识、产品资料、商业条件、地址、附件及间接可识别信息；正则脱敏仅作辅助。外部文件先运行 `CONFIG_SOURCE=file LLM_MOCK=1 pnpm exec tsx eval/run.ts --cases-v2 "$PRIVATE_CASE_FILE"`。外部结果文件和任何包含输入的失败输出同样留在受控位置；公开 plan 只记用例数量、通过与否和内容无关的错误码。真实模型运行需另行授权，本期验收可用合成脚本。

源问题与外部回归的映射留在私有导出登记中，标注租户、失效日期与删除责任人；在源会话到期、行权删除时处理相关副本，公开 core 不声称能撤回浏览器已下载的文件。仅完整独立创作的合成回归可人工新增到 `eval/cases-v2/`，不改 8 个锁定文件、不自动提交、不自动纳入发布闸。

07 的 travel `goal-draft` 及其既有权限、审计和 schema 拒收契约保持；它不是工业路径，也不是公开入库通行证。本期新入口不得回退调用它来获取真实原文。若 owner 要同时改变旧下载格式或权限，必须先补部分取代条款，不能实现时顺手修改。

### R5 · 指标定义与统一日窗口

新增摘要与趋势共用确定性 SQL 聚合函数，不能从当前内存计数拼“昨日”。按部署 `TZ` 的自然日，默认/本次验收为 `Asia/Shanghai`；一个窗口是 `[本地零点, 次日零点)`，以 timestamptz 参数查询。不得用固定减 24 小时处理其他时区的夏令时。与 14 的 `usage_daily.day` 同口径；变更部署时区需维护窗口，不支持在线随意切换。

| 字段                          | 可执行口径                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `receptions`                  | 当日有已落库轮次的去重会话数，不是新增联系人或 AI 回复条数                                                                                                                     |
| `turns`                       | 当日已落库轮次数，以 `started_at` 归日；重复回调重放不产生第二条                                                                                                               |
| `handoffRate`                 | 上述会话中至少一轮 `outcome='handoff'` 的会话数 / receptions；主动人工接手另沿用现有看板，不混称本指标                                                                         |
| `replyP90Ms` / `replySamples` | `outcome='replied'` 且关联已保存 AI 消息、duration 非负的轮次，`percentile_cont(0.9)`；保留模型重试耗时；不含 silent/reset/budget/deterministic/handoff/error、人工和 followup |
| `aiErrorRate`                 | outcome 为 error，或 llm 数组任一项 error 非空的轮次 / turns；后续重试成功仍计出错，一轮最多一次                                                                               |
| `costMilli`                   | `usage_daily` 当日全部用途 `cost_milli_cny` 之和，整数厘；14 的 reply 行为零费用，不把 calls 当金额，不二次计 chat；展示元时除 1000                                            |
| `paidOrders`                  | 按不可回写的 `paid_at` 归日，每个订单计一次；排除作废订单，已退款订单仍是曾付款，文案“已付订单数（含后续退款）”；未付报价不算成交，不把金额混入这项                            |

业务指标只统计 standard 中 `originOf(...)=customer` 的会话/订单；15 的试用公司明确标为“共享试用”，其真实输入仍计入；种子、模拟访客不混入实接待，不能另造一套 id 前缀判断。SQL 的来源谓词与 `src/shared/origin.ts` 同源或由共享分类生成参数，并用三种来源的对照自测约束。费用表没有会话来源维度，`costMilli` 必须标“租户全部模型费用（含测试）”，不能声称已剔除种子费用。

分母为零时比率与 p90 返回 null，费用和计数仅在完整可查询日且无记录时返回 0。统计缺失、清理或不足整日时标 partial/unavailable。p90 是引擎回复耗时，不是微信端到端送达耗时；摘要及图表说明中明确这一点。迟到落库只影响重新查询，不追改已发出的昨日摘要；记录 `computedAt`，不宣称财务结算精度。

### R6 · 每日摘要的租户边界与调度

公开 core 只实现**一个租户一次聚合、一次通知**。平台可给每个 standard 租户启用；同一运维群可收到多条单租户摘要，但 core 不合计、不排序、不暴露跨租户查询。跨租户日报或总榜另走 ADR-003 私有层。

复用现有运维群 `ALERT_WEBHOOK_URL`，不发顾问群，不提供租户可填任意 webhook 的网页接口。新增可选 `OPS_DIGEST_TENANTS`（服务器 env 中的租户 slug 列表，默认空）；应用严格核验其存在且为 standard，解析后的配置绑定租户作用域。真实列表不入库、不入仓库、不回显。复用该租户受控 `public_host` 构造链接，不借旅游宿主地址替工业地址。

每个启用租户每日 09:00（上述 TZ）排昨日 `ops_daily_digest` job，payload 只有 `day`，dedupeKey 为日期派生的固定键。启动及每小时补排，当日 09:00–24:00 只补昨日一次，过了当天不追赶历史。停用、沙箱和未配置跳过；执行及网络发送前重读租户状态。旅游 suspended 后取消未发送摘要且不再排程，恢复只按当前日规则继续，已有“发送中”无法召回，不谎报取消成功。宿主停用不停止工业作用域的 jobs，也不停止主机/存储告警。

`ops_daily_reports` 主键 `(tenant_id, day)`；字段包含随机报告 id、状态、attempts、next_attempt_at、computed_at、sent_at、固定 error_code、聚合值和 coverage。job 与日账本的创建在同一短事务里；已有终态即使 jobs 已清理也不再发送。新 kind 放独立 ops lane，不能让 webhook 等待堵住 followup 或 retention。SQL 只读事务设 5 秒 statement timeout、每次只查一天；首次发送前冻结聚合值与 computed_at，明确拒绝后的安全重试沿用同一快照；发送前发现源数据删除则使未发送快照失效、重新计算 coverage，已发送的仅留原统计时刻，不追改群消息。网络调用不占数据库事务和连接锁。发送经过共享限流器，摘要低于故障告警优先级。

摘要字段严格白名单：日期、固定的试用标识、随机报告短号、计数、百分比、耗时和费用，外加“数据不足”说明；不带租户显示名、原文、成员、客户标识、真实企微账号标识。租户的可读对应关系只放受控运维配置，公开示例全部合成。金额属于要求的运行费用，不含价格、订单明细或商业定价。

试用 7 天留存足以通常覆盖昨日，但手动重置、行权删除、初次开通或采集缺口会使昨日不完整。聚合返回 coverage；检测到清理涉及日窗口或没有完整采集证据时写“留存范围内统计 / 数据可能不全”，不把删掉的接待数当作零。摘要不为凑齐统计延长保留期。

### R7 · 发送失败、重试与跨重启幂等

不能以 `alert()` 的无返回值后台发送充当持久任务完成证据。为摘要复用传输层但增加结构化发送结果：`accepted | rejected | unknown`，不改变原 alert 调用方的语义。5 秒网络 deadline，响应体上限 8 KiB，不跟随重定向；凭据、响应原文、地址不进日志。

日账本状态：`pending → sending → sent | unknown`；可确认未投递的失败回 pending，累计最多 3 次，按 1、5 分钟退避，当天截止后 failed。认领令牌和 `sending` 必须先提交成功再发，避免两个任务并发发送。配置缺失、限流、SQL 故障发生在请求前，可以安全重试；明确业务拒绝也可重试。超时、断连、无法解析响应、含糊的服务端故障都记 unknown，不自动重发。

重启时 pending 重排；sending 一律归 unknown（即使可能尚未实际发出），sent/unknown/failed/skipped 均不自动重排。成功响应后数据库提交失败也按 unknown 恢复。接受极少量漏报而避免未知状态的自动重发。运维可在群里按报告短号查证，再经显式租户的受控命令 `ops-report retry --tenant <slug> --day <date> --ack-duplicate-risk` 重试，记录无正文审计及重发次数；同样的报告 id 保留。新 CLI 只接受当天的昨日统计日；更早的报告即使还在保留期也不能补发。

明确失败或 unknown 只留一次运维事件，不递归用失败的 webhook 发送“告警发送失败”。摘要故障不阻塞引擎；共享限流仍保留原每分钟最多 10 条的应用预算，摘要限流在请求前回 pending。主机巡检保持原独立通道。

### R8 · 延迟告警状态机

默认关闭，新 `OPS_LATENCY_TENANTS` 按显式 standard 租户启用；不依赖摘要是否打开。8 秒本期固定，不提供按租户可配阈值（D5）；后续确有不同服务目标再另改，不先做配置页。

每分钟在后台检查**已结束且额外留出 1 分钟落库等待**的五分钟自然窗口（按 UTC epoch 对齐，与每日时区无关）。每个窗口只评估一次，复用 R5 的有效回复定义，只包含真实客户来源。查询数据库而不是仅订阅 `onTurnEnd`，避免尚未提交及重复回调干扰。5 秒查询超时；窗口延迟落库超出等待时不重评，属于可观测性缺口，不伪造 p90。

- 每窗 `replySamples >= 20` 才有效。连续 3 个相邻有效窗口 `p90 > 8000ms` 触发 `reply_latency`（P2）；等于 8000 不触发，约持续 15 分钟后报告。
- 恢复要求连续 2 个相邻有效窗口 `p90 <= 6000ms`；6000–8000 保持现状并中断恢复计数。恢复发一条通知。
- 样本不足、查询失败或进程漏检窗口会中断连续计数，**不清除已告警状态、不宣称恢复**；停用标为暂停，恢复后重新收集连续窗口。
- `ops_latency_state` 每租户一行，保存 last_window_end、bad_streak、good_streak、active、last_sent_at；同窗重复检查条件更新无效。重启恢复状态，跨重启不因相同窗口再次触发；持续慢每 30 分钟至多一条提醒，升级、恢复沿用现有规则。
- 触发时只临时选择最近慢窗的一条有效 trace UUID 构造深链接；若已清理、无合法 host 或为实例级故障则省略，写“无可用单轮记录”，不捏造会话链接。

### R10 · 趋势接口、缓存与界面

新开 `GET /api/console/metrics/trends?days=7|30`，不改旧 `/metrics` 的字段和默认 7 天，也不改 14 的 `/usage` / `UsageView`。按租户、请求天数、时区、coverage 起点缓存 60 秒，并发请求共用一次聚合；失败不缓存。跨日、租户停用、保留期变更、删除或试用重置作废缓存，不能让旧的聚合延长可见窗口。新接口将 `computedAt` 返回给前端，明确“最多约一分钟延迟”。告警与摘要绕过此展示缓存。

共享 DTO 放 `src/shared/console-api.ts`；`PUT /api/console/traces/:turnId/review` 写评分，GET 同一路径读（未评返回 `review:null`），`POST /api/console/traces/:turnId/regression-draft` 下载骨架。列表原响应行新增可空 review 摘要，旧字段保持；写入校验严格拒绝未知字段，沿用同源/CSRF 防护，请求体封顶 4 KiB。不存在及跨租户 404，内容校验 400，状态不适合 422，竞争 409，审计/存储失败 503。HTTP 成功前必须等事务完成。

实际窗口为请求天数、trace 保留期、租户开通及已知采集可用起点的交集；费用和订单也截在同一窗口，不因它们存得更久凑满 30 天。不能把第一条 trace 时间当作采集起点（低流量可能之前没有事件）；独立的 `ops_metric_coverage` 以 `(tenant_id, day)` 为主键，保存 `first_seen_at`、`last_seen_at`、`has_gap`、`has_deletion`，无任何客户标识；不依赖摘要是否开启。db standard 启动时标记首次/重启所在日，每分钟更新检查点，检查点间隔超过 2 分钟或进程重启即保守标记 has_gap，不猜测停机期间没有流量。只有覆盖完整自然日、无 gap/删除且存储健康的日期可标 complete；无证据的既有历史标 `unknown_history` / partial。保留最近 `min(30, retention_trace_days)` 个自然日，受控清理函数执行。清理/行权函数在同事务中标记受影响的 trace.started_at 和 order.paid_at 日期（无法精确定位时保守标记全部可查询日），只保存日期和删除标志；提交后作废缓存，不保留被删行的 id。今天固定 partial 但显示当前已记录的数；已清掉或采集未知的历史点用 null/断线，完整且无流量的点计数为 0、比率为 null。

采用原生 SVG 绘制最多 30 个点的简洁折线/柱形，并提供相同数据的可读表格；不引入图表库。比较：SVG 无新增依赖，字体与主题直接继承，但坐标、键盘焦点和缺测断线要自己验证；ECharts 可减少复杂交互工作，但本期没有缩放、多轴或大数据量需求，增加依赖与样式适配；Recharts 接入 React 直接，仍多一个依赖，简单趋势收益有限。本比较是本项目范围下的工程判断，不宣称某库当前版本更快，版本/包体未实测。

在现有概览 KPI 下放 7/30 天切换及六项趋势，每图独立单位，不画混合金额/百分比双轴；说明接待与已付订单口径、费用含测试、今天未结束，提供“查看数据”。30 天请求但保留 7 天时标题明确“请求 30 天，可查询最近 7 天”，轴从实际起点开始，不连到更早的虚假零点。与旧 KPI 来源范围不同之处要在标题标“客户接待趋势，排除种子”，不冒称数值必然相同。

遵循风格 A、原主题令牌、Geist / Geist Mono / Noto Sans SC；不靠颜色区分好坏，支持键盘、屏幕阅读器表格、窄屏横向数据表和深浅主题。加载为局部骨架，空为“这段时间没有可统计的接待”，失败保留旧数据并标陈旧、提供局部重试；401/403 清旧数据，503 文件模式说明而非假图。不改 15 设置导航、不重复造用量页；新文案过 `scripts/check-fonts.ts`，按需补字体字形，不能用系统字体掩盖缺字。

### R11 · 本机 Langfuse 验证

固定验证目标为 **Langfuse v3.122.1**（D7）：这是一个可点名复现的 v3 版本，不是“最新版本”或生产选型。web 与 worker 必须同版本，其他服务镜像也固定 tag 和 digest，禁止 `latest` / 浮动 `3`。本机拉取可用性、架构支持及镜像 digest **未核实**；实施第 1 步从该 tag 的官方 compose 解出全部依赖并在 plan 登记准确清单，未完成不得宣称版本已固定或开始验收。若不可用，先修订草案并由 owner 定新版本，不能静默换最新版。

已读一手依据（2026-10-31）：[v3.122.1 release](https://github.com/langfuse/langfuse/releases/tag/v3.122.1) 确认版本名；[原生 OTel 文档](https://langfuse.com/integrations/native/opentelemetry) 说明接收端点为 `/api/public/otel`，trace 专用端点为 `/api/public/otel/v1/traces`；[本机 compose 文档](https://langfuse.com/self-hosting/deployment/docker-compose) 给出本机部署方式。在线文档现为 v4，不能据此断言 v3 字段映射正确，必须使用固定 tag 的配置并实测；v4 另有接入头要求，本次不能照抄到 v3 后宣称通用兼容。

运行在一次性本机 compose project 与独立网络/卷，仅回环绑定端口；不修改线上 compose、不访问生产库、不复制真实 trace、不带真实模型 key。合成 standard 租户通过真实引擎、recorder、现有 OTel exporter 发到真实本机 Langfuse，模型传输使用合成替身。本机凭据运行时生成并放仓库外临时 env，不打印请求头；`OTEL_CAPTURE_CONTENT` 必须完全未设置，关闭 Langfuse 自身非必要外部遥测，网络不通往云端采集端点。

### R12 · 迁移、兼容与回滚

新迁移使用合入时下一个编号，只新增表、索引、权限和函数增补；放宽 `jobs_kind_check` 增加一种 kind 时按迁移规则标注，不重写已提交迁移。不改 messages 的追加规则，不改旧表数据含义；表权限从最小 SELECT/INSERT/UPDATE 起，删除仍走受控清除函数。评分表外键删除需覆盖旧镜像调用既有清除函数的情况。

旧镜像不读四张新表、不识别新接口，后台无新按钮，原指标与销售照旧；旧 runner 的 lane 不认领新 kind，但启动恢复函数可能扫描全部状态，因此不能只靠“认领不到”保证回滚。回滚前停止新功能排程、等待在途；将新 kind 的未完 job 取消，sending 的日账本归 unknown；保留 sent/unknown/failed 日账本，新镜像再前滚不能重发。不得删除日账本、整库恢复或反向 drop 表。旧版会忽略新功能 env，退回后摘要、延迟监测停止，主机巡检仍在。

最小可回退镜像必须包含 14 R6 和 15 已部署的试用删除/重置保护，不能回到会因 suspended 宿主拒绝启动的版本。若旧镜像仍会接收抽检请求，路由自然 404；保留 DB 级评分级联，证明旧版行权删除也不留评分。只在新版中执行日账本/延迟状态清理的能力，旧镜像长期运行会暂停这项维护，回滚手册要求运维停用新功能并在保留期内执行受控清理，不得延长相关明细生命周期。

新镜像在日界/09:00 使用独立到期计时或 runner 的每拍到期检查，不能只依赖每小时补排而晚一小时发送。

本期完成条件是本机贯穿验收与可复现部署说明；不把线上发布列为隐含授权。线上开启单租户摘要和延迟监测需 owner 当次授权，默认均关闭；Langfuse 始终只在本机。

## 验收标准

1. **逐角色权限。** 用 owner/admin/supervisor/agent/viewer、共享试用 agent、匿名逐个请求抽检读写、草稿和趋势；按 R1 得到成功、401/403；跨租户 UUID 404。沙箱拒绝新能力，文件模式先权限再 503，停用会话不可读；无任意成员提权。
2. **评分与竞争。** 真实 trace 上评好/差，验证差评缺原因、好评带原因、自由文本/额外字段、无回复轮次均拒绝；刷新持久、筛选正确。两个并发相同 revision 不丢更新，冲突 409；审计写失败时评分不提交；对话字节与 updated_at 不变。
3. **数据库隔离与删除。** 一次性 `pgvector/pgvector:pg17`，用实际 app/platform 角色验证四表 FORCE RLS、复合外键和无任意 DELETE 权限；交错两个租户后只见本租户。分别跑 trace 到期、purge_conversation、eraseConversation、15 手动重置与 sandbox_tenant_purge，评分与缓存无残留，不伤另一租户；7 天边界和 seed 例外有断言。
4. **安全导出。** 合成夹具故意填入姓名、电话、地址、工具结果和可识别标记（全部假值），下载文件和审计中都找不到原字段；伪造 seed 标记也不能自动导出正文。原样草稿交给 v2 schema 必须失败；未选差评拒绝。工业走新入口，travel 旧 goal-draft 的既有契约及测试保持。
