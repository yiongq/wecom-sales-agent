**一句话：** 现在的回答「能用但不稳」。价格算术一处没错，转人工 8/8 命中；毛病出在三处：话术和代码模板自相矛盾，上下文里缺订单、付款、已提醒这些状态，出口不查长度、重复和越权说法。比这三处更要紧的是回答质量没有评测，问题要等 owner 真机看到才发现。

本 spec 分四步：

1. **先建评测地基。** 用真实模型跑一组带状态的多轮回归集，比较 pass^k，每次跑都有预算上限。
2. **第一批改代码层。** 补状态注入和发送前检查；不动锁定节，不改前缀哈希。
3. **第二批改话术。** 请 owner 定口径，然后一次改完。
4. **最后加一致性检查。** 防止话术、工具提示、代码模板以后再互相打架。

owner 最在意的「先说旺季上浮 10%、又说起价按行程微调」（F）分两批修：

- **第一批**只改代码里不锁定的兜底模板，不再写这句。审查里 35/46 个报价轮的「微调」，大多是模型自己按 SOP 写的，这一批不碰。原因是锁定的自测按原样断言了这些回复。
- **第二批**删掉 SOP 里要求写这句的那条规定，模型就不会再被要求写；出口再兜底删掉报价轮里「按最终行程微调」那半句。这样不用动锁定断言。
- **彻底修好**要同时删掉报价轮里的「这是起价」，以及非报价轮里的「微调」。这要 owner 授权改 3 条锁定断言（见「需 owner 授权的锁定断言」）。不授权的话，F 只能部分消失，剩多少以第二批的 k=5 回归为准。

## 背景与问题

### 审查怎么做的

2026-10-15 做了一次回复质量审查，报告由协调者另存，不进仓库。44 个模拟客户场景用线上模型 `glm-5.3-flashx` 各跑 2 遍，共 88 段、244 条回复，费用 ¥2.99（销售 ¥1.96，客户模型 ¥1.02）。对照组 `glm-5.2` 跑了 47 段，用完了 ¥5 的预算。评测脚本自带的判分不可信：88 段里判失败 61 段，其中大量是谓词误伤。下面的结论以人工通读对话为准，并且每条都经过一轮对抗核实，被推翻或夸大的已经剔除或降级。转录数据在主仓库检出目录的 `var/quality-audit/report.json` 与 `report-glm52.json`，场景生成器是同目录的 `gen.mjs`。这个目录被 git 忽略，worktree 里没有，开工时要复制到 worktree 的同一路径，不进提交。

做得好的部分：两组共 76 轮报价，金额没有一处算错；库外目的地多数诚实说「没有」；退改、资质多数说「由顾问确认」；转人工触发 8/8 准；违法需求、注入、闲聊都能拒绝并拉回正题。

### 和业界的差距：方向没偏，落点落后

业界的共识是「确定的交给代码，措辞交给模型」，Salesforce Agent Script、Intercom Procedures、Decagon AOP 都是这样（厂商自述，没有独立基准）。我们已经在做，有价格护栏、预取、转人工精确规则优先，但只做到了「事后改写」。还缺三样：

- **状态注入。** 订单、付款、已提醒项由代码维护，每轮放进上下文。依据：多轮对话平均掉分 39%（Laban 等）。
- **关键信息走成句模板。** 价格由数据渲染，模型只写前后的话。
- **发送前检查，加一次有时间预算的重写。** 规则能判的就用代码判。

最大的偏离是回答质量没有评测闭环。业界的做法是：从 20–50 条真实失败建回归集，用 pass^k 衡量稳定性（τ-bench），再做线上抽检回流。我们防退化靠锁定短语和提示词前缀哈希，改一句话术就很重；护栏只会事后删句子，越补越复杂。本 spec 先补评测地基和代码层，抽检回流、发布前试跑等放到「后续」。

## 目标

1. owner 看到的问题在回归集上消失或大幅下降：报价轮里「微调」0 次；超长回复的占比降到前置离线回放给出的目标线以内；付款后与换线后不乱说；收尾一致。
2. 审查里的 blocker 和安全类问题（A、B、C、D，以及 E 的越权部分），在第二批之后的真实模型回归上 k=5 全过。
3. 回答质量有评测地基：带状态的真实模型回归集，有 pass^k，每次跑都有预算；每批改动都有前后对比。
4. 话术、工具提示、代码模板之间的矛盾由一致性检查拦住；从本 spec 起不再新增锁定短语。
5. 8 秒线不退化：超 8 秒的占比不升，整轮 p90 不超过前置测量定的上限。

## 原则

- 确定的交给代码，措辞交给模型。金额、订单、链接、转人工照旧只走确定性代码（AGENTS.md 硬规则），每个新护栏都带自测。
- **从本 spec 起不再新增锁定短语。** 新规则一律用回归集里的行为用例守。现有的 17 条契约短语和锁定套件照旧。
- 第一批不改 SOP、【硬性要求】、工具定义：前缀哈希不变，每轮的新状态只进 contextNote（独立的 system 消息）。
- 客户原文不出境：回归集、离线回放、重写模型实测只用合成数据或审查的模拟对话。
- 对客户的固定文字按三种情形渲染：旧版模式企微说「顾问会在微信上联系您」；网页渠道说「顾问会在这个页面里回复您」；模板模式非网页说「顾问会联系您」，不点名渠道，与 `contractRules` 在模板模式下的写法一致（04 R4）。

## 被否决的方案

- **直接上 Jev 或其他海外决策模型。** 原文会出境，没有中文，接口还是 alpha；而且它管不了 owner 看到的六件事里的四件。
- **只改话术、不改代码。** 「不超过 3 行」早就写在话术里，仍有 66% 超长；glm-5.2 同样有 19/30 轮写「微调」；状态缺失，话术怎么写都补不上。
- **一次性大改主提示。** 没有评测基线就大改，好坏都无从知道；锁定短语与锁定套件挡着；回滚粒度也太粗。
- **第一批就删模型写的「微调」，或把报价句换成模板。** 和 V1、s06、V2、V5、q4 的锁定断言硬冲突；改成等第二批 SOP 改完再兜底，再加上「需授权」那一节。
- **第一批补模型漏写的报价句（原稿的 `quote_line`）。** 补出的总价会让 `quoteShown` 认为客户看过这次报价，下一轮 `order_net` 就补「之前报的是…」，与锁定的 C07 冲突。要做，得先改 `quoteShown` 的判定（区分「工具报过」与「客户看到过」），并核 C07，放进以后的 spec。
- **把重写放在后置接管检查之后。** 执行器规定后置接管检查到写消息之间不 await，重写的 2–4 秒里顾问接管或客户付款，AI 回复照样会发出去。

- **把新词表并进 `dropUnbackedClaims`。** 锁定的 price-guard 自测逐字断言了它的输出，另起一步更安全，也更好查裁决。
- **D 类只靠出口词表。** 有限的模式拦不住模型的开放说法；先在上下文给口径，再拿词表兜底。
- **每轮都让模型自查重写、同步 supervisor、LLM 评审当门禁。** 前两个会破 8 秒线，最后一个在校准之前不可信。
- **把工具结果改成有状态的（提醒过就不带 `altitudeNote`）。** 锁定断言要求首轮带它；工具无状态也更好测。
- **把报价或订单金额放进上下文。** 模型会沿用旧金额，价格护栏也找不到出处。
- **不更新 v2 快照、或者关掉比对。** 那就失去了防漂移的能力；改成逐批具名快照、逐条审差异。
