# CI 并行分片

Status: draft
Supersedes in part: [00 · 基线与生产开关](../00-baseline/spec.md) — 「门禁」首句中 CI 只调用四个门禁名的限制；按 owner 的任务要求，CI 测试改用完整链的分片入口。

## 背景与目标

owner 已明确授权实现本任务：串行 CI 耗时过长，测试分为四片并行执行，required status check 仍叫 `check`。本文件记录任务中已定的架构，不增加业务范围；状态留待 owner 确认。

## 行为与不变量

- `package.json` 的 `test` 是唯一完整链，按 `&&` 切分，展开 `test:locked`。本机仍串行执行完整链，只增加分片器自测。
- 严格重跑列表由 `test-tenancy-strict.ts` 导出；无参数跑全部，`--suite <path>` 可重复指定子集，空、未知、重复目标都失败。每套的退出码、进程加载、缺作用域与白名单断言保持不变，汇总按实际子集计算。
- 唯一已确认的跨命令产物依赖是 console build → console dist 检查，必须合成连续执行的一个单元。其余命令只读源码 / 已提交数据，或自行创建临时状态与数据库夹具；严格重跑自行创建报告并启动进程。任何依赖规则缺失、重复或顺序不符均失败。
- 正常命令保留原文与环境前缀，严格列表每套变成一个单元。耗时按 `ci-weights.json` 中的秒数，未知为 10 秒；普通与严格分别使用同一套的估值。最长优先放入最轻的片，同权按完整链原序、同负载按片号打破平局。
- `tsx scripts/ci-shard.ts <i> <n>` 使用从 1 开始的片号，串行执行该片单元。命令交给 shell，打印每条命令的开始、结束与秒数，失败立即退出非零；单条命令超时为 15 分钟，超时或信号结束整个子进程组。
- `--check <n>` 独立按完整链构造覆盖清单，核对每个单元恰一次、原命令完全相同、依赖未拆、严格目标数与原列表相同，并打印每片分配及估时。
- CI `gates` 跑提交署名、原有 gitleaks、安装、format / lint / typecheck 与种子生成一致性；`test` 四片各有独立的原规格 PG service，安装后先检查再执行；`check` 使用 `always()` 汇总，仅当两项结果均为 success 时通过。超时分别 15 / 30 / 5 分钟，matrix fail-fast 为 false，不新增 action。
- 锁定八文件、自测断言、种子数据与业务代码不变；不访问网络、GitHub 或服务器，不提交。

## 验收

1. format、lint、typecheck、locked、分片器自测、`--check 4` 通过。按任务要求本机不跑完整 `pnpm test`。
2. 自测覆盖漏项、多项、拆依赖、片数变化、严格空子集、命令失败停止与环境前缀传递。
3. 逐项记录原 94 条命令的依赖核对依据；打印四片的分配与估时。
4. 从实际分片抽取只用 PGlite 的单元，调用同一执行器验证通过；不连接已有数据库容器。
5. 种子重新生成与 fixture 逐字节一致；workflow 的汇总对失败、取消、跳过都返回失败。
6. 本 PR 上的真实 CI：`gates` 与四片都通过，`check` 通过；从第一个 job 开始到 `check` 结束的墙钟时间不超过 20 分钟（改前约 35–50 分钟），实测值与各片用时记进 `plan.md`。
