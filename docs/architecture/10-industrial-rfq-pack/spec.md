**一句话：** 用 08 的通用形状与 09 的报价审批，做第二个真实行业包「工业品询价」，并在同一部署里开一个演示租户。客户在企业微信或网页里发来型号和数量，常常一次十几行、写法五花八门。AI 先把型号归一，在产品库里找到条目，按阶梯价和起订量试算，说清现货与交期；客户要正式报价时，AI 起草报价单，顾问批准后，系统把报价单链接发给客户。非标、来图加工、账期、样品、超长询价转人工。价格只由代码算；库存、交期、替代只说工具查到的；型号只说产品库里有的。数据全部是合成的。

## 背景与问题

- 08 与 09 给出了通用形状与报价审批，但只有证明包在用，没有真实的第二个包。主参考说过：第二个真实行业包跑通之前，「通用」只是设计主张。
- 询价场景和定制游差别很大，正好检验模板的边界：
  - 单价低、带小数，按数量分档，有起订量；
  - 一次询多行，型号写法不统一（`6205-2RS`、`6205 2rs`、`6205RS`）；
  - 库存和交期每天在变；
  - 有一部分需求系统兑现不了：非标、来图加工、账期、样品。
- 旅游的 `HandoffVocab` 有 104 个键，其中不少是旅游语义（高反、行程变更等）。
- 演示租户会让部署从「一个 standard 租户」变成「两个」。这时公开路由改为严格按 Host 匹配：每个租户都要有 `public_host`，宿主的 `PUBLIC_BASE_URL` 要与它一致（`src/tenancy/hosts.ts:30-45、65-71`）。

## 目标

1. **工业品询价包 `industrial`。** 公开参考包，用合成数据。内容包括：
   - 产品种类 `part`，可用 CSV 导入；
   - 型号归一与匹配；
   - 确定性定价；
   - 四个工具；
   - 护栏：库存与交期、替代、税票、价格承诺、型号、金额；
   - 确定性转人工与客户确认；
   - SOP、policy、品牌、词表、跟进、洞察、mock、后台配置。
2. **演示租户 `industrial-demo`。** 同一部署里另开一个，用自己的域名和网页渠道，有约 40 条合成产品。
3. **评测。** 工业包的模拟客户目标进发布闸；cases v2 回归随 `pnpm test` 跑。
4. **旅游不变。**

## 非目标

- 外部业务系统连接器（11，第一家 Odoo）：本 spec 的库存与交期由商家在产品库里维护。
- 客户发来的图片与文件（12）：本 spec 只处理文字消息，包括一次粘贴多行。
- 体验页 `/try` 的工业包模板（沙箱多模板）。
- 开发票、合同、物流跟踪；多币种；英文。
- 仓库里放任何真实厂商的手册、价格或品牌（ADR-003）。

### 工具定义（摘要）

```ts
find_parts({ query: string; category?: string }) →
  { match: 'exact' | 'ambiguous' | 'none';
    parts: { code; partNo; name; unit; specs: string[]; moq; tiers: { minQty; unitPrice }[];
             stock: '现货' | '部分现货' | '无现货'; leadDays; substitutes: string[] }[] }

quote_items({ items: { query: string; qty: number }[] }) →   // 最多 30 行
  | { error: 'too_many_lines'; limit: 30 }
  | { lines: { query; qty; match; code?; partNo?; unitPrice?; amount?; delivery?;
               note?: 'below_moq' | 'ambiguous' | 'none' | 'over_max'; moq?; candidates?: string[] }[];
      total?: number; unmatched: number }

create_quote_sheet({ items: { code: string; qty: number }[] }) →
  { state: 'pending' } | { state: 'approved'; quoteUrl: string; totalText: string } | { rejected: { code; reason: 'below_moq'; moq }[] }
```

工具结果里的金额以元计（两位小数），方便模型读；声明给 `amounts` 的是对应的整数分。

### 评测目标（R15，至少覆盖）

- 精确型号、别名写法、同系列多个候选（必须让客户选）；
- 档位边界（恰好等于档位数量、差一件）；低于起订量；库存三种情况；
- 一次 12 行的询价（回复不超过 12 行，提出出报价单）；31 行的询价转人工；
- 库外型号不编、不报价；回复里的规格写法（`25mm`、`IP65`、`G1/4`）不被误删；
- 砍价不改价、不承诺；要「最低价」承诺；
- 税票问法；替代型号（有替代 / 没有替代）；
- 非标、来图、账期、样品转人工，`kind: 'pack'`；
- 要正式报价单：回复里只有待审的固定句，没有链接；
- 待审时客户确认；批准后客户确认；过期后客户确认（重新试算）；
- 注入尝试；要求「今天一定发货」。

## 不变量

1. 旅游租户照 08 不变量 1–4、09 不变量 1，全部不变。
2. 工业包回复里的每个金额都有出处（08 不变量 9）；没有工具结果支持的库存、交期、替代说法，不会原样发出。
3. 低于起订量的行没有价格，也进不了报价单。
4. 报价单的单价只来自 `priceLine`；`create_quote_sheet` 的入参没有金额。
5. 一条工业包的 AI 回复（经过 `rfq_trim` 之后），不超过 12 行、600 个非空白字符。
6. `industrial` 租户的锁定节、【硬性要求】与固定句里，没有这些旅游词：线路、出行、出发、行程、旅行、酒店、目的地；也不点名渠道。
7. 已上架的条目里，归一后的型号与别名在本租户内唯一；已上架条目的替代型号都指向已上架的条目。
8. 加了演示租户之后，现网的旅游公开地址按 Host 仍命中旅游租户。

## 安全、隐私与性能

- **钱与承诺**：单价只由 `priceLine` 算；库存与交期只说工具查到的；正式报价要人审（09）。
- **数据**：全部合成；仓库里不放任何真实厂商资料。
- **隐私**：画像的公司名称与交货城市按 08 R4 进模型，昵称与头像不进。
- **性能**：`quote_items` 一次最多 30 行，匹配在进程内用已装载的快照完成，不查库；本机、40 条产品库时，单次调用 p95 不超过 50 ms。
- **滥用**：演示租户网页渠道的硬闸是渠道账号的 `dailyTurns` 与每 IP 限流；05 的按租户预算只记账、告警（R16）。

## 验收标准

1. **旅游不变。** 照 08 验收 1、09 验收 1。
2. **产品库。** 演示租户：
   - CSV 导入 40 条，成为草稿，上架后列表与详情显示两位小数的单价与各档；
   - 档位不递增、第 2 档数量不大于起订量、同一档只填了一半：console 的上架前检查当场列出违反项，服务端以 422 点名字段；`itemRules` 的自测核对 `checkItem` 与 schema 的结论一致；
   - 草稿里替代型号找不到、型号与别人重复，照样能保存；上架时以 422 点名字段；把一条被别人列为替代型号的已上架条目改回草稿，以 422 点名引用方；
   - 改了单价，写新版本，之后的试算按新价，已批准的报价单不变。
3. **匹配。** 自测覆盖 R3 的每条规则：`6205 2rs` 精确命中 `6205-2RS`；`6205` 返回同系列候选，排序符合 R3；`M8x30`、`M8*30`、`M8×30` 归一后相同；不足 4 位的前缀不算同系列；按名称问（「25 内径的深沟球轴承」）时走知识库召回，命中对应条目；库里没有的型号返回 `none`。
4. **定价。** `priceLine` 的自测覆盖各档边界、起订量边界、库存三种情况；mock 对话里，`quote_items` 的逐行单价、行金额、合计与自测一致；低于起订量的那行没有价格，建报价单时被拒并说明起订量。
5. **护栏。** 每条规则都有正例与反例自测；mock 对话分别触发「编造现货」「编造替代」「编造型号」「不含税说成含税」「全网最低」，各自被删或被换，`guard_events` 有记录；规格写法不被误删；问句与条件句不动；15 行询价的回复经 `rfq_trim` 之后只列 10 行，末尾是「另外 5 行已算好」的固定句，全文不超过 12 行、600 个非空白字符。
6. **确定性回复与词表。** 「非标」「来图加工」「月结」「要样品」「31 行询价」各触发一次 `kind: 'pack'` 的转人工；两条各 20 行的消息不触发；R11 确认报价的四种情况（含「已批准之后又试算了一次」），分别符合判定表。104 个键的处理表在 plan 里，每个「置为不匹配」的键都有一条原本会命中的旅游句子作为反例自测，每个「工业改写」的键都有正例自测。

8. **跟进与会话状态。** 「报价」阶段空闲 24 小时：没有待审报价单时发提醒，有待审时不发；「促成」阶段空闲 24 小时发提醒；用注入的时钟验证。`resetSession` 之后，`packState` 的四项都被清掉；`packState` 序列化超过 8 KB 时，按最旧的先删 `partsInPlay` 里的项，直到不超过。
9. **评测与闸。** 工业包的 cases v2 在 mock 下全过（文件配置与 PGlite 配置两种）。20 个 regression 目标真实模型 k = 5：每个 `safety` 目标 5 遍至少过 4 遍，pass^5 不低于 14/20；不达标就记进 Open，由 owner 定。演示租户在后台改一个可编辑节，经闸发布成功。旅游闸的目标集与缓存键不变。
10. **演示。** 开通前检查在预发环境全过；上线之后，网页渠道完整走一遍「询价 → 出报价单 → 工作台批准 → 收到报价单 → 确认」；旅游的公开地址与 `/healthz` 的哈希不变。
11. **回滚。** 有 `industrial-demo` 时部署 08 或 09 的 tag，检查脚本以 9 拒绝，处理步骤里有停用这个租户。

## 开放问题

1. **第二个公开参考包从「电商售后」改成「工业品询价」。** 推荐改：工业品询价仍是销售形态，能复用旅游已经验证过的阶段、报价、转人工；同时它用到了 08 新加的全部通用形状，最能检验模板。电商售后是工单形态，按主参考设计为英文、多币种，要先泛化币种，放后面更合适。白名单里保留 `ecommerce-aftersales`。owner 定了之后，写 ADR-005，并改主参考的拍板表。
2. **虚构品牌名。** 推荐「衡石工业品」，开工前由 owner 查重；与旅游 demo「云途定制旅行」一样，标注虚构。
3. **报价审批的缺省。** 推荐 `autoApproveMaxFen = 0`，即全部人审；商家可以在 policy 里打开「小额、全现货、全精确匹配」的自动批准。
4. **阶梯价用扁平字段还是子项。** 推荐扁平、最多 4 档（R2）：CSV 能直接导入，模型读起来直观。用子项要先扩展 CSV 导入，收益不大。
5. **演示租户接不接企微客服账号。** 推荐先只用网页渠道；owner 在自己的企业微信里另开一个客服账号之后，用 `channel-account add-wecom` 接上，不改代码。
6. **演示租户网页渠道的用量闸。** 推荐渠道账号的 `dailyTurns` 设成与旅游访客每日上限同一个量级（今天旅游 demo 是每天 500 次模型调用），每 IP 限流用现有的缺省值；owner 按费用定。

## 被否决的方案

- **条目编号从型号推导。** `6205-2RS/C3` 与 `6205 2RS C3` 推出来是同一个编号，会撞号。改由商家给编号，型号另做唯一性检查。
- **阶梯价存子项。** 见开放问题 4。
- **型号护栏用「字母数字混合就算型号」的宽规则。** 会把 `25mm`、`IP65`、`G1/4` 这类规格写法一起删掉。改为排除规格与单位的写法，并把在场条目的规格词算作已知。
- **「过期后确认」走确定性回复。** 确定性回复做完就结束这一轮，没法接着试算。改为给模型写一条上下文说明，由它调 `quote_items`。
- **在仓库里放真实厂商的手册与价格。** 有版权问题，也违反 ADR-003。真实材料留给 12，只在本地处理，不入库。
