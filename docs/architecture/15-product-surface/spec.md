## 目标

1. `www` 能解释产品、展示合成演示、通往后台与文档；`docs` 能指导管理员完成首次配置。
2. 后台新增「设置」一栏，覆盖组织信息、成员与角色、渠道绑定、用量；上手清单引到真实可完成的操作。
3. 登录页以「使用演示账号登录」收口，停止从产品入口一键创建临时租户；演示数据定期恢复到合成基线，既有演示硬规则仍可验证。
4. 平台品牌统一为「单来」，保留租户自己的组织名、客户页面品牌、行业包与 MIT 核心。
5. 形成 11、14、15 的联合切换与回退步骤，由 owner 当次授权后上线。

## 非目标

- 定价、客户案例及相关素材：另记；若上线，内容与组装放仓库外的私有运营层，公开 core 不依赖私有代码。
- 自动收款、租户开通、套餐购买、跨租户运营后台、统一 SaaS 身份平台；本期不把人工开通伪装成自助注册。
- 重做后台视觉、迁移前端组件库、改模型、提示词、价格或订单护栏。
- 网页渠道在 prod 解禁、ERP 设置界面、企微个人好友自动聊天、邮箱服务接入。
- 改写历史 MIT 版本，或让「单来」替换合成行业包内的商家名称。
- 本次起草不写代码、不改其他文件、不提交、不 push、不操作服务器。

## 现状与方案

### R1 · 入口、部署与公开边界

只有下列子域职责进入公开文档，完整地址通过私有发布配置注入；文中一律称产品域名（另记）。

| 子域   | 用途                                                 | 会话与运行位置                                                                      |
| ------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `www`  | 官网：首页、能力、文档入口、隐私政策、服务条款、页脚 | 静态产物，不接成员 cookie、不调租户 API                                             |
| `app`  | 正式后台入口，保留 `/console/` 路由                  | 现有 Node 服务，经 Caddy；初期 Host 对应一个明确的 standard 租户，开放问题 6 定映射 |
| `docs` | 面向使用者的六类文档                                 | 独立静态产物，不发布 spec、plan 与内部运维记录                                      |
| `demo` | 专用合成演示与演示账号入口                           | 与正式环境隔离，不能借共享账号访问现有真实微信会话                                  |

通用前端、文档模板、设置接口与可复用的演示边界代码留公开仓库；部署覆盖、域名映射、实际运营者信息、演示账号配置与定时重置的部署编排另记。公开构建允许占位配置，正式发布检查拒绝缺少必要链接或法律文本的产物，不把未填值展示给访客。

**托管比较（开放问题 4）。** 两种都只承载 `www`、`docs` 的静态产物，`app` 与 `demo` 的动态服务仍在现有服务器。

| 选项                   | 成本与适用点                                                                                       | 回退                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 现有 Caddy（推荐首批） | 已有发布路径，多两个按 Host 分开的静态根目录；证书、可用性与服务器一起维护，静态站与应用共享故障域 | 保留构建目录与上一版本，改静态根即可回退；以后同一产物可迁移 |
| Cloudflare Pages       | 多一套项目、域名绑定和发布配置；静态站可独立发布，与应用进程解耦；实际访问效果要从目标网络实测     | 保留同样的 URL 结构，改 DNS 与发布目标；需处理缓存和证书切换 |

依据：Pages 支持自定义子域 CNAME，但须先绑定项目，不能只改 DNS；静态重定向使用 `_redirects`。Caddy 可用 `file_server` 配静态根并自动管理 HTTPS。以上是厂商能力，推荐 Caddy 是基于现有部署的工程判断，不作地区速度或可用性承诺。[Pages 自定义域名](https://developers.cloudflare.com/pages/configuration/custom-domains/)、[重定向](https://developers.cloudflare.com/pages/configuration/redirects/)、[Caddy 静态服务](https://caddyserver.com/docs/caddyfile/directives/file_server)、[HTTPS](https://caddyserver.com/docs/automatic-https)。

静态根只能指向构建产物，不指仓库根，不带符号链接逃逸路径。`app`、`demo` API 与 HTML 沿用 `no-store` 和 CSP；不加跨子域 cookie，不开放跨源租户 API。兄弟子域也不能绕过现有同源检查。

### R2 · 官网

拟新增独立的静态站源码目录 `site/`，不把官网塞入现有 `public/` 的客户业务页面。首页依次是「单来」字标、一句话能力说明、可验证的产品画面、工作流程、进入演示与文档的入口；能力页仅展示已经交付的接待、产品库、话术、人审报价、人工接手及用量能力。11 的实时库存只有联合发布验证后才标为可用，并注明需管理员配置。

固定页面为 `/`、`/product/`、`/privacy/`、`/terms/`；页脚提供文档、后台、演示、隐私、条款、开源入口和品牌说明。截图只用合成数据，不带真实会话、二维码、凭据与部署地址；不使用占位客户标识、效果数字或未获许可资产。

隐私与条款有版本、生效时间、适用服务范围和联系渠道。模板须覆盖处理的数据类别、AI 服务商处理、保留和删除、备份副本、用户请求入口、演示使用范围与限制；实际运营者与具体运营信息由 owner 在仓库外维护并审定，不能编造。现有会话隐私告知与同意记录保持独立，官网政策不能替代它；未定正文不得作为正式服务条款上线（开放问题 9）。

静态正文与导航不依赖登录或 API；脚本未加载时仍能读正文和跟随链接。图片缺失显示文字说明，错误链接有 404 与回首页入口；不设置假咨询表单。移动端、键盘与读屏可用，公开页面可索引，后台及演示不索引。

| 快速开始     | 从 `console-access.md`、`how-it-works.md` 抽取使用者路径；与 `local-dev.md` 的开发者安装区分，说明正式账号如何取得 |
| 绑定企业微信 | 修订复用 `wecom.md`，补设置中心提交、待应用、回调验证及故障排查；env/CLI 接法留独立段落                            |

构建必须使用明确文件及章节白名单；先生成只含批准内容的临时源目录，再交给文档生成器。只藏侧栏不算隔离：HTML、搜索索引、源码映射、资源复制与站点地图都不得包含 `docs/architecture/`、`docs/features/`、spec、plan、ADR、部署手册或私有内容。已有指南连到 spec 的链接改成使用说明，开发者资料可单独链接公开仓库，不把整个 docs 树发布为用户站。

源指南变更后构建得到新内容；站内链接与锚点检查失败应挡构建。空搜索给「没有找到」与清除入口；搜索加载失败给重试与目录；页面正文不受搜索故障影响。空更新日志只说尚无公开发布记录，不造日期。

### R4 · 设置外壳、权限与共享接口

侧栏新增「设置」，下面用页签分组织、成员、渠道、用量；拟新增路由 `/console/settings/organization`、`/members`、`/channels`、`/usage`，后三者均在 `/console/settings` 下。默认打开组织页，深链接刷新可恢复。沿用风格 A、主题、字体、`StateView`、错误映射、未保存保护与路由懒加载，不重做外壳。

首批推荐 owner/admin 能进入设置，其他成员不显示入口、直接访问返回无权提示；匿名、沙箱与公开演示账号无设置权限。服务端独立校验，不能靠隐藏按钮。具体权限如下：

| 操作                                               | owner               | admin                                | supervisor / agent / viewer |
| -------------------------------------------------- | ------------------- | ------------------------------------ | --------------------------- |
| 组织信息、成员名单、渠道状态、14 用量读取          | 允许                | 允许                                 | 禁止                        |
| 邀请、改角色、移除成员                             | 可管理 admin 及以下 | 只能管理 supervisor / agent / viewer | 禁止                        |
| owner 转让、变更 owner、全局停用账号、代改他人密码 | 平台命令行          | 禁止                                 | 禁止                        |
| 新增渠道或更换凭据的申请、撤销未应用申请           | 允许                | 允许                                 | 禁止                        |
| 应用渠道变更、Host、额度、tenant 状态与密钥环      | 平台运维            | 禁止                                 | 禁止                        |

所有新增设置接口放 `/api/console/settings/*`；用量例外，原样调用 14 的 `/api/console/usage`。响应复用现有 `{ error, detail? }` 错误形状；匿名普通设置为 401、越权为 403、租户外目标为 404、版本冲突为 409、字段校验为 422、依赖不可用为 503。14 的匿名/沙箱 403 语义不被此规则覆盖。

Host 先确定租户，服务端从有效会话派生身份与租户，不接受请求里的 tenantId/slug 作授权依据。写请求沿用 JSON、Origin 与 `x-csrf`；输入采用严格白名单，拒绝多余字段。邀请领取与演示登录是单独列出的未登录入口，只豁免尚无会话时的 CSRF token，仍要求 JSON、同源与限流，不放宽全部 `guardWrites`。新增审计与业务写入同事务，字段级审计不含密码、令牌或渠道输入值。

共享契约放 `src/shared/console-api.ts` 或由它导出的独立 settings 类型；所有工作分支先依赖同一份已合入的契约。URL 中成员参数一律是 `userId`，渠道参数一律是 `accountId`，申请一律是 `requestId`；渠道 `key` 只用于稳定路由，不把邮箱、key 与 UUID 混用。

### R5 · 组织信息

推荐首批只读：组织名、组织标识、行业包、当前品牌与状态；链接到成员、渠道和用量，不展示数据库角色、内部连接串。来源是当前租户的权威配置；展示业务品牌时区分已发布值与待生效值，不能把待生效的 `tenants.brand` 当线上品牌。平台「单来」与组织名分开。

拟新增 `GET /settings/organization`：`{ name, slug, packId, status, publishedBrandName, pendingBrandChange }`；状态使用现有租户枚举，`publishedBrandName: string | null`，`pendingBrandChange: boolean`。本阶段不新增组织资料表，不加随意联系字段、不把品牌变更直接注入运行中 SOP。

开放问题 5 若选择在线编辑组织或 AI 品牌，须在 ready 前补齐写接口、数据库授权、发布与回退契约；不能由实现者把 `tenant-brand` 偷包成保存接口。只读版本在页面说明组织信息变更由管理员联系平台处理。

### R6 · 没有邮件服务时的成员开通

推荐一次性邀请链接：owner/admin 输入邮箱、姓名与目标角色，服务器签发链接，由邀请人通过已有沟通渠道交给本人。界面明确「请复制后自行发送」，没有「邮件已发送」提示；首次 owner 继续由平台命令行建立。邀请链接不是邮箱所有权验证，邀请人负责确认接收人。

拟新增契约：

```ts
type ManagedRole = 'admin' | 'supervisor' | 'agent' | 'viewer';
interface MemberView {
  userId: string;
  displayName: string;
  email: string;
  role: 'owner' | ManagedRole;
  revision: string;
}
// GET /settings/members -> { items: MemberView[], invites: InviteView[] }
// POST /settings/invites { email, displayName, role: ManagedRole }
//   -> 201 { inviteId, inviteUrl, expiresAt }，原始令牌只在创建响应出现一次
// DELETE /settings/invites/:inviteId -> { ok: true }
// PATCH /settings/members/:userId { role: ManagedRole, revision }
// DELETE /settings/members/:userId { revision }
// POST /auth/invitations/accept { token, password }
//   -> { ok: true }，成功后走普通登录，不在链接中携带登录会话
```

`InviteView` 只有 inviteId、邮箱、显示名、角色、expiresAt 与 pending/accepted/revoked/expired 状态。已接受邀请不再次授予权限；重复创建对同租户同邮箱的旧待领邀请撤销并换新，不重复建成员。

1. 令牌为加密安全随机的 32 字节，数据库仅存 SHA-256；建议 24 小时到期（开放问题 2）。链接落在对应租户 Host 的 `/console/join#token=…`；浏览器读取片段后立即移除，只在内存暂存，以 JSON POST 领取，GET 无副作用。页面 `no-store`、`no-referrer`、无第三方资源；令牌不进日志、审计、trace、错误详情、本地存储与埋点。
2. 新增 `member_invitations`：tenant_id、id、token_hash、归一化邮箱、display_name、role、created_by、expires_at、accepted_at、revoked_at、created_at，FORCE RLS；只允许 standard 租户，禁止邀请 owner。过期后不能领，定期清理已结束记录遵循审计保留约定，不清除审计本身。
3. 新邮箱由受邀者选择密码，沿用 scrypt 与现有至少 10 字符规则；已有账号必须提交其现有密码或先在本 Host 有效登录并核对相同身份，邀请绝不重置已有密码、姓名或停用状态。页面统一说明两种情形，创建邀请不能探测全局账号是否存在。
4. 领取时原子锁定邀请行，复核到期、未撤销、租户未停用与邀请者当下权限；账号建立或身份核验、成员关系建立、邀请消费与审计作为可验证的单次操作，失败不消费邀请。并发领取只成功一次；已有成员不被邀请覆盖角色。密码哈希计算在事务外，提交时校验读取的旧哈希/状态未变，防并发改密。
5. app 仍无 users、memberships、auth_sessions 直接表权限。增加专用 `SECURITY DEFINER` 函数，由有效会话 token hash、目标租户及请求参数确定身份，检查角色与范围；固定 search_path、撤销 PUBLIC 执行权，不接受调用方自称 owner。匿名领取函数只在正确 Host/租户和有效邀请 hash 下工作，不返回全局用户资料。实现前在第 1 步定好函数签名与授权矩阵。
6. 禁止修改/移除自己，网页不能改任何 owner；剩余有效 owner 数在同租户串行事务中保护，平台命令行同时遵守最后 owner 约束。角色变化下个请求生效，移除成员撤销本租户会话；不影响其在其他租户的账号与会话。事件流沿用现有 60 秒内复核上限。
7. 创建、领取与无效 token 都有限流和有界状态；领取沿用登录级别的 IP 与账号失败限流，不因持有邀请无限尝试已有账号密码。新增内存状态登记状态清单。实际发链接由人操作，系统不自动对外发消息。

临时密码加首次强制改密、平台 CLI 人工开通是开放问题 2 的替代项；本草案未授权同时实现三套。

### R7 · 渠道绑定：网页提交，维护窗口应用

推荐第一批只开放企微账号新增、更换完整凭据和停用/启用申请，不增加在线热切换；web 渠道只显示既有状态，prod 封顶不变。页面步骤为「准备应用 → 填写配置 → 已保存待应用 → 平台应用 → 在企微验证回调 → 收到测试消息」。最后两步不能靠“数据库里有一行”勾完成。

拟新增 `GET /settings/channels`，每项包含 `accountId`、key、name、kind、配置状态、运行状态、是否已配置凭据、固定回调路径、revision 和最近申请摘要。只返回字段投影，不序列化 `ChannelAccountRow`；不返回密文、keyId、corpId、openKfId、appSecret、callbackToken、callbackAesKey 或其尾号。回调完整 URL 由已校验的当前 public base 拼出，仅供授权页面复制，不写日志或公开文档。

拟新增 `POST /settings/channel-requests`：新增为 `{ operation: 'create', key, name, corpId, openKfId, secrets }`；更新为 `{ operation: 'update', accountId, revision, name?, enabled?, secrets? }`，其中 secrets 是三项完整替换，不接受部分缺省覆盖。`DELETE /settings/channel-requests/:requestId` 只能撤销 pending。成功返回 202 与 `{ requestId, state: 'pending' }`，页面明确「已保存，应用后才能验证连接」。凭据输入用遮盖控件，无显示旧值、无复制旧值按钮；提交、取消、会话失效或失败后清空秘密字段，非秘密字段可保留。

**为何需要独立申请。** 现有运行时启动装载账号；直接改活动行会让内存、回调和新解密的值不一致。拟新增 `channel_change_requests` 保存 tenant_id、id、account_id、operation、base_revision、申请状态、申请人、时间与加密负载；FORCE RLS、standard 限定、每账号至多一个 pending。新账号提前分配 accountId，pending 新建还按租户与 key 唯一，重复提交返回冲突，不因重复生成 UUID 建两份申请。状态只有 pending/applied/cancelled/conflict，失败保持 pending 并返回不含原始输入的原因码。敏感输入一起用现有密钥环的 AES-256-GCM 密封，AAD 为独立的 `channel_change_requests:v1` 域、tenant_id 与申请行 id；应用时重新加密到既有 `channel_accounts:v1` 与 accountId。旧明文只在请求/应用内存短暂存在。密钥轮换须覆盖未结束申请，旧 key 在两类密文都迁完前不能移除。

拟新增受限 CLI `channel-apply --tenant <slug> --request <id>`，使用 agent_app 身份且必须取得现有租户独占锁；锁被占则拒绝，网页无重启按钮、不接 Docker socket。它复用既有字段验证、账号唯一性、不可变标识、默认前缀、导入状态与恢复哨兵规则，在一个事务里核对 base_revision、写渠道账号、标申请已应用、写审计。业务 revision 仅覆盖配置，不能用会随拉取变化的 cursor/updated_at 充当版本。重复应用幂等；过时申请标 conflict、CLI 非零退出，HTTP 修改冲突为 409，要求重新提交。失败不改活动账号、不把密文写到错误里。

已有 env 账号、已导出状态、未完成迁移/恢复等情况显示平台准备事项，不允许网页隐式执行 channel-import；首次无账号场景也须由离线应用入口正确建立标记与初始化状态，不丢旧 cursor。更换企业或客服标识只能建新账号，不能改原账号身份；停用代替删除，消息和审计继续保留。申请进入 applied/cancelled/conflict 后清空密文，保留不含输入值的结果元数据。

重启读取新账号，回调校验与收到入站消息分别提供真实状态；连接失败给可重试步骤，已应用不等于已连通。R12 的贯穿验收必须经过真实申请、CLI、启动装载、回调、入站与出站，不只测存储函数。若 owner 要即点即生效，开放问题 3 必须改写本节并补齐在途收发、token 缓存、cursor、失败恢复与回滚设计后再开工。

### R12 · 线上切换、贯穿验收与回退

不在本次起草执行。先在一次性本地环境完成下面流程，产品域名（另记）购买、解析、证书、Caddy 配置、企微后台与服务器操作均须 owner 在当次会话授权。

1. 联合发布前核对 11 的验收与未决事项、14 的迁移/接口与 15 的验收；构建同一候选 tag。保持 11 的发布范围：不擅自给线上租户配置 ERP 连接器。发布记录与实际地址映射存私有运维记录。
2. 建新 DNS 与证书，静态站先验证；Caddy 按 Host 分开路由，未知 Host 拒绝。保留业务服务 `/` → `/console/`，官网仅在 `www`。核对新旧 Host 对应的同一租户，不把旅游与工业租户合并成一个 `app`。
3. 备份并记下旧 public_host、`PUBLIC_BASE_URL`、入口/演示配置和代理配置；按既有 `tenant-host` 设置、协调重启，验证宿主二者一致且其他租户不串。`public_host` 只有一个值，不能声称数据库天然支持新旧别名。
4. 按开放问题 10 的窗口保留旧入口。浏览器 GET 导航先用临时重定向观察，稳定后转永久跳转，目标只从固定映射取，保留批准的路径与查询/片段，不接受任意 return URL。新 Host 的 `__Host-sid` 不共享，用户须重新登录。
5. 企微回调的 GET 验证与 POST 事件不依赖 301/302 跟随：过渡期旧回调由明确的代理映射转入同一租户处理链，再在企微后台换新回调并实测。必要的 Host 改写仅在受信反代的固定站点规则完成，外部不能通过自带转发头选租户。历史客户订单、报价、网页会话和沙箱微信链接逐类测试，带旧域凭据的 API 不能一刀切跨域跳转。
6. 新域走一次授权测试：回调验证、客户发消息、入站落库、回复与人工接手、客户链接打开、后台用量增长；核对 11 没有意外配置、14 的额度生效与演示隔离。真实凭据由 owner 本人录入，公开证据只记录成功/失败及脱敏结果。
7. 失败按反顺序恢复代理、Host/基地址、入口与回调配置、上一镜像/静态产物，再验证旧路径；不回滚数据库删除已写消息。邀请与渠道申请的新增表是加法迁移，旧镜像忽略，但回退前暂停签新邀请/提交新申请；已生效渠道仍按 03 规则启动，不能靠退镜像恢复旧凭据。联合回退先满足 11、14 的各自检查。

**贯穿用例（本机必须可重复）。** 从真实浏览器登录 owner，创建邀请并由第二个浏览器领取 → 登录为成员，核对两租户不串 → owner 提交渠道申请 → 停测试 app、真实 CLI 持锁应用 → 重启走真实配置装载 → 用本地假企微传输服务驱动真实验签回调与消息拉取 → 真实引擎/仓储/发送账本产出一条回复 → console 显示会话、渠道进度、上手清单与 14 用量。仅模型响应和外部企微 HTTP 使用替身，认证、设置 API、数据库、CLI、注册表、引擎与 UI 查询使用真实实现；刻意令 key 与 UUID 不同，避免 11 第 5、6 步那类两边假门面各自通过的问题。真实 PG 的权限部分使用当次新建的 `pgvector/pgvector:pg17` 容器。

## 不变量

1. 平台品牌替换不改变任何租户已发布 SOP 的系统前缀、四个哈希、价格与订单决定。
2. 普通设置写请求同时受 Host 租户、有效会话、角色、同源与 CSRF 检查；网页从不持有平台数据库权限。
3. 渠道明文、邀请原始令牌、密码不进入日志、审计 diff、trace、模型、缓存或持久化前端状态；渠道任何读接口均不回显凭据。
4. 每张新增租户表都有 tenant_id 与 FORCE RLS，新增状态有所有者，消息继续 append-only。
5. 成员邀请不能重置已有全局账号，不能提升邀请者权限、移除最后 owner 或影响另一租户。
6. 渠道保存只表示 pending；离线应用、运行时装载、连通验证和收到消息是不同事实。
7. 用量只来自 14 R9，null、0、403、401 和陈旧数据不被转换成虚假的正常状态。
8. 公开演示账号碰不到真实业务数据、真实收发凭据与设置写接口，重置只作用于指定合成环境。
9. demo 的四项硬规则继续可用，prod 的封顶不能被演示配置放宽。
10. 文档站构建及索引只含白名单用户文档；公开仓库不含产品域名、私有运营内容与真实素材。
11. 换域名不迁移租户身份、不清消息，不把微信回调或凭据接口当普通网页重定向。

## 验收标准

1. **公开入口**：未登录打开官网能读能力并走到文档、正式登录和演示；四个子域职责可区分，未知 Host 无法命中其他租户，404 可回首页；手机宽度可完整使用（人工浏览器）。
2. **文档范围**：六类文档都有可完成的步骤、有效链接；改白名单源指南后产物随之变化；遍历产物、搜索索引与 sitemap，找不到 spec/plan/部署材料，直接猜测相关路径为 404。
3. **品牌**：首帧及运行时标题、登录、关于、两份 README 的平台名一致；租户名与客户品牌仍正确；锁定文件 byte-identical、四个哈希无变化。
4. **角色与隔离**：按 R4 权限矩阵逐项验证读取/写入；匿名、普通成员、沙箱、演示账号与其他租户不能绕过 URL 取得设置；跨源、缺 CSRF、伪造 tenantId 拒绝。真实 PG 下 app 直读写登录表仍被拒绝。
5. **无邮件开通**：邀请人只得到一次链接，受邀者能领并登录；新账号设密码、已有账号证明身份后仅加关系；错误密码、过期、撤销、并发重复领取、邀请者被降权均不能意外建成员；账号存在性不从创建邀请接口泄漏。
6. **成员变更**：admin 不能操作 admin/owner；不能自移除与失去最后 owner；并发修改有确定结果；移除后该租户会话失效，其他租户不受影响，审计能定位操作者与角色变化。
7. **渠道秘密**：浏览器保存后输入清空，响应只含申请结果；检查数据库为租户与行绑定的密文；跨行/跨租户调换密文无法解密；日志、trace、审计、GET、错误响应均无输入秘密；缺密钥保存失败且无半条记录。
8. **渠道应用**：保存后旧账号继续按原配置工作；CLI 遇持锁拒绝，维护窗口应用成功后重启才读新值；重复应用不重复建账号、过时申请不覆盖新配置；回调错误显示未连通，真实测试消息到达后才完成引导。
9. **用量**：真实 14 接口返回后页面正确区分 null/0/正常/超限/无数据；一条实际回复使数字按 14 口径增加；不提供调额度入口；403、401 和刷新失败可观察且不显示假零值。
10. **新手与界面状态**：全新组织、仅有草稿、仅已保存渠道及完成配置四种场景的清单结果正确；R9 状态矩阵逐行走查加载、空与错误，明暗主题、窄屏、键盘可用，路由深链接刷新不丢页（人工浏览器）。
11. **演示入口**：产品登录页不再自动创建临时租户；演示登录 POST 可用且只发 demo 本源 cookie；prod/错误租户/错误角色拒绝；匿名只读、重置、种子保鲜、访客清理以及现有 sandbox 回收回归通过。旧链接按 owner 选项验证。
12. **演示重置**：注入时钟跨过重置窗口，旧会话失效、合成基线恢复；中途故障保持维护状态；生产标识/真实凭据配置时拒绝重置，正式数据与审计行数未变。公开账号无法写配置或对外发送。
13. **贯穿链路**：R12 的本机用例从 UI、邀请、渠道申请、真实 CLI 到回调、引擎、会话与 14 用量全部成功；打断其中一个共享字段的语义会导致用例失败，不能由两份 mock 各自证明通过。
14. **发布内容**：官网政策和条款已有 owner 审定版本，无空联系人或假运营主体；品牌授权说明与分发资产范围一致；未发布功能不当作上线事实（人工）。
15. **切换与回滚**：一次性环境先完整演练；owner 当次授权后真实新域验证 HTTPS、登录、回调、客户链接与一问一答，旧路径在窗口内工作；回退后旧 Host、回调、会话与静态站恢复，日志无重复发送迹象（live）。
16. **门禁与清理**：format、lint、typecheck、完整 test 全过；真实 PG 权限用例通过；新增 durable 自测并入既有 tsx 门禁、无新测试框架；没有残留临时容器、浏览器与后台进程。

## 开放问题

下列选项都未获批准。每项在 ready 前由 owner 按代价决定；上线窗口、法律文本与实际地址在发布前再确认。推荐只是起草基线，选其他项须先修订相应 R、验收及 plan，不能开工时自行补架构。

1. **演示账号开放到哪、旧沙箱怎么收？** A（推荐）专用隔离的只读合成演示，每日恢复，旧沙箱停新建、存量到期，开源能力保留；代价是不能试编辑、发布与设置。B 专用隔离可写演示，必须另定所有允许写操作、阻断真实出站和重置事务，开发与运维明显增加；不能开放当前真实微信租户。C 保留每人沙箱，只改文案；改动最小，但不满足“不再开临时租户”。A→B 可另加功能；B 一旦接入真实数据很难安全撤回，必须单独确认。此项同时决定是否部分取代 05 的旧否决与 AGENTS.md 如何保留演示行为。
2. **没有邮件怎么加成员？** A（推荐）一次性邀请，24 小时有效、手工转交；用户自己定密码，增加受限函数和邀请表。B 管理员设初始密码并首次强制改密，需增加受限登录状态，不能只多一个输入框。C 平台 CLI 开通、页面仅列表与改角色，最省工但管理员仍不能自行加人。A/B 回退到 C 容易，但须撤销未领邀请或临时登录状态；依据是 owner 是否接受链接转交与本期工作量。
3. **渠道保存多久生效？** A（推荐）网页提交加密申请、平台维护窗口离线应用；沿用已有恢复模型，代价是等待和一次重启。B 网页即时生效，需完整的账号热重载、在途屏障与失败回滚设计，不能只复用 CLI。A 日后可升级；B 出站状态已变化后难退。依据是首批是否接受平台协助，ready 前定。
4. **静态站托管与文档构建？** 托管 A（推荐）Caddy；B Pages。前者少一条发布链但共用服务器故障域，后者独立静态发布但多供应商配置，均可用相同产物迁移。文档 A（推荐）独立 VitePress 白名单构建；B 手写静态目录和搜索，依赖少但维护更多。迁移内容不难、主题和构建要重做；跨阶段选择定案后新增 ADR，本次不新增第三个文件。依据是现有发布维护成本与实测访问效果。
5. **组织信息是否可在线改？** A（推荐）首批只读，品牌仍走既有待生效与发布流程。B 只编辑组织显示名，要补受限写权限与运行时一致性。C 还编辑 AI 品牌，须复用 04/07 发布闸并验前缀，范围显著增加。A→B/C 容易；已发布品牌不能当普通资料直接撤回。依据是首批是否必须自行改名。
6. **`app` 当前承接什么组织？** A（推荐）本期指定一个正式租户的入口，其他现有租户保留各自 Host 映射，人工开通；统一 SaaS 登录另写 spec。B 本期做统一身份与选组织，必须重写 05 Host、会话与公开客户路由契约，增加隔离迁移成本。A 后续可迁移，B 错路由会触及用户数据且难退；依据是本期是否必须多组织共用同一入口。
7. **品牌标识怎么分发？** A（推荐）正式标识放私有素材，公开代码保留可换默认入口并声明名称/标识不在 MIT 授权内。B 标识随公开仓库，先明确单独资产许可和范围。A 维护两处构建配置，B 贡献者需理解两种资产边界；错误公开许可难以追溯收回，owner 单独确认，不影响现有 MIT 代码授权。
8. **仓库是否改名？** A（推荐）产品叫单来，仓库/包/镜像名保持；B 一并改名，要盘点 CI、clone、文档、镜像与集成引用。A 仅命名不同，B 成本较大且外部链接迁移不完全可控；可后做，依据是是否需要统一技术标识。
9. **官网法律文本怎么上线？** A（推荐）公开通用模板，owner 审定的服务专属正文在私有发布层组装，发布检查缺项即拒绝。B 公开固定服务正文，需要重新明确 ADR-003 下运营主体等信息的边界，不能在本草案填。A 多一份内容版本管理，B 内容修改会留公开历史；选择可以换，但已生效版本须留档，发布前由 owner 给出审定版本。
10. **旧地址兼容多久？** A（推荐）至少 30 天观察窗口，历史客户链接再按实际有效期延长，回调独立保留到新回调实测通过且旧请求归零；B 更长固定窗口，减少断链但多维护证书与代理；C 立即全跳转，回调和 cookie 风险不可接受。A/B 可延长；过早下线导致旧凭据与客户链接失效后难补，依据是旧链接有效期与脱敏访问统计，数值和地址另记。

## 与现有规则及其他 spec 的关系

- **05 与演示硬规则**：登录入口条款需要部分取代；共享可操作账号是旧否决，绝不能只改按钮上线。AGENTS.md 四项演示行为继续成立，不默认授权删除旧能力；若 owner 要改变硬规则，须另行明确修改后才能实施。
- **01、03**：成员页是 01 明列的后续；受限认证函数是增补，不能给 app 平台权限。渠道申请增补 03，离线应用沿用独占锁、标识不可变与恢复纪律；选热生效需新的部分取代设计。
- **后台 UX、04/07**：增加设置与上手清单、平台标题；风格 A 不动，租户品牌发布与哈希契约不动。品牌在线编辑若被选中，须补相应增补/取代范围。
- **14**：用量接口是依赖且尚未实现，15 不改 R9 权限、额度或状态；共享演示账号无权读取时如实显示边界。
- **ADR-003 与许可**：官网定价/客户案例内容、生产组装及真实运营信息另记；品牌声明不能缩减已经授出的 MIT 软件许可。私有品牌资产和公开 MIT 核心必须有清楚边界。
- **上线**：域名未购买不阻塞本地实现，但阻塞 live 验收与 implemented；11/14 未完成各自验收也阻塞联合上线。本次仅新建两份草案，旧文档与规则均未修改。

## 被否决的方案

- 把公网演示按钮接到现有真实微信租户的共享 admin：违背 05 已记录的安全判断，隔天重置解决不了泄漏和误发送。
- 只去掉 UI 的 `/try` 链接而保留公开自动创建路径：入口仍能直接调用，不能兑现收口。
- 在 HTTP handler 中运行平台 CLI、读取平台连接串或挂 Docker socket：把运维权限扩散给 app。
- 渠道写库后直接显示已连接：运行时仍是旧快照；回调验证与真实收发根本未发生。
- 回显渠道旧凭据、以星号表示但把原值放在 DOM/响应：明文仍已泄漏。
- 把 docs 整棵目录做站点、仅从菜单藏 spec：搜索与可猜 URL 仍能访问内部设计材料。
- 全仓替换商家名称、修改已发布 SOP 来显示「单来」：破坏行业包边界与前缀稳定性。
- 新旧域名所有请求一律 301：微信回调、cookie、订单访问与已有会话各有不同语义。
- 两边各写一个对得上的假 API 就宣称集成完成：11 的映射问题已经证明必须走真实链路。

## 分批

- **A 决定与契约**：owner 定开放问题、关联标注和必要 ADR；固定路由、DTO、认证函数、表结构与静态产物边界。
- **B 后端能力**：成员邀请、渠道申请与离线应用、组织与上手状态；可按边界并行，迁移和公共入口由一个整合者负责。
- **C 产品入口**：官网/文档、设置/引导、品牌/演示三路；共享文件串行收口，14 用量接真实接口。
- **D 验证与发布**：真实 PG、贯穿用例、浏览器状态验收、本机切换回退演练；owner 当次授权后与 11、14 一次上线，全部验收记录完再请求 implemented。
