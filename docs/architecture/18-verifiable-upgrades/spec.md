## 给你看的一页

**做什么：** 在不碰线上、不等真实客户的前提下，做四项能用仿真测出前后差别的改进，外加一次需要你手机配合的实测。

- **代码出数**：试算的单价、小计、合计、库存交期由代码渲染成「价格块」，模型正文只写一个占位符；旧金额护栏原样保留兜底。客户要价时一定拿得到价，数字不再靠事后删句保证。
- **仿真闭环**：仿真跑完，检测器自动标出疑似坏轮（要价没拿到、对的内容被删、内部 JSON 漏出等）；人确认后，一条命令生成永久回归用例，进 `pnpm test`。
- **主备切换**：可以多起一个备用进程等锁；主进程崩溃或发版时，备用进程自动接管。加 epoch 栅栏，保证任一时刻只有一个进程能认领消息和发消息。
- **企微去重实测**：你在手机上看同一条消息 msgid 重发几次收到几条，用结果关掉或确认 03 开放问题 4。
- **混合检索**：做一个 5000 条的合成产品库和带标注的查询集，先量现状，再上「属性过滤 + 关键词 + 向量 + 融合排序」，用召回率证明有用。

**怎样算做完：** 第 6 次留出集主跑（main）比第 5 次：客户要价没拿到 0 轮、金额删句减少、成功率不降（验收 1–6）；检测器能找回 11-02、11-03 人工读出的全部已知问题（验收 7–9）；在真实 Postgres 上杀主进程、滚动发版、掐断锁连接三种演练都不丢不重（验收 10–14）；企微实测有记录（验收 15）；检索评测报告给出现状和新方案的召回对比（验收 16–19）。

**代价与限制：** 真实模型与嵌入费用整份上限 ¥12（账本口径），每次运行你当次授权。主备只覆盖同一台服务器上的进程崩溃和发版，覆盖不了整机宕机、进程卡死。价格块让回复更像报价单、少一点口语感，要抽检。5000 条是合成数据，召回数字不能外推到真实商家。

**不做：** 多活多副本、Redis、消息队列、灰度和 A/B、向量入库、精排模型、把检测器接进后台。

**已定结论：** D1–D7 已于 2026-11-07 按 ★ 全部定为 A（owner 原话「都按推荐」）。

**要你定的：** 无。D1–D7、档位 heavy 与 `ready` 均已于 2026-11-07 定下；开工即调整 11-03 定的「功能收尾，只修 bug」。每次真实运行、服务器操作仍要当次授权。

## 目标

1. 试算轮的商品金额由代码渲染，客户要价一定拿得到价；模型正文不写商品金额。
2. 仿真跑完自动标出疑似坏轮，确认后一条命令变成永久回归用例。
3. 主进程崩溃或发版时备用进程自动接管；任一时刻只有一个进程能提交入站认领、出站发送标记和会话写入。
4. 用一次实测关掉或确认 03 开放问题 4。
5. 在 5000 条合成产品库上有检索评测，混合检索的召回可量化地好于现状。
6. 用第 6 次 main 给出 1、2、5 的前后数字。

## 非目标

- 不做多活多副本（每会话锁、fence read、拉取选主）、Redis、消息队列、灰度、A/B、向量入库与 HNSW、精排模型、向量降维和 `Float32Array`（5000 条约 80 MB，不是瓶颈；改精度会动旅游的检索顺序）。
- 不改旅游包、跟进消息、正式报价单卡片、审批与自动批准规则；8 个锁定文件与 `eval/cases.json` 逐字节不变；不改 16 的判分口径与目标。
- 不把检测器接进 17 的后台抽检（真实流量出现后另起 spec）。
- 不扩大演示产品库：40 条照旧，仿真场景依赖它。
- 不碰线上。Caddy 配置、企微实测、发版和换容器都要 owner 当次点名。

## 方案

### R1 · 代码出数：价格块

**占位符。** 工业包声明三个块，模型在正文里写占位符，代码在出口换成文字：

| 占位符         | 数据来源                                                | 渲染内容                                        | 没写占位时 |
| -------------- | ------------------------------------------------------- | ----------------------------------------------- | ---------- |
| `{{试算明细}}` | 本轮最后一次 `quote_items` 的结果（模型调的或预取的）   | 按可报价程度分三种模板，见下                    | 附在正文后 |
| `{{档位价}}`   | 本轮 `find_parts` 精确命中的条目                        | 「型号：1–19 件 X 元；20–99 件 Y 元……」，起订量 | 不附       |
| `{{应付金额}}` | 本轮 `acceptingOrderId` 指向的订单（#466 已有这个字段） | 「这份报价合计 X 元」                           | 附在正文后 |

**试算明细的三种模板。** 只用工具结果里已有的字段，渲染器不做算术：

| 情况                                                               | 渲染                                                                                            |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 全部可报价（工具返回了 `total`）                                   | 首行「试算：」；逐行「型号 × 数量：单价 X 元，小计 Y 元；现货 / 交期」；末行「合计 Z 元」       |
| 部分可报价（有未匹配、低于起订量、超过单次上限的行，没有 `total`） | 只列可报价的行，不写合计；另起一行「另有 N 行需确认：型号（未找到 / 起订量 M / 超过单次上限）」 |
| 全部不可报价                                                       | 不出现金额，只列每行的原因                                                                      |

- 首行标「试算」，与现有待审报价规则一致。没到最高档的行，行尾加「满 N 件 X 元」（D2，取工具结果新增的下一档字段）。数字统一两位小数加「元」。不出现 markdown。
- 库存与交期的写法沿用 `industrial_claims` 现在认可的说法，包括「以顾问确认为准」的附加条件；第 3 步对照 `src/packs/industrial/guards.ts` 定成渲染模板。
- 只有本轮确有数据才渲染。占位符没有数据、或不是这三个名字时，删掉占位符所在的句子；客户可见文本里不能出现 `{{`、`}}`。
- 同一个块在一条回复里只渲染一次，重复的占位符删掉。

**长度预算。** 回复整体上限沿用 `trimRfq` 的 12 行、600 字（去空白后计），块计入这个上限。块的明细行数按预算倒推：正文至少留 2 行，其余给块；放不下的明细行用 `trimNote(n)` 收尾，有合计时合计总要保留。`shape_check`、`rfq_trim` 按「正文 + 块」的总量判断形状和长度，但只改正文、不改块。trace 记录展开后最终文本的形状。

**什么时候不附块。** 新旗标 `turn.flags.blocksSuppressed`，按 `validate.ts` 的读写声明登记。只有「整段换成固定话术」的步骤写它：`quote_claim` 的改写、`industrial_claims` 里把整段换成固定句的分支（第 3 步对照 `guards.ts` 列全）、`money_provenance` 删空后用兜底句、`turn_failure` 转人工。局部纠正（如把「运费另计」改成「运费0元」）和普通裁剪也返回 `replace`，但不写这个旗标。读到旗标时不放任何块，占位符一并删掉。占位符被护栏随句删掉的，也不补回。

**正文规则。** 【硬性要求】加一句：「单价、小计、合计、应付金额只写占位符，由系统填写；正文不写商品金额。」`quote_items`、`find_parts` 的工具说明同步写明占位符用法，结果里加 `block` 字段提示可用的占位符。运费门槛这类政策常数照旧可以写在正文里，由现有护栏检查。这些都是代码持有的文本（`src/packs/industrial/sop.ts` 与工具定义），可改的 SOP 节不动。代码改动会改变渲染结果与工具哈希，沿用 01 的启动重新渲染流程（`causes`），第 0 步核实它对 db 租户怎么生效、要不要过发布闸。

**管线。** 分两步，都同步执行：

1. `reply_blocks:render` 排在 `stage_advance` 之后、`shape_check` 之前：按本轮工具结果和 `acceptingOrderId` 渲染出块的文本，把文本和行数、字数放进 context。
2. `reply_blocks:place` 排在 `rfq_trim` 之后、`takeover_check:post` 之前（后置接管检查到写消息之间不能有 `await`，06 R10）：读 `blocksSuppressed`，把块放进占位符或附在正文后。

中间的护栏看到的是占位符，不含金额，所以不会删价格块；块放进去之后不再经过删句护栏。`money_provenance` 原样保留，只管正文。

**核心与包的边界。** 核心只提供通用机制：包可选声明 `replyBlocks`，核心的两个 `reply_blocks` 步骤按名字渲染和替换。包没声明时不装这个步骤，旅游的步骤表与现在逐项相同。跟进消息没有工具调用，不装。

**记录。** trace 的 `turn.blocks` 记渲染了哪些块、放在原处还是附在后面、行数，以及正文里还剩多少处裸商品金额（模型没守规矩的次数）。

### R2 · 仿真闭环

```
journal ─► triage.ts（检测器）─► 疑似清单 ─► 人确认 ─► promote.ts ─► eval/cases-v2/q18-*.json ─► pnpm test
                                                    └► 修在提示词的：按目标 id 定向复跑开发集
```

**检测器**（`eval/sim/triage.ts`）跑在 journal 的每一轮上。和 16 的审计一样，不 import `src/packs`、`src/core/guards`，算价复用审计自己的 `oraclePrice`。

| 检测器              | 查什么                                                                                                                                   | 对应的已知问题          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `price_withheld`    | 本轮试算有可报价的行，或客户问价且本轮 `find_parts` 精确命中，但最终回复里没有对应型号的单价、小计或合计（运费、包邮门槛等政策金额不算） | 第 2 次 5 轮要价没拿到  |
| `correct_deleted`   | 护栏删掉的句子里，金额全部等于 oracle 的值，或交期、现货与产品库一致                                                                     | 第 2、5 次删对的内容    |
| `ask_after_accept`  | 本轮已记 `acceptedAt`，回复还要求客户再确认                                                                                              | 第 4 次 31 段           |
| `amount_not_order`  | 接受轮回复里的金额不等于被接受订单的合计                                                                                                 | 第 4 次付款金额说成旧单 |
| `internal_leak`     | 回复里有 JSON 片段、工具名、内部字段名或「询价摘要」                                                                                     | 第 5 次 JSON 进回复     |
| `choice_overridden` | 客户本轮或之前明确选了型号，回复被整条换成「查到多个候选」，或推回旧型号                                                                 | 第 5 次候选改写         |
| `dangling`          | 回复以冒号、标题、孤立序号结尾，或以「不过」「另外」开头                                                                                 | 第 4 次删句后残句       |
| `duplicate_text`    | 同一句兜底话术在一条回复里出现两次                                                                                                       | 第 4 次                 |

`price_withheld` 不算的情况：客户没给型号或数量、全部行不可报价、本轮转人工、本轮写了 `blocksSuppressed`。

**疑似清单与确认。** `triage.ts` 写 `candidates.json`：每条有稳定 id（`sha256(runId + goalId + 遍号 + 轮号 + 检测器)` 前 12 位）、检测器、所在轮和证据摘录。确认写进 `triage-review.json`：`confirmed` 或 `false_positive` 加一句理由。跑仿真的 agent 初裁，owner 抽看；误报率进报告。两份文件都含对话摘录，留在 `var/`，不入库（16 D5）；入库的只有计数和生成的用例。

**journal 补完整快照。** 现在 journal 每轮的状态快照只有订单、接管状态和阶段（`eval/sim/runtime.ts` 的 `snapshot`），重建不了这一轮之前的会话。16 的 journal 每轮新增 `sessionBefore`：销售这一轮开始前的完整会话（含 `packState`、`moneyLedger`、画像、失败窗口）、订单（含审批状态与时刻）。两边都是合成数据。这是 16 R6 journal 格式的新增字段，旧字段不变。第 1–5 次的旧 journal 没有这个字段：检测器照常跑（只用回复、trace 和订单快照），`promote.ts` 拒绝并提示「旧 journal 只能手写用例」。

**v2 夹具扩两个可选字段**：`fixtures.session.moneyLedger`，以及 `fixtures.orders[].approval`（`pending` / `approved`，带 `decidedAt`，写法照 10 R15 的模拟目标审批种子）。这取代 10 验收 9 的「v2 不新增审批种子字段」。原因：第 4 次查出的两类接受轮问题，不带审批状态复现不了。

**生成用例**（`eval/sim/promote.ts`）。对一条确认的疑似生成一个 v2 工业用例：

- 夹具取 `sessionBefore`；夹具订单按顺序重建，v2 worker 会重新生成订单 id 和创建时间，所以用例里引用订单一律用序号，`promote.ts` 把 journal 里的订单 id（含 `acceptingOrderId`）换成序号。
- 客户输入照抄；模型脚本只放这一轮模型自己的原稿和工具调用，预取（trace 里来源是代码的调用）由引擎照常重做，不写进脚本。工具照常执行，结果由代码重算。
- 断言按检测器生成，例如 `price_withheld` 断言回复含该行单价，`internal_leak` 断言不含 `{`。
- 必须通过 `validateCase`。用例在找到问题的提交上要失败，修复之后要通过（在隔离副本里验证）。

仿真对话两边都是合成的：产品库是虚构的，客户由模型按作者写的目标扮演。所以按 17 D1，人工核对没混入真实内容后，生成的用例可以公开入库。真实对话的差评仍走 17 的私有路径，两边不互相读取（16 R8 不变）。

**修在提示词或模型行为的问题**，mock 用例验证不了，要用真实模型复跑。已知问题所在的场景全在留出集（`split: holdout`），按 16 R5 不能当开发集跑。所以：找同一场景族的开发集场景定向复跑（`--kind dev`，每个 5 遍）；开发集没有覆盖的，新写开发集场景，不复制留出集场景。结果写进 plan，不计入「第 N 次」。复跑留出集场景只能作为下一次 main，要重新冻结、owner 授权。

**趋势。** 第 6 次报告加一张附表：按账本里跑完的 main（第 1、2、4、5、6 次；第 3 次开跑约 1 分钟后中止，列出不计），给出每个检测器的疑似数、确认数、每百轮确认数。旧的几次由检测器回溯 journal 得到，不花模型费用。

### R3 · 主备切换

**等锁启动。** 新环境变量 `TENANT_LOCK_WAIT=forever`；不设时启动和失锁行为与现在完全相同。设了以后，`holdTenantLocks` 每 500 毫秒以内重试一次，一直等到拿到全部租户锁；等锁期间不装载配置、不监听端口、不连企微、不跑任务，每 60 秒打一行日志；等锁时收到 SIGTERM 直接退出 0。拿到锁后照现有顺序：装载、启动恢复、开端口。

**epoch 栅栏。** 新表 `process_epochs`（每租户一行）。进程拿到租户锁后，在一个事务里把 epoch 加 1，记下自己的 epoch。下面三类写入，都在同一事务里先 `select epoch … for share` 比对，不等就回滚并报 `process_epoch_stale`：

1. 入站一页插入 `channel_inbox` 并推进 cursor；
2. 出站分段改成 `sending`（`markSending`）；
3. 会话、消息落库。

第 0 步列出这三类的全部写入点。

**发送前的检查。** 只栅栏 `markSending` 不够：标记提交之后、请求发出之前可能失去主身份；启动恢复补发的 `sending` 段（`alreadySending`）和同段重试根本不再经过 `markSending`（`src/adapters/wecom.ts`）。所以等锁模式下，每次发请求之前（含恢复补发、同段重试）都要满足：锁视图是 `held`、没收到过 `process_epoch_stale`；不经过 `markSending` 的路径在发之前补查一次 epoch。查完到发请求之间不 `await`，照现有接手代次的写法。

**过期不能降级成「库不可用」。** 现在 `markOutboundSending` 把各种异常都归成 `db_unavailable`，下游按 03 R6 照发。等锁模式下新增结果 `stale`，`stale` 一律不发，进程走优雅退出。03 R6 的照发只在锁视图是 `held` 时允许；锁丢了就不照发，因为别的进程可能已经是主。

**能保证到哪一步**：过期的进程开始不了新的发送；已经发出去的请求收不回。所以「只有一个进程在发」的残余窗口，是最后一次检查通过时正在路上的那一个请求。

**收到 `process_epoch_stale` 之后**：立即停止拉取和新开轮次，走现有的优雅退出。被拒绝的写入直接丢弃；那条入站由新主进程按 03 的启动恢复表处理。

**重取锁之后先核对 epoch。** 现在重取成功只把锁状态改回 `held`。等锁模式下，重取成功后先比对库里的 epoch：还是自己的，说明期间没别人拿过锁，恢复服务；变了，说明别的进程当过主，内存里的会话、订单、配置都可能过期，直接优雅退出，由 Docker 重启后作为备用进程等锁。

**共用的 `var/`**：两个容器继续挂同一个宿主 `var/`，恢复哨兵和渠道标记要两边看到同一份。规则：

- 等锁的进程拿到锁之前不读写 `var/`。
- 持锁时正常停机留下的 spill 照现在，由下一个拿锁的进程在开始收消息之前回放。
- 等锁模式下，`held_by_other` 或收到 `process_epoch_stale` 之后的停机，drain 不写 spill，直接丢弃并计数告警。这些是旧进程失去主身份之后的写入，回放会盖掉新主进程的数据。代价：旧进程最后几秒里已发出的回复可能不在会话历史里，与 03 R6 的例外同类，告警带条数。现有的「`held_by_other` 时 drain 直接 spill」只在不设 `TENANT_LOCK_WAIT` 时保留。
- 第 0 步核对 `var/` 里其余每类文件（`src/channels/markers.ts` 的标记等）都符合「只有持锁进程读写」，不符合的在第 7 步一起改。

**失锁即停收**（只在等锁模式下）：锁连接一断，就暂停拉取企微、暂停新开轮次、关闭 HTTP 监听（新连接被拒，Caddy 转到另一个上游）；在途的轮次照常走完，但每次写入和发送都过上面的检查。重取成功且 epoch 没变，就恢复并重新监听；`held_by_other` 或 epoch 变了，就优雅退出。不设 `TENANT_LOCK_WAIT` 时，失锁仍是「对话照常」。

为什么锁和栅栏都要：正常情况下锁保证只有一个主进程；锁连接断了而旧进程还活着时，新主进程已经拿到锁，旧进程要等下一次重取才知道，这段时间由栅栏和发送前检查拦住它。

**部署。** compose 增加 `app-standby` 服务（同一镜像、另一个宿主端口、同样的 `restart: unless-stopped`），两个服务都设 `TENANT_LOCK_WAIT=forever`。Caddy 把两个端口都列为上游，按顺序选第一个可连的，连接被拒时重试最长 15 秒（只重试连不上的请求，已送达的 POST 不重发）。Caddy 配置在服务器上，改动要 owner 授权；仓库里只写不含域名的配置片段和运维手册。`deploy.sh` 第 7 步改成滚动：

```
1. 迁移（只增不删，旧镜像可继续跑）
2. 用新镜像重建备用容器 → 它等锁
3. SIGTERM 主容器 → 停收、走完在途、落盘、放锁
4. 备用容器拿锁 → 装载 → 恢复 → 开端口 → 健康检查（revision 是新 tag）
5. 用新镜像重建原主容器 → 它成为新的备用
失败（第 4 步超时）：停掉新容器，用 :prev 起原主容器，同现在的回滚
```

巡检 `deploy/watch.sh` 现在只探 app 的固定宿主端口，接管之后那个端口变成等锁的备用、不监听，连续 3 分钟就会报健康故障。改为两个端口都探：恰好一个返回 `ok: true` 为正常，备用端口连不上是正常状态；都不通告警；两个都在服务也告警（不该出现）。

要求「先停应用」的命令行（`catalog-fix`、`channel-import` 等）在有备用进程时要两个都停，否则备用进程会接过锁；运维手册和这些命令的报错提示一起改。README 的「当前运行时仍要求单实例」改为「同一时刻只有一个活动实例，可加一个等锁的备用实例」。沙箱服务和平台命令行不变。

**覆盖不了的情况**（写进运维手册）：

- 整台服务器宕机。
- 进程卡死但连接还在：锁不释放，不会切换。
- 失去主身份时正在路上的那一个请求。
- Postgres 重启期间，主进程锁还在、按 03 R6 照发而结果没落库的段，新主进程可能再答一次。这与 03 R6 现有的例外同一类，有告警。

### R4 · 企微 msgid 去重实测

新命令行 `src/cli/wecom-dedup-probe.ts` 做成对实验：每个间隔 g 用一个新的 msgid，先发一次，隔 g 秒用同一个 msgid 再发一次；记录两次的实际时间差和接口返回码，不打印凭据和标识。g 缺省为 0 秒、2 秒、1 分钟、5 分钟、30 分钟（可配）。每个间隔独立一个 msgid，是为了不把「窗口从首次发送算起」和「被重发刷新」混在一起。接收人与账号在运行时传入，不进仓库。

- 前提：owner 在 48 小时内给这个客服发过消息（否则 48002）。凭据只在服务器上，所以要在服务器上跑，owner 当次授权。
- owner 在手机上看每一对是否多出一条。最长的「重发不多出」间隔记为去重窗口 W；证据不一致（同一间隔有时去重、有时不去重）就当作不去重。
- W 至少 1 分钟时，把常量 `RESEND_UNKNOWN` 换成窗口规则。启动恢复时，给 `sending` 的段算绝对截止时刻 `sentAt + W − 30 秒`：已过截止的照旧记 `unknown`；没过的按同一 msgid 补发，截止时刻交给发送层。发送层在每次请求和每次重试之前比对，等 token、退避期间过了截止就停，记 `unknown`。`OpenOutboundFacts` 已有 `sentAt` 和 `now`，判定仍是纯函数；发送层改动在 `src/adapters/wecom.ts` 的同段重试循环。
- 只要 0 秒或 2 秒的重发就多出一条，说明企微不按 msgid 去重，保持现状，记录结果。
- 结果写进本 spec 的 plan，并在 03 顶部加 `Amended by:` 指向这里。

### R5 · 混合检索

**评测集**（`eval/retrieval/`）：

- `gen-catalog.ts`：固定随机种子生成 5000 条合成条目，至少 8 个类目，规格沿用现有「键 + 数值 + 单位」写法（如「内径25mm」「螺纹M8」「线圈DC24V」），带别名、系列、相近型号。
- `gen-queries.ts`：从同一份真值生成带标注的查询，类型包括：精确型号、别名、系列前缀、属性组合（「内径 25 的密封轴承」）、描述性（「耐油的气管接头」）、口语和错别字、库里没有的。另有手写的 `queries.handwritten.json` 至少 60 条。相关条目集合由生成器的真值算出。
- `run.ts`：对指定的匹配实现跑全部查询，算 recall@5、MRR@5、空结果率、误给型号率（走到语义回退的纯型号查询，返回了规格里没有这串字符的别的型号；精确、别名、前缀命中不算）、单次检索 p50 / p95（不含 embedding 调用），按查询类型分列，写 `docs/reports/retrieval/<日期>/`。生成的产品库和向量缓存留在 `var/`，只提交生成器、手写查询和报告。
- 真实嵌入只在评测时调用一次，按指纹缓存；自测用确定性的假嵌入，不花钱不联网。

**新流程**（只改 10 R3 第 (4) 步，前三步不动）：

1. 精确型号、别名、去汉字后重试、系列前缀：与现在相同，命中就返回。
2. 属性解析：从当前产品库快照的规格里建「键 → 取值」词表，在查询里识别数值加单位、螺纹、电压、防护等级、类目名。只用无歧义的识别结果。
3. 候选集：先按类目，再按识别出的属性硬过滤；过滤为空时去掉属性条件，只留类目。
4. 关键词召回：在候选集上算 BM25，分词为汉字二元组加字母数字串（按 `normalizePartNo` 归一）。
5. 向量召回：在候选集上逐条算余弦，不再取全局前 k 再过滤。
6. 融合：两路名次做 RRF（k = 60），同分时有货在前。取前 5，结果顺序就是融合名次。
7. `exact` / `ambiguous` / `none` 的含义不变；语义回退路径上「纯型号查询，规格里必须字面出现这串字符」的规则不变，只作用在这条路径上（前缀命中照旧可以返回同系列的型号）。

1. 价格块里的每个数字都等于本轮工具结果或被接受订单里的同一字段，渲染器只做格式化，不做算术；工具没给 `total` 时块里没有合计。
2. 价格块放进去之后不再经过删句护栏；正文仍经过全部现有护栏。
3. 回复的最终文本（展开块之后）不超过 12 行、600 字（去空白后计）。
4. 本轮写了 `blocksSuppressed` 时，回复里没有任何块。
5. 包没有声明 `replyBlocks` 时，回复步骤表与现在逐项相同；跟进消息的步骤表不变。
6. 客户可见文本不含 `{{` 或 `}}`。
7. 同一租户同一时刻只有一个 epoch 是当前值；入站认领、`sending` 标记、会话写入都在比对 epoch 的同一事务里提交。
8. 等锁模式下，锁视图不是 `held`、或收到过 `process_epoch_stale` 的进程，不开始任何新的发送请求（含恢复补发与重试）。
9. 等锁模式下，重取锁时 epoch 已变的进程不恢复服务。
10. 未设 `TENANT_LOCK_WAIT` 时，启动、失锁、停机 spill 的行为与现在相同。
11. 等锁的进程拿到锁之前不监听端口、不连企微、不跑任务、不读写 `var/`、不写库（取锁查询除外）。
12. 补发窗口规则下，过了截止时刻的段不再发出请求。
13. `triage.ts`、`promote.ts` 不 import `src/packs`、`src/core/guards`。
14. `promote.ts` 生成的用例只含仿真数据，并通过 `validateCase`。
15. 精确型号、别名命中时的结果与现在相同，不经过混合检索。
16. 走到语义回退的纯型号查询，不会返回规格里没有这串字符的其他型号。
17. 混合检索每轮不查库、不多调模型，每个查询至多一次 embedding 调用。
18. 8 个锁定文件与 `eval/cases.json` 逐字节不变；旅游 v2 快照 0 差异。

## 决策卡

**D1 · 出数的形态（已定 A）**

- **A ★ 整块占位**：模型写 `{{试算明细}}`，代码渲染整块明细。模型只要守住一个占位符，遵守风险最低；没写就附在后面，客户总拿得到价。代价：比较句（「多买 8 件便宜 1.2 元」）只能由块里的「满 N 件 X 元」表达。
- B 逐数占位：模型写 `{{6207-2RS.单价}}` 这类引用，代码逐个填数。最自然，但小模型要守住几十个引用的写法，错位、漏写都要再设护栏，需要先实测遵守率。
- C 只追加、不占位：模型正文完全不提价格，代码在末尾附明细。最简单，但回复常写成「价格如下：」之后隔着别的话，读起来割裂。

**D2 · 价格块带哪些事实（已定 A）**

- **A ★ 单价、小计、合计、库存交期、下一档**：第 2、5 次被误删的对的内容，大多是交期、现货和跨档省钱提示，一起由代码出才能根治。
- B 只带金额：改动小，库存交期仍由模型写、由 `industrial_claims` 检查，误删照旧。

**D3 · 主备的写入保护（已定 A）**

- **A ★ 锁 + epoch 栅栏 + 失锁即停收**：锁连接断了而旧进程还活着的那几秒也不会双写。
- B 只等锁：改动最小，但锁连接断开后有最多约 13 秒（5 秒重取加 8 秒停机）两个进程都在处理消息。
- C 不做主备，只把发版改成「先起新容器再停旧容器」：没有崩溃接管。

**D4 · 备用进程常驻吗（已定 A）**

- **A ★ 常驻**：崩溃自动接管，发版也走同一条路径。等锁的进程不装载配置，内存开销小（第 0 步实测）。
- B 只在发版时临时起：省一点内存，崩溃仍靠 Docker 重启。

**D5 · 检索评测的规模（已定 A）**

- **A ★ 5000 条，生成查询加至少 60 条手写**：足够让过滤、关键词、向量各自的短板显出来，嵌入费用不到 ¥1。
- B 2000 条：便宜一点，差别可能不明显。
- C 不扩，只在 40 条上做：几乎测不出差别。

**D6 · 第 6 次要不要再换客户模型跑一遍（已定 A）**

- **A ★ 要**：和 16 一样，用换模型的差值说明结果不是某个客户模型特有的，约 ¥2。
- B 不要：省钱，前后对比只看 main。

**D7 · 仿真生成的用例放哪（已定 A）**

- **A ★ 公开的 `eval/cases-v2/`**：两边都是合成数据，人工核对后可以公开，每个 PR 都跑。
- B 私有层：和 17 的真实回归放一起，公开仓库里看不到闭环的结果。

## 开放问题

1. 企微对同一 msgid 是否去重：R4 实测后定，结果决定 `RESEND_UNKNOWN`。
2. 服务器上的 Caddy 能否按「第一个可连的上游」加连接重试：第 0 步 owner 贴出配置或授权只读查看后定写法。R3 让非活动进程一律不监听（等锁时不开、失锁时关），所以「能连上」就等于「是活动进程」；Caddy 做不到连接重试的话，改用主动探活。
3. 「满 N 件 X 元」会不会让回复读起来像推销：验收 5 抽检后定，不合适就只在客户问价格档位时带。
4. 检测器误报率多高算可以接受：第 6 次附表出来后，owner 看误报理由再定；在那之前不设门槛。
5. db 租户怎么拿到新的【硬性要求】和工具说明：交叉评审核实启动重新渲染会发布新版本；是否要过发布闸、闸的基线会不会因此失效，第 0.2 步读 01 的流程后写进 plan，必要时补一步。

## 被否决的方案

- **再调一个模型核对金额**：06 已实测，验稿通过率只有 12–14%，还多一次往返。
- **只加强事后护栏**（补「小计 360.00」这类写法的解析）：能堵上这个漏洞，但误删的问题照旧，客户还是会拿不到对的价。
- **精排模型**（交叉编码器）：多一次调用会吃掉 8 秒线，几千条规模下候选本来就能全部交给主模型读。
- **Postgres 全文检索、pg_trgm 或 pgvector + HNSW 入库**：要每轮查库，破 07 R11 的「每轮不查库」；中文全文检索还要装分词扩展。规模到单租户上万条再议。
- **外部协调服务选主**（etcd、Consul）：同一台机器、同一个 Postgres 下，advisory lock 加 epoch 就够了，多一个组件多一个故障点。
- **多活多副本**：要每会话锁、拉取选主、fence read 和全部进程内状态的迁移，改动面大，0.23 QPS 用不上；主备已经拿到可用性的大部分好处。
