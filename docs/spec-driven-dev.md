# wecom-sales-agent 的规格驱动开发（SDD）

规格是主产物，代码服务于规格。对实质性的工作，先写一份 RFC 式的 `spec.md` 说清问题、行为、设计决定、不变量和验收标准，再动手。小改动不走这套。

做法参考 DeepChat 的 `docs/spec-driven-dev.md`（Apache-2.0）并简化：架构讨论的结论写成 spec，实现由 coding agent 或人按 spec 做，`spec.md` 就是讨论与实现之间的交接物。

## 什么时候走 SDD

走：新模块、跨模块改动、数据迁移、公开契约（IPC / 协议 / 插件格式）、运行时架构、安全边界、以及任何「半年后有人会问为什么这么定」的决定。

不走：样式和文案、单一模块内的局部逻辑、常规文档修订、版本号与发版元数据。

判断标准只有一条：**如果一个能干的开发者拿到需求后必须自己发明架构，就需要 spec；如果他只需要在既有边界内写代码，就不需要。**

## 目录

每个目标一个 kebab-case 文件夹，按性质放：

- `docs/architecture/<goal>/` — 重构、迁移、依赖边界、共享契约、运行时架构、跨模块设计。**阶段性工作也在这里**，以两位数序号开头（`00-foundation`、`01-…`）。
- `docs/features/<goal>/` — 新功能、用户可见能力、集成、工具。
- `docs/issues/<goal>/` — 复杂 bug、回归、可靠性问题。

每个文件夹两个文件：

- `spec.md` — RFC。只保留有实际信息的段落，从这些里选：背景与问题、目标与非目标、现状与方案、所有权与依赖方向、接口与数据流、不变量与失败行为、兼容与迁移、安全 / 隐私 / 性能约束、**验收标准**、开放问题、被否决的方案。
- `plan.md` — 有序的实现步骤和它们的完成状态，包括最终审查、验证决定、清理和质量门。**这是唯一的执行跟踪，不建 `tasks.md`。**

复杂 bug 通常只要 `spec.md`（问题、影响、根因、修法、简短清单、验证结果、关联 issue）。

## spec 怎么写

- 写到「能干的开发者不用发明架构就能做局部决定」的程度，不写到伪代码。
- 接口用 TypeScript（或项目语言）签名给出，字段名是真实的。
- 不变量单独列，每条一句话，能写成断言或测试。
- **验收标准描述可观察的结果或可独立验证的契约**，不描述实现。好：「应用重启后未回答的权限弹窗仍在且可回答」；坏：「权限状态持久化到 SQLite」。
- 界面类 spec 覆盖加载、空、错误三种状态。
- 开放问题写清「什么时候、依据什么能定」，而不是留白。
- 顶部一行 `Status:`——`draft` / `ready` / `implemented` / `superseded by <link>`。
- `draft` → `ready` 只有 owner 能翻；agent 只能在验收全过、结果记进 plan 且 owner 确认后翻 `implemented`。
- 顶部可选一行 `Revisions:`——记录同一份 spec 内的就地修订：日期 + 改了哪个字段 + 旧的是什么 + 为什么。`Status: implemented` 之后不再使用。

## plan 怎么维护

- 步骤有序，每步一行，前面 `[ ]` / `[x]`；子步骤用 `10.1`、`10.2` 缩进，不重排已有编号。
- 实现过程中发现的新步骤直接加进去，不另开文件。
- 最后三步固定：对照当前全部验收标准逐条验证、清理临时探针和测试、更新 spec 的 `Status`。
- 交接记录按日期追加在步骤之后：已完成 / 半成品状态 / 阻塞 / 下一步。
- plan 不复制 spec 的内容，只引用。

## 改变决定

不改旧 spec。新建一个 spec 说明改了什么、为什么、旧的哪些部分作废，旧 spec 顶部标 `Status: superseded by <link>`。决策记录只追加不改写，半年后仍能看到「当时为什么那么定、后来为什么推翻」。

例外：spec 还是 `draft` / `ready`、且尚无代码依赖该契约时，可以就地修订，条件是在顶部 `Revisions:` 写清日期、改了什么、旧的是什么、为什么改。一旦 `Status: implemented` 或已有代码依赖，只能新建 spec supersede。

跨阶段的技术选型另外写 ADR 放 `docs/adr/`。

**公开与私有的边界**：影响贡献者和用户的决定（许可证、边界、接口、取舍）进公开的 spec / ADR；市场判断、定价、目标客户、营收、谈判相关的内容不进仓库，放仓库外的私有笔记，ADR 里只留一句「另记」。

## 和代码 agent 的交接

- 开工不需要指令。agent 自己找当前阶段：序号最小、`Status: ready`、`plan.md` 里还有未勾选步骤的那份 spec，从第一个未勾选的步骤（或交接记录里写的半成品状态）接着做，动手前说一句选了哪份 spec 哪一步。要指定别的目标时才说「按 `docs/<...>/spec.md` 实现」。
- agent 读 `AGENTS.md`（硬规则）→ 读 spec → 维护 plan → 跑门禁 → 标 status。
- spec 不够用时 agent 应停下来说缺什么，而不是自己补架构。缺的部分由 owner 决定后补进 spec。
- 门禁（format / lint / typecheck / test）由 git hooks（lefthook）和 CI 强制，对所有 agent 和人一视同仁，不依赖 agent 自觉。
- 任何两次会话都互不记得对方，`plan.md` 是唯一的交接面。每次停下之前必须把「做完的 / 做到一半的（代码停在什么状态）/ 下一步」写进 `plan.md`；同一个 worktree 同一时间只让一个 agent 干活，并行用 `git worktree`。

## 主参考与 spec 的关系

`docs/architecture/master-reference.md` 是「从哪来」：所有决策、参考项目、取舍都在那里。各阶段的 `spec.md` 是「做什么」：从主参考里裁出当前阶段需要的部分，补上接口和验收标准。主参考不直接指导编码；spec 才是。主参考的「分阶段路线」一节是各阶段 spec 的目录。
