# ADR-003：公开 / 私有边界：开源核心 + 私有运营层

- **状态**：采纳
- **日期**：2026-09-25
- **背景**：本仓库以 MIT 公开并继续公开开发，产品化之后会出现四类不能进公开仓库的东西：客户数据、生产配置、来自真实对话的评测集、运营设施。GitHub 上推送过的提交即使改写历史，`refs/pull/*` 中的副本也只能联系 GitHub 支持清除，所以边界要在写代码之前定好，并由门禁拦截。

---

## 决策

### 1. 许可证

- **已发布的 MIT 版本不动**，也不改写历史。`main` 上的 `demo-v1` 标签是基线。
- **以后的 core 继续用 MIT**，不换 AGPL、BSL、SSPL，也不加附加条款。
- **预设一个触发条件**：发现有人基于本仓库的 core 做同类商业产品，就从下一个版本起改用 FSL-1.1-MIT。托管服务和出售私有化部署都算同类商业产品。已经发布的版本不受影响。
- **外部贡献**：
  - 暂不接受外部 PR；接受时使用 DCO（`Signed-off-by`）。
  - 不需要 CLA。MIT 授予了再许可权，贡献进来仍是 MIT；以后并入 FSL 版本时，保留原版权声明和许可声明即可。
  - 只有 core 改成 copyleft 协议时，CLA 才是前提。

### 2. 划分规则：代码按「谁用得上」分，数据按「从哪来」分

| 放在哪        | 放什么                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本仓库（MIT） | 任何部署者都用得上的代码：<ul><li>引擎 core：LLM 层、护栏流水线、价格出口校验、前缀缓存</li><li>企微渠道</li><li>Postgres schema、多租户 RLS 及其测试套件</li><li>`/console` 后台：账号、审计、价格确认闸、报价快照</li><li>评测框架（cases v2、模拟客户、pass^k）和合成用例</li><li>两个参考行业包：定制游（虚构数据）、电商售后（合成数据）</li><li>通用的 compose、从 tag 部署、备份脚本</li><li>本 ADR</li></ul> |
| 私有仓库      | 只有运营方才用得上的东西：<ul><li>生产配置覆盖（不含凭据）、租户清单、域名、runbook、恢复演练记录</li><li>脱敏后的真实评测集、客户数据导入脚本</li><li>来自客户的行业包（如有）</li><li>生产环境的组装入口</li><li>计费、开通自动化、跨租户看板等运营设施</li></ul>                                                                                                                                                  |
| 不进任何仓库  | <ul><li>客户的 SOP、产品、价格、政策：进数据库，在后台编辑</li><li>真实对话原文、客户资料原件：进数据库或私有存储</li><li>凭据：只放服务器上的 env 文件（01 起按 compose 服务拆分），不写进日志</li><li>市场、客户、合同等商业内容：另记</li></ul>                                                                                                                                                                   |

配套规则：

- **依赖方向**：公开代码不得 import 私有代码，只能是私有部分依赖公开的 core。
- **公开工具要能读仓库外的数据**：评测 runner 和导入脚本都接受 `--cases <path>` 这类外部路径，私有数据不用拷进本仓库。
- **客户环境里的实例**：部署在客户自有环境里的实例，只装 core 和该客户用到的包。计费、开通、跨租户这类运营代码不装进去。
- **公开文档**：spec、ADR、README 里涉及商业内容的地方只写「另记」。

### 3. 私有仓库的机制（第一段私有代码出现时才启用）

- 私有仓库的名称和位置不写进公开文档，另记。
- 私有仓库做外层 pnpm workspace，把本仓库作为 git submodule 挂进去。`workspace:*` 能直接链接公开的包，本仓库的工作区和 lockfile 保持干净。
- 启用时点：
  - 02 阶段第一次需要生产配置时，建私有仓库，只放数据和运维，不 import 代码。生产环境 = 公开 tag + 私有配置。
  - 出现第一段私有代码时，才切换成外层 workspace + submodule，最早在 04 抽取行业包时。
  - 在那之前，不承担双仓提交的成本。

### 4. 门禁拦截

- **行业包目录约定**：行业包一律放在 `src/packs/<name>/`，与总参考一致。
- **路径黑名单**：跑在 `pnpm lint` 里，pre-commit 和 CI 都会拦。除 00 spec 列出的 `.env`、`var/`、密钥文件、二维码等之外，还拦这三类：
  - `src/packs/` 下白名单以外的子目录。白名单从 00 起写死为 `travel`、`ecommerce-aftersales`；新增公开包要改白名单，并在 PR 里说明。
  - 仓库根目录的 `tenants/`。后台里合法的租户设置页等代码不受影响。
  - `eval/real/`。
- **内容黑名单**：「另记」类内容的词表本身不进仓库，从 CI secret 或被忽略的本地文件读取；命中时只报文件和行号，不回显内容。
- **密钥扫描**：CI 跑密钥扫描。
- **二维码不入库**：二维码图片编码了真实账号 ID，文本扫描器扫不出来。保持放在已被忽略的 `var/` 下，运行时读取；路径黑名单也拦任何位置的 `kf-qr*`。
- **本地 agent 配置不入库**：`.gitignore` 忽略 `.claude/*`，只放行共享的 `settings.json` 和 `hooks/`。

## 理由

- **值钱的东西不在代码主体里。** 值得保护的是客户的 SOP、产品和价格，来自真实对话的评测集，以及运营设施。按上面的规则把它们放进私有仓库或数据库，保护效果和闭源差不多，代码主体仍能公开开发、公开验证。
- **多租户、RLS 和后台都放公开。** 后台前端打包后本来就会下发到浏览器，藏不住；多租户的安全要靠 RLS 测试和登录限流，不能靠把代码藏起来。
- **现在换协议没有收益。** MIT 没有终止条款，已发布的版本收不回；决策 1 的触发条件尚未出现，换协议只影响以后新写的代码。
- **预案选 FSL-1.1-MIT。** 它拦的是同类商业产品，不拦「为被许可人提供专业服务」，两年后自动转回 MIT。
- **物理隔离优于源码可见的收费目录。** 同一仓库里放源码可见的收费目录（`enterprise/`、`.ee.` 这类做法），保护效果取决于协议能否执行；拆成两个仓库则不依赖协议。
- **黑名单按目录约定写。** 行业包目录只有一种写法，黑名单才拦得住；推上去的东西自己洗不掉，所以白名单从 00 起就写死，而不是等到 04 抽取行业包时再补。

## 被否决的方案

- **冻结公开仓库，新代码全部闭源**：已发布的 MIT 版本收不回，冻结只挡得住以后的代码；需要保护的东西（客户数据、真实评测集、运营设施）本来就不在代码主体里；后台前端打包后会下发到浏览器，藏不住。商业层面的考量另记。
- **行业包全部公开**：来自客户的词表、阈值和话术属于客户资料，不进公开仓库；而行业包本来就是独立的包，放私有几乎没有成本。这个方案有一条被吸收了：电商售后包用合成数据公开。
- **同一仓库里用 gitignore 覆盖目录**：实测公开的 pnpm-lock 会泄漏私有包的路径。
- **私有 fork**：GitHub 规定公开仓库的 fork 只能是公开的。
- **npm 私有包**：每改一次 core 都要发一次版。
- **现在就换 AGPL / BSL / SSPL，或加附加条款**：决策 1 的触发条件尚未出现；换成 copyleft 之后，接外部贡献还得先上 CLA。

## 后果

- **变好的**：core 继续公开开发、公开验证；私有部分靠物理隔离，不依赖协议能否执行；边界由门禁在提交前拦截，不靠人记。
- **代价**：
  - 切到外层 workspace + submodule 之后，改 core 要在两个仓库各提交一次，并更新 submodule 指针；两边的 CI 都要跑。
  - 路径白名单和内容黑名单要维护：新增公开行业包要改白名单，内容词表要随「另记」的范围更新。
  - 部署到客户自有环境的实例带着该客户用到的私有包，这部分代码只能靠合同保护，门禁和仓库隔离管不到。
- **以后变难的事**：
  - 已发布的 MIT 代码永远收不回，改协议只能从下一个版本起。
  - 公开 core 的接口一旦被私有包依赖，改接口要两个仓库同步。
